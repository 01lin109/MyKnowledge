## 1.EasyExcel流式解析
你在简历中提到，针对导入模块的 OOM 风险，你引入了 EasyExcel 流式解析，并在入库阶段采用了批量处理，将 5 万级数据的导入耗时降至 1.5s 。

- **问题：** 如果业务规模扩大，在每天上午 9 点的极端并发场景下，有 100 个网点同时上传 5 万行数据的 Excel，此时你的流式解析加批量入库策略可能会遇到什么瓶颈？数据库连接池、MySQL 锁机制以及 JVM 内存分别会发生什么现象？你会如何进一步从架构层面（比如结合你用过的 RabbitMQ ）改造这个导入流程，以保证系统的主业务不受影响？
### A：我的回答
这种情况下即使引入了EasyExcel流式解析以及批量处理仍有OOM的风险，甚至导致数据库压力过大而宕机，可以引入消息队列进行消峰，设置一次导入的上弦，异步的把导入任务按文件拆解，防止一次性太多导入文件涌入服务。
### B：回答点评：
#### 🚨 面试官的犀利点评（你回答中的不足）：

1. **避重就轻，缺乏底层现象的剖析**： 我题目中明确问了“JVM 内存、数据库连接池、MySQL 锁机制分别会发生什么现象”，你用一句“导致数据库压力过大而宕机”一笔带过了。大厂面试官非常看重你对**底层灾难现场的推演能力**，因为这决定了你能不能在线上排查真实的线上故障。
    
2. **异步拆解的颗粒度不够**： 你提到“把导入任务按文件拆解”，但如果每个文件依然是 5 万行，10 个消费者同时拉取 10 个文件，数据库依然要瞬间承受 50 万行的并发写入，这叫“转移了压力”，不叫“解决了压力”。
    
3. **忽略了 IO 与内存的隐形杀手**： 如果 100 个网点同时上传，哪怕你用了 MQ，这 100 个 Excel 文件（假设每个 5MB）在进入 MQ 之前，是先通过 HTTP 传到你的 Java 后端内存里的。这 500MB 的突发大对象极有可能在放入 MQ 之前，就直接把 Tomcat 线程池和 JVM 内存打爆了。
### 🌟 满分参考答案（大厂标准架构图景）

如果是我，我会这样回答这道题，分为“灾难推演”**和**“架构重构”两部分：
#### 第一部分：极端并发下的灾难推演（What & Why）

“面试官您好，在每天上午 9 点 100 个网点并发上传 5 万行 Excel 的场景下，如果不做限流和架构改造，系统会经历以下连环崩溃：

1. **JVM 内存雪崩**：100 个 HTTP 请求瞬间涌入，虽然用了 EasyExcel 流式读取，但 Tomcat 处理请求的线程数激增。更致命的是，由于下游数据库写入变慢，导致 EasyExcel 读取的流阻塞，对象囤积在内存无法释放。JVM 老年代迅速填满，触发频繁的 **Full GC**，CPU 飙升至 100%，整个服务进入“假死”状态，最终抛出 `OOM: GC Overhead Limit Exceeded`。
    
2. **数据库连接池耗尽**：假设我们的 HikariCP 最大连接数配置为 20，但并发有 100 个线程需要拿连接去执行批量 Insert。大量线程会阻塞等待连接，最终超过 `connectionTimeout`，抛出连接获取超时异常。
    
3. **MySQL 锁冲突与长事务**：如果我们将 5 万行数据包在一个 `@Transactional` 里，这是一个典型的**长事务**。它不仅会长期占用连接不释放，还会持有大量的行锁。如果不同网点的数据有涉及相同设备的更新操作，极易引发死锁（Deadlock）；甚至在某些隔离级别下，大量的行锁可能升级为表锁，导致整个业务库瘫痪。”
    

#### 第二部分：基于 MQ 的高可用导入架构重构（How）
[[Kafka]]
“为了彻底解决这个问题，我会将同步导入改造为『对象存储分离 + MQ 异步消费 + 进度反馈』的架构：

1. **存储剥离（上传即走）**： 前端不再直接把文件二进制流传给后端，而是通过签名直传到 **OSS（如阿里云 OSS 或 MinIO）**。前端拿到文件的 URL 后，只把 URL 和操作人信息传给我的后端接口。这样瞬间解除了 Java 后端接收大文件的内存和带宽压力。
    
2. **MQ 异步削峰**： 后端接口收到 URL 后，在数据库的 `import_task` 表里生成一条记录（状态为：排队中），然后将任务组装成消息丢入 **RabbitMQ**，并立刻给前端返回“任务已提交”。
    
3. **平滑消费与分批入库（核心策略）**： 启动一个专门的 Consumer 服务监听队列。设置 `prefetch count`（预取数量，比如设为 2），限制同一台机器同时只处理 2 个文件。
    
    - Consumer 下载 OSS 文件并用 EasyExcel 读取。
        
    - **关键点**：抛弃大事务。在 EasyExcel 的 `ReadListener` 中，每积累 1000 条数据，就通过**编程式事务**（`TransactionTemplate`）执行一次批量入库并提交，而不是用声明式大事务。这极大地缩短了持锁时间，保护了 MySQL。
        
4. **闭环反馈机制**： 因为是异步的，前端怎么知道结果？前端可以通过轮询查看 `import_task` 表的状态，或者我们在后端处理完毕后，通过 **WebSocket** 主动向前端推送成功/失败以及失败的具体行数，完成业务闭环。”
### 延伸：
针对 Java 导入模块在处理 10w+ 级数据时的 GC 压力与耗时问题，对比研究了 Go 语言的并发模型。提出并 demo 验证了基于 **Go 协程池 + Channel 管道** 的流式导入方案，在模拟测试中，相较于原 Java 线程池方案，内存开销降低了 60%，处理速度提升了 2 倍。
