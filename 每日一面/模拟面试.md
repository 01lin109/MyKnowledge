# 导入优化
## 布隆过滤器
[[清能互联实习#2.布隆过滤器是否多余]]
#### 1. 针对假阳性（误判存在导致新增误入更新流）的处理
布隆过滤器的核心是“判断不存在则绝对不存在，判断存在则可能存在”。在我们的导入场景中，它主要用来做前置“粗筛”：

- **绝大多数新增数据被 100% 拦截**：由于不存在的数据绝对不会被误判为“不存在”，因此绝大部分新数据直接进入**纯新增流**批量写入，完全避免了无意义的数据库查询。
    
- **利用数据库原子能力做无感知降级（方案 B）**：
    
    - 对被误判进“更新流”的少量新增数据，无需在应用层提前做额外的 DB 查询。
        
    - 数据库表本身建立了**唯一业务键/主键**索引，批量执行 `UPDATE` 时根据返回值判断（`rows affected == 0`）。若受影响行数为 0，说明该记录在库中根本不存在，代码捕获后直接触发降级补偿机制，将该条数据回流补录到**新增流**写入即可。
        
    - _(或者直接说明：我们在底层批处理中直接利用了 MySQL 的 `INSERT ... ON DUPLICATE KEY UPDATE`，即使分流出现假阳性，数据库层也会自动保证存在则更新、不存在则插入。)_
        

#### 2. 布隆过滤器的动态维护与后续扩展

由于标准布隆过滤器基于 BitMap 和哈希置位，**不支持原生物理删除**（删除置 0 会影响命中相同 Bit 位的其他记录）：

- **当前业务方案（低频导入场景）**：
    
    - 因为电厂数据导入并不是高频实时行为（通常是周期性/批处理导入），我们采取的是**离线异步全量重建 + 内存原子指针替换（Double Buffering）**。在导入周期前，后台线程按主键流式读取并构建新的布隆过滤器，构建完毕后一次性原子替换旧实例，随后释放旧内存，从根本上防止 Bit 位饱和膨胀。
        
- **扩展方案（高频/持续增删场景）**：
    
    - 如果后续遇到高频实时导入或存在频繁物理删除的场景，可以演进为**布谷鸟过滤器原生支持 `Delete` 操作。
        
    - **但布谷鸟过滤器的后续维护成本明显更高，原因主要在于**：
        
        1. **内存与扩容成本高**：布谷鸟过滤器在负载因子较高（通常超过 90%~95%）时，插入会频繁触发踢出甚至陷入“踢出死循环（Cuckoo Loop）”，需要预留更多空间或频繁扩容，扩容迁移成本远高于纯位图操作。
            
        2. **删除可能导致“假阴性（误删）”**：由于它只存储元素的指纹信息（Fingerprint），如果两个不同的元素哈希值相同且指纹完全一致，删除其中一个会导致另一个在过滤器中也“被删除了”（即破坏了“不存在绝不误判”的底线原则）。
            
        3. **实现与运维复杂度高**：相比纯单机/分布式 BitMap 的高并发无锁操作，布谷鸟过滤器的踢出置换需要更多的并发锁控制，在分布式集群环境（如 Redis/Redisson 节点扩缩容、数据持久化）下的运维排错和稳定性要求显著更高。

## 假阳性兜底---Upsert死锁

### 1. Upsert 批处理为什么容易出现死锁（解决：排序）
`Upsert` 本身不一定导致死锁，**批处理让一次事务涉及更多数据、持锁时间更长，如果多个事务访问相同数据的顺序不同，就容易形成死锁。**
例如两个事务同时批量 Upsert：

```
事务 A：Upsert [1, 2, 3]
事务 B：Upsert [3, 2, 1]
```

执行过程可能是：

```
A：拿到 id=1 的锁
B：拿到 id=3 的锁

A：继续 Upsert id=3 → 等待 B 释放锁
B：继续 Upsert id=1 → 等待 A 释放锁

        ↓

A 等 B
B 等 A
        ↓
      死锁
```

所以批处理本身不是死锁的根因，**核心还是多个事务之间存在循环等待**。批量操作只是让事务持有更多锁、更长时间，从而增加了发生死锁的概率。

常见解决方式就是：**统一数据处理顺序、控制批次大小、缩短事务、必要时对死锁进行重试。**

---
### 2. MyBatis Batch 和“大事务”的关系
**MyBatis Batch ≠ 大事务。**
MyBatis Batch 主要解决的是：
> **把多条相同类型的 SQL 批量提交给 JDBC，减少数据库网络 IO 和执行开销。**
而事务解决的是：
> **这些 SQL 到底什么时候提交、什么时候回滚。**

所以两者是两个维度：

```
MyBatis Batch
    ↓
控制 SQL 的批量执行 / flush

事务
    ↓
控制 COMMIT / ROLLBACK
```

例如：

```
10000 条数据
↓
每 1000 条 Batch Flush
↓
共 Flush 10 次
```

如果外面是一个事务：

```
BEGIN
 ├─ Batch 1000
 ├─ Batch 1000
 ├─ Batch 1000
 ├─ ...
 └─ Batch 1000
COMMIT
```

这就是**一个大事务 + 多次 Batch 执行**。

但如果自己设计成每 1000 条一个事务：

```
BEGIN → Batch 1000 → COMMIT
BEGIN → Batch 1000 → COMMIT
BEGIN → Batch 1000 → COMMIT
...
```

就是**多个小事务 + Batch 执行**。

所以最关键的一句话是：

> **MyBatis Batch 的批次大小和事务大小是两个概念。Batch 决定一次批量执行多少 SQL，而事务大小取决于我们自己的事务边界和配置，比如 `@Transactional` 的范围。**

对你这个**批量 Upsert 落库、减少网络 IO**的场景，比较合理的组合通常就是：

**MyBatis Batch + Upsert + 合理大小的短事务**。

# 线上排查慢SQL
#### 1. 线上慢 SQL 标准排查路径与 `EXPLAIN` 核心字段

**线上排查标准路径（4 步法）：**

1. **告警确认与上下文收集**：通过 APM 监控平台（如 SkyWalking/CAT）或慢查询日志（Slow Query Log）**或者我们的HMP监控平台**，获取慢 SQL 完整语句、执行耗时、发生频次以及当时的业务入参和数据库负载（CPU、连接池打满情况）。
    
2. **区分“真慢”还是“偶发”**：排查慢是由**锁等待/事务阻塞**、连接池耗尽引起的，还是由于**数据量膨胀/执行计划走偏**导致的。
    
3. **分析执行计划**：在预发/从库环境带入真实参数执行 `EXPLAIN`，必要时开启 `optimizer_trace` 深入查看优化器的成本评估（Cost）。
    
4. **制定优化方案并灰度上线**：按优先级评估——加索引/改联合索引 > 重构 SQL（拆分/规避深分页）> 引入缓存/ES > 分库分表归档。在低峰期通过 DDL 工具（如 gh-ost/pt-online-schema-change）无锁变更上线并持续监控。
    

**`EXPLAIN` 重点关注的 4 个核心字段：**

- **`type`（访问类型）**：衡量查询性能的核心指标。性能从优到差依次为：`system > const > eq_ref > ref > range > index > ALL`。生产要求至少达到 `range` 级别，杜绝 `ALL`（全表扫描）和无过滤条件的 `index`（全索引扫描）。
    
- **`key` / `possible_keys`**：`possible_keys` 表示可能用到的索引，`key` 表示实际最终选用的索引（若为 `NULL` 说明没走索引或优化器认为全表扫描成本更低）。
    
- **`rows`**：预估需要扫描检查的行数。值越小，I/O 开销越低，索引区分度越好。
    
- **`Extra`（额外信息）**：
    - **好现象**：`Using index`（覆盖索引，无需回表）、`Using index condition`（ICP 索引下推）。

#### 2. 针对核心查询的联合索引设计深度剖析

目标 SQL 语句：

```sql
SELECT id, order_status, total_amount 
FROM t_order 
WHERE user_id = 1001 
  AND order_status IN (1, 2) 
  AND create_time >= '2026-10-01 00:00:00' 
ORDER BY create_time DESC 
LIMIT 20;
```

##### (1) 联合索引的最佳设计

- **推荐索引方案**：`idx_user_status_time (user_id, order_status, create_time)` _(或者在特定场景下权衡为 `idx_user_time_status (user_id, create_time, order_status)`，具体见下文原理解析)_
    

##### (2) 为什么是这个字段顺序？
> **联合索引一般按照：等值查询 → 枚举/多值查询 → 范围查询。**

比如：

```
WHERE user_id = 1001
  AND order_status IN (1, 2)
  AND create_time >= '2026-10-01'
```

所以设计：

```
(user_id, order_status, create_time)
   ↓          ↓            ↓
 等值        枚举          范围
```

为什么？

### ① 等值放最前面

```
user_id = 1001
```

它可以直接把索引定位到：

```
所有 user_id = 1001 的数据
```

相当于先把搜索范围砍掉一大块。

---

### ② 枚举放中间

```
order_status IN (1, 2)
```

它本质上可以理解成：

```
order_status = 1
或者
order_status = 2
```

所以在已经找到 `user_id=1001` 的基础上，再继续缩小：

```
user_id=1001
    ↓
status=1 / status=2
```

这样扫描的数据更少。

---

### ③ 范围放最后

```
create_time >= '2026-10-01'
```

它不是一个具体值，而是一段范围：

```
2026-10-01
      ↓
2026-10-02
2026-10-03
2026-10-04
...
```

一旦走到范围，索引就从“精准定位”变成了“扫描一段范围”。

所以把它放最后：

```
user_id = 1001
       ↓
status IN (1,2)
       ↓
create_time >= xxx
```

可以先通过前面的等值、枚举条件**尽可能缩小范围**，最后再做范围扫描。

---

### 你就记这个图

```
联合索引：

(user_id, order_status, create_time)
     ↓           ↓          ↓
    等值        枚举        范围
     ↓           ↓          ↓
  精确定位 → 进一步缩小 → 范围扫描
```

**本质就是：**

> **能精准定位的条件先用，能进一步缩小范围的条件继续用，最后才进入范围扫描。**

所以才有我们平时说的：

**等值 → 枚举 → 范围。**
