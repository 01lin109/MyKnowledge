# 1.职业规划（技术支持）
“关于职业规划，我一直信奉的是雷总提出的那套方法论**‘看 5 年、想 3 年、踏踏实实做好一两年’**的节奏。结合飞书的业务形态，我的具体规划是这样的：

**首先，立足当下做好一两年：在技术支持岗位上纵深扎根，建立技术底座。** 初期做好日常工单，OnCall的处理工作同时呢，更需要从每天处理的问题和高频需求里**做共性归纳与沉淀**，而不是只停留在单点救火，在这个过程中逐步建立起对飞书全局架构与能力的宏观理解。_”

**其次，想三年：沉淀出大客户集成全局观，走向更具商业或架构价值的生态位。** 我在之前的产品交付实习中深刻体会到：**交付质量和解决方案的天花板，高度取决于你对产品宏观把控与边界的理解。** 3 年左右，随着我对飞书底层技术和企业真实业务场景的理解足够深入，我会考虑两种发展形态：

- **第一种是内部向‘售前解决方案架构师（SA）’演进**：把技术支持时期‘从实际企业问题里摸索出来的边界经验转化为商业赋能的能力，在前端为大客户出具更严谨、更具落地性的解决方案；
    
- **第二种是在技术支持线向‘资深技术专家 / TAM’深耕**：如果业务在 Agent、复杂生态上有更深的技术攻坚需求，我也非常愿意在技术支持线继续承担架构级保障和疑难攻坚的工作。

**最后，看五年：放眼全球化，服务 Lark 的出海与海外生态。** 字节和飞书的国际化一直是非常重要的战略方向。我一直计划在秋招结束后好好强化英语，考个雅思把语言能力打扎实。如果未来 3 到 5 年团队有出海或跨国业务机会，我希望自己不仅能服务国内客户，更能无缝承接 Lark 海外企业客户的技术支持与解决方案落地。”
# 2.选择技术支持的动机
“对我来讲，校招求职主要就在研发和技术支持这两个方向之间权衡。结合之前的几段实习复盘，我选择技术支持主要有三点原因：

**第一，源于我对工作‘正反馈和成就感’的自我认知。** 在我之前的交付和开发实习中，我发现比起按部就班照着 PRD 去写常规的业务功能，我真正觉得有深度正反馈的瞬间，反而是**和业务人员对接实现细节、深挖排查复杂的 Bug，以及自己开发工具和 Skill 去解决工程问题**的时候；在交付实习中帮客户彻底扫清集成障碍的满足感，也远大于单纯交付一段代码。而技术支持恰恰能提供的就是这种承上启下的工作环境，向上要解决客户的各种问题，向下也需要和开发，产品对接提供建议

**“第二，是技术支持岗位的成长空间相较于纯开发更加多元和灵活。**
纯研发的成长路径通常比较聚焦在技术栈和系统内部的纵向深耕；而技术支持处于**技术、产品边界和真实企业业务**的三者的交汇处。虽然初期都会扎根在某个具体的核心模块里，我们日常处理的也是真实企业的集成痛点。
这种‘既懂技术细节、又懂产品边界、还见过大量真实业务场景’的复合积累，让未来的发展路径宽得多：
- **走技术线**，可以持续深耕，成为负责核心模块疑难攻坚的资深技术专家或 TAM；
- **走业务与架构线**，在技术支持一线摸爬滚打积累出来的系统集成边界认知，正是未来转型**售前解决方案（SA）**甚至客户成功（CSM）最核心的护城河。
对我而言，这种兼具技术硬实力与业务视角的岗位，在职业发展上拥有更灵活的前景

**第三，也是二面时面试官给我的启发：在 AI 时代，技术支持工作仍然强调人的经验。** 现在的很多标准代码都可以靠 AI 辅助完成，但在企业级技术支持中，客户报过来的问题往往是非常模糊的，夹杂着复杂的业务上下文。虽然我们有智能 OnCall 和 Agent 工具来帮我们拉日志、做初筛，但**如何在充满噪音的复杂报错中快速还原真相、如何用经验做出边界权衡，并用切实高效的行动赢得企业客户的信任**，人的经验在这个闭环里依然起到举足轻重的作用。这让我坚信这是一个长期有价值、有护城河的赛道。”
# 3.Agent相关
### 一、 简历项目深挖（必考：验证你是不是“调包侠”）

既然你简历上有 OnCallAgent，Leader 一定会借题发挥。他不会问理论，而是死抠**工程落地的“脏活累活”**：

1. **“知识库检索召回不准、或者模型产生幻觉给错了排障建议，你怎么解决的？”**
    
    - **考点**：RAG 优化细节。
        
    - **回答核心**：切片粒度（Chunking）优化、引入关键词+向量的**混合检索（Hybrid Search）**、在 Prompt 里增加强约束（_“必须严格基于参考文档作答，未提及的一律声明未知”_），以及文档元数据（Metadata，如按服务名、错误码打标）过滤。
        
2. **“手册文档如果有变更，或者排障方案更新了，你的 Agent 怎么保证知识的时效性？”**
    
    - **考点**：知识库的增量更新与生命周期管理。
        
    - **回答核心**：不是每次全量重新向量化，而是基于文档变更事件做增量同步（Upsert/Delete），配合版本号或时间戳淘汰老索引。
        
3. **“你怎么评估这个 OnCallAgent 的效果？有没有量化指标？”**
    
    - **考点**：业务指标闭环。
        
    - **回答核心**：不要只说“感觉挺好”。可以说：**Top-3 召回命中率**、**排障方案采纳率**、以及**人工二次介入修改率**。
        

### 二、 飞书生态集成与排障场景（考察你对飞书业务的即战力）

Leader 会模拟真实客户提交的工单，看你能不能秒懂背后的工程问题：

1. **“客户自建的 AI 助手接入飞书机器人，反馈说‘机器人经常隔十几秒才回复，而且偶发一条问题重复回答两三次’，你会怎么排查？”**
    
    - **考点**：飞书 Webhook 机制与异步解耦。
        
    - **回答核心**：
        
        - **根因**：Agent 推理或调外部工具耗时过长，超过了飞书 Webhook 回调的超时阈值（通常 3~5 秒），触发了飞书服务端的自动重试。
            
        - **解法**：建议客户改造为**异步架构**——服务端收到 Webhook 先秒回 `200 ACK` 截断重试，后台扔给任务队列慢慢跑，跑完后调用飞书 OpenAPI 的发消息接口，或者用消息卡片流式推回给用户。
            
2. **“企业自研的 Agent 想要在飞书里实现像 ChatGPT 那样的‘流式打字机’逐字输出，接口层面是怎么配合的？”**
    
    - **考点**：SSE（Server-Sent Events）与飞书新版交互式卡片（CardKit）机制。
        
    - **回答核心**：长连接推送流式 Token，利用飞书卡片的**流式更新（Streaming Update）能力**局部刷新内容，同时注意更新频率节流（Throttle），防止触发单卡片的限频。
        
3. **“如果客户的 Agent 要帮员工查工资、查审批，在权限和 Token 上要注意什么？”**
    
    - **考点**：飞书的鉴权体系与数据安全红线。
        
    - **回答核心**：不能乱用代表企业全局的应用身份凭证（`tenant_access_token`），涉及个人敏感数据必须使用用户授权的 `user_access_token`，确保数据权限遵循严格的 RBAC 隔离。
        

### 三、 概念边界与技术权衡（考察你的技术判断力）

不考死记硬背，而是考你在什么时候选什么方案：

1. **“在企业实际场景中，什么时候用 Prompt/知识库（RAG）就够了，什么时候才真正需要 Agent（Tool Calling）？”**
    
    - **回答核心**：
        
        - **RAG / 知识库**：解决的是“信息输入与问答”（只读、静态查资料，如查公司报销规范、查排障手册）。
            
        - **Agent**：解决的是“多步行动与状态变更”（带动作、动态决策，比如根据报错自动调接口拉日志、查机器 CPU、甚至自动提单）。
            
2. **“Function Calling 的底层原理是什么？大模型是真的自己去调接口了吗？”**
    
    - **回答核心**：模型本身不执行代码。模型只是根据用户意图和给定的 JSON Schema，**输出了一段符合格式的 JSON 参数**；真正的 API 调用是由宿主程序（我们的代码）执行的，执行结果再拼回给模型继续推理。
        

### 四、 灵魂拷问：人机协同与生产安全（考察你的底线思维）

在技术支持体系里，Leader 最担心的就是“盲目相信 AI 惹出大祸”：

- **典型问题**：“如果未来把排障 Agent 推广给支持团队，Agent 诊断错误给了一个有缺陷的解决方案，导致客户系统瘫痪，这种风险在流程上该怎么防范？”
    
- **满分回答**：
    
    > “任何辅助运维或技术支持的 Agent，在现阶段都必须严格定位为 **Copilot（副驾驶）**，绝不能脱离人机协同（Human-in-the-Loop）。
    > 
    > 1. **权限分级**：只读排查（查日志、拉配置）由 Agent 自动化跑完并整理证据链；但任何写操作、涉及客户生产环境的修改建议，必须做**高危红线阻断**。
    >     
    > 2. **证据链输出**：Agent 给出建议时，必须附带‘依据来源’（如引用了哪篇文档、匹配了哪条 TraceID 日志），方便工程师快速交叉验证。
    >     
    > 3. **人工终审**：最终发给客户的结论或在系统上点击执行的动作，必须由具备经验的一线支持同学做最后确认，永远让人承担最终把关职责。”
    >
