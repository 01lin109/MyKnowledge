### 第一部分：如何保障 Agent 调用工具的安全与边界？（防高危幻觉）

“面对大模型不可控的幻觉，我们的核心设计理念是：**绝对不信任大模型生成的任何高危参数。** 我们通过构建三道防线来保障系统安全：”
#### 1. 第一道防线：Prompt 层面的软隔离（基于 Multi-Agent）
不要把所有工具（查询、重启、扩容）都塞给同一个大模型。
- **做法**：采用你简历中提到的 Multi-Agent 架构。建立一个**只读 Agent**（只绑定查询日志、监控等 Query 工具）和一个**操作 Agent**（绑定重启、清理等 Execute 工具）。当用户的意图需要重启系统时，必须经过“意图路由”转发给操作 Agent，从物理上隔绝了普通咨询引发高危操作的可能。
#### 2. 第二道防线：代码层面的硬校验（Tool 层参数白名单）
不要指望大模型能 100% 遵守你 Prompt 里写的“不要重启核心容器”。
- **做法**：在开发 Go 语言的 Tool 函数时，进行强逻辑校验。比如在 `RestartPod(ctx, namespace, podName)` 这个函数内部，硬编码一个**白名单列表（Whitelist）**或者**正则表达式**。如果 LLM 幻觉生成了 `namespace="kube-system"`，Go 代码层直接拦截报错返回，绝不往下执行。
#### 3. 第三道防线：Human-in-the-Loop（人类在环审批机制）
这是大厂 AIOps 最核心的兜底。
- **做法**：对于高危操作（如服务降级、重启实例），Agent **没有直接执行的权限**。它的动作是：生成一份“操作建议”，并通过企微/飞书发送一张 **卡片消息（Webhook）** 给真正的运维工程师。卡片上写着：“根据排查，建议重启 X 容器，参数 Y，是否同意？”。**只有人类点击了卡片上的【执行】按钮，后台回调接口才会真正去调外部系统。**

### 第二部分：Plan-Execute 如何打破无限循环？（防死循环挂机）

“Plan-Execute 架构最大的痛点就是大模型变成‘偏执狂’——计划错误 -> 执行失败 -> 生成同样的计划 -> 再次执行失败。为了打破这种循环，我的调度系统设计了以下兜底机制：”
#### 1. 物理层中断：最大迭代步数（Max Iterations）与全局超时控制
- **做法**：在 Plan-Execute 框架（如 Eino）的外层，设置硬性拦截。
    - **步数限制**：定义 `max_steps = 5`，只要 Replan 超过 5 次还没得出结果，引擎直接抛出 `MaxStepsReachedError` 强制退出。
    - **时间限制（结合 Go 并发）**：利用 Go 的 `context.WithTimeout`，给整个 Agent 的执行链路设定一个全局超时时间（如 30 秒）。时间一到，触发 `context.Done()`，所有正在执行的 Goroutine 立刻取消（这也是前面那道 Go 基础题的答案引申）。

#### 2. 逻辑层阻断：历史动作哈希去重（Loop Detection）

- **做法**：在 Re-plan（重新规划）节点，程序会自动检查 Agent 过去的“执行历史”。如果发现 Agent **连续两次调用了同一个工具，并且传入了完全一样的参数**，但都返回了失败。说明它陷入了思维死胡同。此时，系统强行给大模型注入系统提示语：“注意，你已经尝试过操作 X 并失败了，请勿重复，必须更换排查方向！”
#### 3. 业务层兜底：降级转人工（Escalation）

- **做法**：当触发上述的“最大步数”或“无限循环”阻断后，系统不应该只是抛出一个生硬的 Error。它会触发一个 **Fallback 机制**：将此前 Agent 收集到的所有监控截图、日志报错、以及尝试过的排查步骤，自动打包生成一个工单（Ticket），然后 @ 当天值班的真人 OnCall 工程师：“AI 排查失败，已尝试 A 和 B，请人类介入接管。”
