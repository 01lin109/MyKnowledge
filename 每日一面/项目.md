### 第一部分：如何保障 Agent 调用工具的安全与边界？（防高危幻觉）

“面对大模型不可控的幻觉，我们的核心设计理念是：**绝对不信任大模型生成的任何高危参数。** 我们通过构建三道防线来保障系统安全：”
#### 1. 第一道防线：Prompt 层面的软隔离（基于 Multi-Agent）
不要把所有工具（查询、重启、扩容）都塞给同一个大模型。
- **做法**：采用你简历中提到的 Multi-Agent 架构。建立一个**只读 Agent**（只绑定查询日志、监控等 Query 工具）和一个**操作 Agent**（绑定重启、清理等 Execute 工具）。当用户的意图需要重启系统时，必须经过“意图路由”转发给操作 Agent，从物理上隔绝了普通咨询引发高危操作的可能。
#### 2. 第二道防线：代码层面的硬校验（Tool 层参数白名单）
不要指望大模型能 100% 遵守你 Prompt 里写的“不要重启核心容器”。
- **做法**：在开发 Go 语言的 Tool 函数时，进行强逻辑校验。比如在 `RestartPod(ctx, namespace, podName)` 这个函数内部，硬编码一个**白名单列表（Whitelist）**或者**正则表达式**。如果 LLM 幻觉生成了 `namespace="kube-system"`，Go 代码层直接拦截报错返回，绝不往下执行。
#### 3. 第三道防线：Human-in-the-Loop（人类在环审批机制）
这是大厂 AIOps 最核心的兜底。
- **做法**：对于高危操作（如服务降级、重启实例），Agent **没有直接执行的权限**。它的动作是：生成一份“操作建议”，并通过企微/飞书发送一张 **卡片消息（Webhook）** 给真正的运维工程师。卡片上写着：“根据排查，建议重启 X 容器，参数 Y，是否同意？”。**只有人类点击了卡片上的【执行】按钮，后台回调接口才会真正去调外部系统。**

### 第二部分：Plan-Execute 如何打破无限循环？（防死循环挂机）

“Plan-Execute 架构最大的痛点就是大模型变成‘偏执狂’——计划错误 -> 执行失败 -> 生成同样的计划 -> 再次执行失败。为了打破这种循环，我的调度系统设计了以下兜底机制：”
#### 1. 物理层中断：最大迭代步数（Max Iterations）与全局超时控制
- **做法**：在 Plan-Execute 框架（如 Eino）的外层，设置硬性拦截。
    - **步数限制**：定义 `max_steps = 5`，只要 Replan 超过 5 次还没得出结果，引擎直接抛出 `MaxStepsReachedError` 强制退出。
    - **时间限制（结合 Go 并发）**：利用 Go 的 `context.WithTimeout`，给整个 Agent 的执行链路设定一个全局超时时间（如 30 秒）。时间一到，触发 `context.Done()`，所有正在执行的 Goroutine 立刻取消（这也是前面那道 Go 基础题的答案引申）。

#### 2. 逻辑层阻断：历史动作哈希去重（Loop Detection）

- **做法**：在 Re-plan（重新规划）节点，程序会自动检查 Agent 过去的“执行历史”。如果发现 Agent **连续两次调用了同一个工具，并且传入了完全一样的参数**，但都返回了失败。说明它陷入了思维死胡同。此时，系统强行给大模型注入系统提示语：“注意，你已经尝试过操作 X 并失败了，请勿重复，必须更换排查方向！”
#### 3. 业务层兜底：降级转人工（Escalation）

- **做法**：当触发上述的“最大步数”或“无限循环”阻断后，系统不应该只是抛出一个生硬的 Error。它会触发一个 **Fallback 机制**：将此前 Agent 收集到的所有监控截图、日志报错、以及尝试过的排查步骤，自动打包生成一个工单（Ticket），然后 @ 当天值班的真人 OnCall 工程师：“AI 排查失败，已尝试 A 和 B，请人类介入接管。”

# 2. 个人项目架构拷问（AI Agent 模式对比）

在你的“智能 OnCall Agent 系统”中，你基于 Eino 框架设计并实现了多个 AI Agent，包括基于 ReAct 模式的对话 Agent 以及基于 Plan-Execute-Replan 模式的智能运维 Agent 。

- **我的问题：** 在AIOps智能运维场景下 ，Plan-Execute-Replan 架构相比于单纯的 ReAct（Reason + Act）循环，解决了什么核心痛点？假设在 Execute 阶段，Agent 调用某个底层重启容器的API失败了，你的 Replan（重新规划）机制是如何获取报错上下文，并调整后续执行图的？
## 回答：
> **核心痛点解决：** 传统的 ReAct（Reason + Act）模式在处理简单问答时很高效，但在 AIOps 这种复杂、多步骤的运维场景中，很容易出现“死循环”、“遗忘最初目标”或“上下文超载”的问题。Plan-Execute-Replan 架构将“思考规划”和“执行”分离，**Plan节点**拥有全局视野，负责生成有向无环图（DAG）或步骤列表；**Execute节点**只管专注执行具体的单一任务（如查日志、调接口），稳定性大大提升。
> 
> **失败重排（Replan）机制：** 假设执行重启容器的 API 失败，Execute 模块不会直接报错崩溃，而是会将**错误上下文（如 HTTP 状态码、错误日志、甚至部分堆栈信息）**作为反馈（Feedback）回传给 Replan 模块。Replan 模块的大模型会根据最初的 Plan 和当前的错误反馈进行重新推理。例如，它可能会发现是权限不足，从而动态调整执行图，在当前步骤前插入一个“申请临时高权限”的动作，然后再重试重启，实现真正的“智能容错”。


# 对话Agent
## Q1：切分策略
  
> “在你的智能 OnCall Agent 项目中，内部文档和排障 SOP 格式比较复杂，请问你的知识库切分策略（Chunking）是怎么设计的？为什么这么选型？底层具体如何落地存储和映射？”

**核心回答提纲：**
**1. 选型动机与痛点权衡**
在文档切分上，传统的固定滑动窗口（如硬性每 500 字截断）在 OnCall 场景有两大致命伤：
- **结构截断**：极易把完整的排障命令、YAML 配置或代码块拦腰截断，导致模型理解出错。
- **检索与生成的天然矛盾**：切块过大（>800 字），向量表征被稀释，检索命中率暴跌；切块过小（<200 字），命中率虽高，但喂给模型时严重缺乏前后文依赖与环境背景。
为此，我们采用了“Markdown 标题层级切分结合父子文档索引（Parent-Child Indexing）”的串联方案。
**2. 核心架构与落地四步流水线**
- **第一步：按 Markdown 标题提取父块（Parent Chunk）**
    - 利用结构感知解析器，按照文档原生语义树（H1/H2/H3）拆分为相对完整的排障逻辑段落（通常 600~1000 tokens）。
    - 提取整条面包屑路径作为元数据（如 `{"path": "支付服务/HikariCP报错/排障步骤"}`），并赋予全局唯一 `parent_id`。
- **第二步：在父块内部递归细切子块（Child Chunk）**
    - 在每个父块内部，使用代码感知的递归字符切分器进一步拆分为高密度小块（约 150~250 tokens，带 20 tokens 重叠）。
    - 切分逻辑严格避开代码块（` ``` `）和配置语法内部，且每个子块元数据中强绑定 `parent_id` 并继承父级路径信息。
- **第三步：计算向量（仅子块）**
    - 仅批量调用 Embedding 模型对 **Child Chunk** 文本计算向量，**Parent Chunk 不做向量化**，保证语义聚焦度与向量空间的区分度。
- **第四步：双层存储分离落地**
    - **向量数据库（如 Milvus / Qdrant）**：仅存储 Child Chunk 的向量、子块文本与携带的 `parent_id`。
    - **文档 / KV 存储（如 Redis / DocStore）**：以 `parent_id` 为 Key，只存储 Parent Chunk 完整的 Markdown 大文本。
**3. 检索与反查工作流（闭环）**
- **高精召回**：用户提问（如“Hikari 连接池慢查询排查命令”）先在向量库中精准匹配到得分最高的 Child Chunk。
- **回溯反查**：应用拿到命中的子块后，提取其 `parent_id`，在内存中做 Set 去重（防止同篇文档多个子块命中导致重复拉取），随后以 $O(1)$ 复杂度直接从 KV 库读取完整的 Parent 文本。
- **组装 Prompt**：最终喂给大模型的是信息完备、代码完整的 Parent Chunk，既保证了“搜得准”，又解决了“答得全”的问题。

## Q2 ReAct模式详解：
#### 1. 核心定义与背景（一句话切入）

> “ReAct 是 **Reasoning + Acting** 的缩写，是目前构建自主 Agent 最经典的基础范式之一。它的核心思想是**将大模型的链式思考（Reasoning）与外部环境的工具执行（Acting）紧密交织在一个反馈闭环中**。
> 提出这个模式主要是为了解决两个极端痛点：
> 1. **纯 CoT（思维链）** 容易在封闭系统内‘自言自语’，导致幻觉累积且无法感知外部世界；
> 2. **纯 Act（行动模式）** 则类似于无脑调用 API，缺乏多步推演和任务规划能力。ReAct 正好结合了两者的长处。”

#### 2. 核心运行机制（拆解细节）

> “在具体实现上，ReAct 是一个标准的 **Thought-Action-Observation 控制循环**：
> 1. **Thought（推理）**：LLM 结合当前上下文思考：目标是什么、现状如何、下一步需要什么信息，决定是否调工具；
> 2. **Action（行动）**：模型输出结构化的工具调用请求（比如工具名和 JSON 参数）；
> 3. **Observation（观察）**：执行引擎拦截 Action，调用外部系统（如 API、数据库或搜索引擎），将真实结果回填到 Prompt 中。
> 这个循环会持续迭代，直到 Thought 判定信息已经完备，触发结束动作并给出最终答案。”
#### 3. 架构对比（展现技术视野）

> “在技术选型上，常将 ReAct 与 **Plan-and-Solve（规划-执行模式）** 对比：
> - **Plan-and-Solve** 是‘先定完整计划，再按图索骥执行’，适合确定性高的大任务，但缺乏容错机制，中间某一步报错整个流就断了；
> - **ReAct** 是**单步决策、边走边看**，具备极强的**动态自愈和反馈纠错能力**，外部工具报错了它能在下一个 Thought 里换个参数或换个工具重试，但在长链路任务中宏观规划能力稍弱。”

#### 4. 生产落地的工程考量（加分项，突出实战经验）

> “在实际业务中落地 ReAct，不能只停留在 Prompt 模板层面，有几个关键工程挑战：
> 1. **防死循环与超时**：模型可能会在某两个相似工具间反复横跳，系统层必须加硬限制（如 `max_iterations` 截断）和死循环探测；
> 2. **上下文膨胀（Context Overflow）**：Observation 抓取的数据如果过长（比如大段网页或日志），多轮循环后不仅 Token 成本剧增，还会引发模型注意力漂移，通常需要做中间摘要或向量截断；
> 3. **现代技术演进**：现在的工程实现（如基于 LangChain、LangGraph 或 Go Eino 等框架）已经很少用早期正则解析文本的方式，而是直接依赖底层大模型的 **原生 Function / Tool Calling** 能力，输出强类型的结构化调用，执行稳定性高很多。”
### 💡 面试官可能的追问预案（建议同步准备）

- **“如果一个任务步骤特别多（例如超过 15 步），ReAct 容易走偏怎么办？”**
    - _答题点_：结合层次化架构（Hierarchical Agent）或引入 Plan-and-Solve + ReAct 的混合架构——顶层 Planner 做宏观路线图，底层 ReAct 做具体步骤的动态自适应执行。
- **“工具调用报错时，怎么让 ReAct 更好地自我纠错？”**
    - _答题点_：规范 Observation 的错误回传格式（返回清晰的 Error Reason，而非单纯的 HTTP 500），并在 System Prompt 中预置 Few-Shot 告诉模型遇到此错误时该如何调整参数重试。
# 运维Agent
## Q1：AIOps 选 Plan-Execute 而不是 ReAct？
- **ReAct 的核心硬伤（单步推演的局限性）**：
    
    - **容易“失焦”或死循环（Goal Drift / Dead Loop）**：ReAct 采用“Thought $\to$ Action $\to$ Observation”的单步贪心策略。排障链路一旦超过 4~5 步（如查指标 $\to$ 查日志 $\to$ 查配置 $\to$ 查慢 SQL $\to$ 交叉比对），模型极易受到工具单次异常输出的干扰，忘记原本的排障主线，或者在两个工具间来回无效重试。
        
    - **Token 浪费与延迟极高**：每执行一步都要将前面所有步骤的观察结果全量塞回 Context 让模型重新思考，随着步骤加深，推理延迟成倍暴增。
        
- **Plan-Execute 的优势（全局规划 + 确定性执行）**：
    
    - **解耦规划与执行**：
        
        - **Planner（规划器）**：结合告警上下文和知识库检索出的 SOP，一次性生成一份全局执行计划（结构化的 Task DAG 或步骤列表，如 `[Step1: 查CPU指标, Step2: 抓取ERROR日志, Step3: 查活跃线程]`）。
            
        - **Executor（执行器）**：严格按照步骤调用工具执行，不让模型在每一步胡思乱想。
            
    - **动态重规划（Re-plan）兜底**：仅当某一步执行发生预期外的重大分支异常时，才将执行摘要交给 Re-planner 修正后续计划，既保证了全局目标的收敛，又大幅降低了延迟与 Token 成本。
        

**2. MCP 工具调用的安全防御与熔断机制**

在后端工程设计中，我们采用了“防御性边界设计”来确保高危工具调用的绝对安全：

- **数据与权限隔离（防误删 / 慢查询防护）**：
    
    - **账号层强隔离**：通过 MCP 接入的 MySQL 工具，底层配置专属只读数据库账号（强制 `READ ONLY` 权限），物理级阻断一切 `INSERT/UPDATE/DELETE/DROP` 操作。
        
    - **SQL AST 静态语法解析校验**：在后端执行器层，工具接收到模型生成的 SQL 后，先通过 SQL Parser 进行抽象语法树解析。强制要求必须带有 `LIMIT` 阈值（默认限制上限 100 条），且命中全局无索引查询或全表扫描风险时直接拒绝执行。
        
    - **连接保护与超时**：设置独立的数据库只读连接池，执行超时阈值压低到 3 秒以内，防止慢 SQL 拖垮业务数据库。
        
- **高危动作的人工介入（Human-in-the-Loop）**：
    
    - 将工具分级为“只读观测类”和“变更操作类”。
        
    - 对于服务重启、配置修改、Kill 线程等写操作或破坏性工具，Agent **只能生成操作建议工单**，必须触发告警群的人工审批确认回调（Webhook/审批按钮），人工确认后才由后端执行，杜绝模型自主误操作。
        
- **死循环熔断与异常兜底**：
    
    - **Max Iterations 强截断**：在 Eino 图编排的循环控制器上设置最大执行步数（比如最大 6 步），一旦超过阈值触发熔断，降级为“生成当前已知信息摘要 + 转交人工 OnCall”。
        
    - **Tool Execution Timeout**：每个外部 MCP 工具调用都挂载 Go 的 `context.WithTimeout`（如日志检索限时 5 秒），超时直接返回超时错误码给 Planner，由重规划逻辑选择跳过或降级处理，避免协程悬挂。

## Q2 高危指令防范
> “在你的 AIOps 智能运维系统中，Agent 需要调用诸如数据库操作、服务日志排查、甚至是杀死进程（Kill Process）这类工具。大模型存在幻觉、越狱（Jailbreak）和注入风险，请问你们在工程架构上是如何防止 Agent 误执行高危破坏性命令的？具体如何实现安全防御与人工介入（Human-in-the-Loop）？”
**核心回答提纲：**

**1. 核心认知与安全防线定位**
- **安全认知**：绝对不能依赖大模型的 System Prompt 来做安全约束。大模型本质上只负责规划并产出结构化的调用参数（JSON），**没有直接操作基础设施的权限**，系统调用权完全收敛在后端的 Executor 代码中。
- **防御原则**：采取“后端硬编码拦截 + 静态语法解析 + 物理权限隔离”的三层纵深防御体系（Defense-in-Depth），杜绝因模型失控或越狱对生产环境造成不可逆破坏。

**2. 三层硬隔离防御落地**
- **第一道防线：Executor 调度层的 AOP 硬拦截（状态机挂起）**
    - **元数据分级**：在工具注册中心将工具标记为“只读观测类（SAFE）”和“高危变更类（HIGH_RISK）”。
    - **代码级硬拦截**：Go 代码中的调度执行器内置拦截中间件。当检测到调用的工具属于高危类别（如 `kill_mysql_process`、配置变更）时，Go 代码的 `if-else` 分支直接打断执行，**物理阻断对底层 API 的调用**。
    - **状态挂起与建单**：代码将当前执行状态（Snapshot/Checkpoint）序列化存入 Redis，生成唯一的审批单 ID，将任务状态置为 `PENDING_APPROVAL`，并向前端返回等待状态。
- **第二道防线：参数语义层的 AST 静态解析校验**
    - 针对执行自由查询的工具（如 `run_mysql_query`），大模型可能在参数中注入恶意语句。
    - **语法树解析拦截**：后端在将 SQL 下发给数据库前，先通过 SQL Parser（如 `tidb/parser`）解析为抽象语法树（AST）。
    - **硬校验规则**：如果语法树根节点不是 `*ast.SelectStmt`（出现 `UPDATE`、`DELETE`、`DROP` 等 DDL/DML 操作），代码直接报错截断；同时强制在 AST 尾部追加 `LIMIT 100`，防止无限制全表扫描拖垮数据库。
- **第三道防线：基础设施与账号物理权限隔离**
    - **数据库只读账号**：Agent 主服务配置的 MySQL 连接账号在数据库层面被 DBA 赋予强隔离的全局 `READ ONLY` 权限。即使代码层全部失效，数据库引擎层也会直接以 `Access denied` 拒绝破坏性写入。
    - **特权凭证物理分离**：具备 Kill 进程或重启服务特权的凭证，**完全不配置在 Agent 服务中**，而是托管在独立的运维审批中心。只有当人工审批回调合法时，才由外部审批中心代为调用。
    
**3. 人工介入（Human-in-the-Loop）闭环流程**
- **群卡片推送**：任务挂起后，系统向飞书/企业微信值班群推送交互式 Webhook 卡片，明确呈现告警类型、大模型建议操作的命令、风险等级及影响评估，附带 `[ 确认执行 ]` 与 `[ 拒绝 / 转人工 ]` 按钮。
- **验签与鉴权**：值班工程师点击审批后，回调接口严格校验操作人权限并落库操作审计日志。
- **异步唤醒（Resume）**：验证通过后，审批中心以特权凭证调用底层动作，并将真实执行结果回填给原挂起的任务快照，唤醒 Eino 工作流继续向下复查指标并生成排障总结。


# LLM wiki
**LLM Wiki**（由 Andrej Karpathy 等人推广的概念）是一种全新的**持久复利型个人知识库（PKM）范式**。

它用一句话概括：**“Obsidian 是 IDE，LLM 是程序员，Wiki 是代码库，你则是产品经理。”**

### 一、LLM Wiki 是什么？它和传统 RAG 有何区别？

传统的“知识库 + AI”（如常见 RAG 向量检索）：每次提问时临时切片、匹配、合成答案，回答完就忘掉，知识库本身依然是一盘散沙。

**LLM Wiki 的核心是“增量复利”（Compounding Knowledge）**：

- **人类负责**：输入高质量原始信源、方向审阅、提出深层问题。
    
- **LLM 负责**：阅读材料，将内容拆解并更新到 10~20 个相关的原子概念词条中，建立双向链接 `[[...]]`，维护全局索引与变更日志。
    
- **结果**：你的 Wiki 就像维基百科一样，随着每读一本书、输入一份论文，所有实体（人物、概念、理论）的页面都在不断生长和交叉引用。
    

|**维度**|**传统个人笔记 / 传统 RAG**|**LLM Wiki 范式**|
|---|---|---|
|**维护成本**|随着笔记变多，整理分类维护成本极高|**接近零维护**，LLM 负责跨页面批量重构与链接更新|
|**知识沉淀**|问完即弃（临时生成摘要），互不关联|**持续沉淀**，以原子 Markdown 文件固化到本地|
|**链接网络**|极度依赖用户手动输入 `[[]]` 打标|LLM 自动维护双向引用与图谱关系|

### 二、三层目录架构（Vault Architecture）

搭建这套体系最关键的是**读写权限分离**：

Plaintext

```
My-Obsidian-Vault/
├── 01-Raw/           # 【人类专属】只读层：PDF、网页剪藏、原始会议纪要（LLM 只能读不能改）
├── 02-Wiki/          # 【LLM 专属】生成层：实体页、概念页、合成总结（人类只看不手写）
│   ├── Concepts/     # 核心概念原子页（如：注意力机制.md）
│   ├── Entities/     # 人物、组织、论文、工具页
│   ├── Index.md      # 全局主索引（目录树与概念图谱）
│   └── Log.md        # 维护日志（记录每次 Ingest 动了哪些文件）
└── SYSTEM_PROMPT.md  # 【契约规范】定义 frontmatter 规范、打标规则、命名约定
```



# 知识库文档发生变更后，Agent 底层应该如何感知并更新向量库？

#### 1. 考察核心

- 避免低效的“全量重新嵌入（Full Re-embedding）”造成资源浪费与向量索引震荡。
    
- 考察**事件驱动架构（Event-Driven）**、**语义语法树解析（AST）**以及**向量数据库的增量 CRUD 与垃圾回收机制**。
    

#### 2. 标准解答维度

- **变更感知层（Push + Pull 兜底）**：
    
    - **主通路**：接入文档源（如语雀）的 **Webhook**，监听文档更新/删除事件，将任务推入 MQ 削峰解耦。
        
    - **补偿通路**：利用文档元数据中的 `version` / `updated_at` 字段做定时轻量轮询，防止回调丢失。
        
- **差异判定层（AST 结构化切分 + 内容 Hash）**：
    
    - 将 Markdown 文档解析为 AST 树，按标题或段落粒度拆分为逻辑 Block。
        
    - 对每个 Block 维护一个内容签名（如 SHA-256），并持久化映射表（`DocID + SectionPath -> Hash`）。
        
    - **非语义变更过滤**：微小样式、排版改动或纯标点微调，通过阈值比对或段落不变性直接跳过向量化。
        
    - **增量下发**：仅对 Hash 失效或新增的 Block 打上 `DIRTY` 标记，流转到后续 Embedding 管道。
        
- **存储闭环层（精确 Upsert 与孤儿清理）**：
    
    - 向量库中 Chunk ID 采用确定性命名规则（如 `DocID_SectionHash` 或 `DocID_ChunkIndex`）。
        
    - 发生段落删除时，对比新旧 AST 树节点，向向量数据库下发标量过滤删除指令（如 `delete by expr: doc_id == X and chunk_id in [...]`）。
        

#### 3. 现场高光回答话术

> “针对文档变更，我们采用的是一套**事件驱动的细粒度增量刷新架构**，避免昂贵且破坏索引的全量重建： 首先，通过语雀的 Webhook 实时捕获更新事件，结合消息队列做削峰缓冲； 其次，利用 Markdown AST 将文档按语义段落结构化解析，并为各块计算 Hash 签名，只有真正发生内容变动的段落才会流转到 Embedding 环节，无语义变化的修改会被自动拦截； 最后，在向量数据库侧利用确定性 Chunk ID 与元数据执行精确的局部 Upsert 和废弃切片删除，保证了知识库时效性与存储成本的平衡。”

# 如何评测Agent的效果 
### 一、 拆解链路：分模块硬指标评测（最易落地、代码可量化）
你的项目用了 **Milvus (RAG) + Eino (Plan-Execute-Replan) + MCP (工具调用)**，整个链路很长。如果只测最终输出，出问题了根本不知道是知识库没搜到，还是工具参数传错了。所以第一步是**卡死中间件的硬指标**：

| **评测层级**                | **关注点**                         | **具体怎么测（可落地的工程手段）**                                                                | **核心指标**                                                | 解决措施                                     |
| ----------------------- | ------------------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------- | ---------------------------------------- |
| **1. MCP 工具调用层 (最核心)**  | 监控查询、日志拉取等 Tool 调得对不对           | 写几十个真实的告警输入，用正则或 JSON Schema 校验模型生成的 Tool Call。看它**选没选对工具**、**时间窗口/服务名等参数提取得准不准**。 | **工具选择准确率**、**参数合法率**（如：时间格式、必填项是否缺失，直接用代码 `assert` 校验） | [[#一、 针对“MCP 工具调用准确率/参数合法率低”的优化]]        |
| **2. RAG 检索层 (Milvus)** | 排障 SOP 文档召回得准不准                 | 不测大模型生成，只测向量检索。拿 30~50 个真实告警名称去搜 Milvus，看排在 Top-3 的文档块里有没有对应的 SOP。                 | **Top-K 命中率 (Hit Rate)**（代码跑个脚本几秒钟就能出结果）                | [[#二、 针对“Milvus (RAG) Top-K 召回命中率低”的优化]] |
| **3. 规划与收敛层 (Eino)**    | Plan-Execute-Replan 会不会死循环、耗时多长 | 统计每次排障走完的 Step 数量和 Token 消耗。运维有时效要求，一个告警分析转了 10 轮还没出来就是失败。                         | **平均推理步数 (Step Count)**、**死循环截断率**、**端到端耗时 (Latency)**  | [[#三、 针对“Eino 规划死循环 / 推理步数过多 / 耗时高”的优化]] |
### 二、 端到端评测：基于“历史工单回放 + Mock 沙箱”
面试官如果问：“那你怎么测整个 Agent 的排障结论对不对？难道每次测都要把线上服务器搞挂吗？”
这时候你抛出“故障回放（Replay）+ MCP 接口 Mock”方案，工程味直接拉满：
1. **怎么攒测试样本（不用搞几千条，20~30 条典型 Case 足够）：**
    直接从过去真实发生过的告警工单（或者你自己模拟的故障，比如 Redis 连接池打满、MySQL 慢查询引发 CPU 飙升、某微服务 OOM）里，抽取出当时的**告警报文**、**当时的监控指标快照**和**最终真实的根因结论**，存成 JSON 文件。
2. **为什么要做 MCP Mock（关键细节）：**
    因为评测时不能让 Agent 去查现在的实时监控（现在系统是正常的，查出来全绿，测不出排障能力）。所以在评测环境下，把 MCP Server 的返回结果替换成**当时故障发生时的历史监控/日志快照数据**。
3. **怎么判定结果对不对（关键点比对）：**
    不用人工一条条看。在每个历史 Case 里标注 2~3 个“必现实体词”（例如：根因必须包含 `慢SQL`、`order_table`；建议必须包含 `加索引` 或 `限流`）。先用代码做关键词/正则硬匹配，匹配不上的，再用一个小模型（或高阶模型）只针对“模型输出的根因是否与真实根因一致”打 0 或 1 的二分类分（比打 1~5 分靠谱得多）。
### 三、 生产环境闭环：靠“运维人员动作”收集隐式指标
如果面试官继续追问：“上线之后怎么持续评估效果？”
千万别说“让运维人员给每次回答点赞点踩”（实际上没人愿意点）。用**业务行为指标**说话：
- **工具兜底重试率：** 监控 Eino 框架里 Replan 的触发频率。如果某个工具经常因为参数报错触发 Replan，说明这个 MCP 工具的 Description 写得不够清晰，需要优化 Prompt 或 Schema。
- **SOP 采纳率 / MTTR（平均恢复时间）对比：** 告警触发后，Agent 给出排查结论和修复建议，看值班人员是直接采纳了建议去操作，还是完全无视 Agent 自己去翻日志。
- **红线指标（安全底线）：** **高危操作拦截率 / 幻觉率**。比如模型如果编造了一个不存在的 Pod 名称或日志报错，通过将模型输出中的实体词与 MCP 工具实际返回的数据做字符串比对（检查模型输出的 IP/Pod 是否出现在工具返回的上下文里），一旦发现无中生有，直接记为严重 Bad Case。
### 四、 面试现场可直接背诵的回答话术（约 1分半钟）

> “在 OnCallAgent 这个项目里，我们没有搞那种大而全的学术评测，因为运维场景非常看重**确定性**和**时效性**。我当时是把评测拆成了**‘模块级硬指标’**和**‘端到端故障回放’**两块来落地的：
>
> 
> **第一，把链路拆开测硬指标。**
> 
> 因为我用了 Milvus 做 SOP 检索、用 MCP 调外部监控工具，如果全堆在一起测，出问题了没法定位。所以我先针对 RAG 测 **Top-3 的 SOP 召回命中率**；针对 MCP 工具调用，写自动化测试脚本去跑几十个典型告警，直接用代码校验模型选的 Tool 对不对、提取的‘时间窗口’和‘服务名’参数合不合法，保证**工具调用准确率在 95% 以上**。
> 
> **第二，端到端效果我用的是‘历史故障回放 + MCP 数据 Mock’。**
> 
> 运维评测最大的痛点是不能在线上真造故障。我的做法是把之前出现过的几十个典型故障（像 CPU 飙高、数据库连接池满、OOM 等）当时的告警报文、Prometheus 指标和日志快照存成 JSON。评测的时候，通过 Mock 的方式让 MCP 工具返回当时的故障快照数据，看 Agent 能不能顺藤摸瓜定位到根因。
> 评判标准上，我也没有用那种虚的打分，而是只看三个硬指标：**1）根因定位是否命中关键故障点；2）Plan-Execute 循环有没有在规定步数（比如 5 步）内收敛，防止死循环；3）模型输出的 Pod 名、报错信息是不是全部来自工具返回的数据，确保零幻觉。**
> 每次我改了 Prompt、调了 Eino 的编排逻辑或者换了模型，都会跑一遍这几十个回放 Case，看看哪个指标掉了，针对性地去修 Bad Case。”

这套逻辑既有你项目里的具体技术栈（Eino、MCP、Milvus），又解决了运维场景最头疼的“环境不可复现”问题（通过 Mock 快照），面试官一听就知道你是真正在工程上琢磨过这个系统的。
运维 Agent 和普通对话问答 Agent 最大的区别在于：**运维场景不看重“文字写得多优美”，只看重“查得准不准、工具调没调对、花了几秒钟、有没有胡说八道”。**

面试官问这个问题，最反感听到直接照搬学术界的 BLEU、ROUGE 或者泛泛而谈“构建黄金数据集”。在工程落地上，你可以把评测体系拆成“分层拆解评测（组件级）+ 故障回放评测（端到端）+ 线上隐式反馈（生产级）”三个实打实的落地步骤来回答。

# Agent优化
### 一、 针对“MCP 工具调用准确率/参数合法率低”的优化
[[#一、 拆解链路：分模块硬指标评测（最易落地、代码可量化）]]
在评测中，最常见的问题是：**相对时间换算错误**（比如模型算错时间戳）、**乱传枚举值**（比如环境名传了 `prod` 而不是规范的 `production`），或者在相似工具间**选错工具**。
- **1. 参数前置加工与降维（代码代劳，不让模型算）：**
    - **问题：** 告警发生在 `14:05:00`，让大模型去推算前 15 分钟的 Unix 时间戳或 ISO 时间字符串，经常算错或格式不合法。
    - **解决措施：** 在 Go 编写的 MCP Tool Schema 中，**将绝对时间参数改为相对时间偏移量**。比如把 `start_time` / `end_time` 改为 `lookback_minutes: int`（默认 15），并在 Context 中直接注入告警发生的基准时间 `alert_timestamp`。具体的 `time.Add(-15 * time.Minute)` 换算逻辑全部下沉到 Go 代码内部执行，直接将时间参数错误率降为 0。
- **2. 强 Schema 约束与负向边界描述（Prompt & Schema 调优）：**
    - **问题：** `query_error_logs`（查错误日志）和 `query_trace_detail`（查链路追踪）经常被混用。
    - **解决措施：** 在 MCP 工具注册的 Description 中加入明确的**适用场景与禁用场景（Negative Prompting）**。例如：“仅在已知具体 `trace_id` 时调用此工具；若只有服务名和报错关键字，严禁调用此工具，请先调用 `query_error_logs`”。同时对环境、服务名等固定参数在 JSON Schema 中使用 `enum` 枚举锁死。
- **3. 报错信息结构化自愈（Actionable Error Feedback）：**
    - **问题：** 工具调用失败直接返回 `400 Bad Request` 或 Go 底层 panic 报错，Eino 触发 Replan 时模型不知道怎么改参数，导致连续重试失败。
    - **解决措施：** 在 MCP Tool 的 Wrapper 层拦截错误，将生硬的系统报错包装成**带修正指引的自然语言提示**返回给模型。例如：`"参数错误：service_name 'order' 不存在。当前可用服务列表为：['order-service', 'payment-service']，请修正后重试。"`
### 二、 针对“Milvus (RAG) Top-K 召回命中率低”的优化
[[#一、 拆解链路：分模块硬指标评测（最易落地、代码可量化）]]
在评测 SOP 召回时，最容易出现的问题是：**告警报文里全是噪声**（如长串的堆栈、随机 Pod ID `order-pod-7f8b9c-x2k`、IP 地址），直接 Embedding 后向量发生偏移，搜不到标准 SOP。
- **1. 查询前置清洗与实体抽取（Query Rewriting）：**
    - **问题：** 原始告警文本带有大量动态 ID 和时间戳，稀释了核心报错语义。
    - **解决措施：** 在进入 Milvus 检索前，先用 Go 正则表达式或极速小模型做一层**日志脱敏与特征提取**，剔除 IP、UUID、Pod 后缀和时间戳，只保留 `服务名 + 核心告警指标 + 异常类型`（如将整段报警精简为 `"order-service HighCPUUsage MySQL SlowQuery"`）再去生成向量检索。
- **2. 混合检索（Hybrid Search）+ 元数据过滤（Metadata Filtering）：**
    - **问题：** 运维场景中有很多专属错误码（如 `ERR_REDIS_OOM_004`、`ORA-01555`），纯稠密向量（Dense Vector）对这种精确字符匹配非常不敏感。
    - **解决措施：**
        - 利用 Milvus 的**标量过滤（Scalar Filtering）**，在入库时给 SOP 打上 `component`（如 MySQL、Redis、K8s）和 `alert_type` 标签；检索时先根据告警来源做标签过滤，缩小检索范围。
        - 结合 **BM25 全文检索（稀疏向量）+ 稠密向量检索**，通过 RRF（倒数排序融合）重排，兼顾“语义相似”和“错误码精准匹配”。
- **3. 按 SOP 结构切片（Structure-aware Chunking）：**
    - **问题：** 按固定字数（如 500 字）硬切 Markdown 文档，把“故障现象”和“排查命令”切到了两个不同的 Chunk 里，导致召回了现象却丢了排查步骤。
    - **解决措施：** 按运维 SOP 的 Markdown 标题层级（`# 告警名称` -> `## 触发原因` -> `## 排查步骤`）进行结构化切分。用“告警名称 + 故障现象”做向量索引，但在 Milvus 的 Payload 中存储**完整的 SOP 全文（父子文档模式）**，确保一旦命中，整套排查流程完整喂给模型。
### 三、 针对“Eino 规划死循环 / 推理步数过多 / 耗时高”的优化
[[#一、 拆解链路：分模块硬指标评测（最易落地、代码可量化）]]
在端到端回放评测中，常会遇到 **Plan-Execute-Replan 陷入死胡同**（例如某个监控指标查出来为空，模型就不停地换时间段反复查），或者串行调工具导致端到端耗时超过 30 秒。
- **1. 图编排层面的熔断与重复调用拦截（Eino Graph 状态控制）：**
    - **问题：** 模型在 Replan 阶段出现“鬼打墙”，用完全相同的参数反复调用同一个 MCP 工具。
    - **解决措施：** 在 Eino 的全局 `State` 中维护一个**工具调用签名哈希表（Call History Hash）**（以 `ToolName + 参数JSON的MD5` 为 Key）。在执行节点（Execute Node）前置拦截：如果发现当前请求与历史某次调用完全一致，直接拦截不发请求，强制注入一条系统提示：`"你已使用相同参数调用过该工具，请勿重复调用，尝试其他排查方向或直接基于现有信息给出结论"`；同时设置硬性 `MaxIterations = 5`，超限后强制路由到 `Summarize Node` 输出阶段性排查结论并转人工。
- **2. 基于 Go 协程的并行工具执行（Parallel Tool Execution）：**
    - **问题：** 排障初期通常需要同时看 CPU、内存、近期错误日志和最近一次发版记录。如果让 ReAct 一步步串行调 4 次工具，光网络 IO 和模型推理就要十几秒。
    - **解决措施：** 在 Plan 阶段引导模型一次性生成多个无依赖关系的子任务，在 Eino 的自定义执行节点中，利用 Go 的 `errgroup` 或 `sync.WaitGroup` **并发发起多个 MCP 请求**，将多源监控数据的采集耗时从“累加”变为“取决于最慢的那一个接口”，端到端耗时直接砍半。
- **3. 工具返回结果裁剪与摘要（Context 瘦身）：**
    - **问题：** 调一次日志接口返回了几百行堆栈，直接塞进 Context 导致 Token 暴增，后续 Replan 推理越来越慢，甚至撑爆上下文窗口。
    - **解决措施：** 在 Go 工具层做**返回数据截断与聚合**。比如日志查询接口，在代码层按错误堆栈做 Group By 聚合，只返回 Top-3 高频报错的样本及出现次数，单次 Tool Output 严格限制在 1000 字符以内。
### 四、 针对“实体幻觉（编造 Pod 名/指标数值）”的优化
- **解决措施：结构化输出 + 后置实体校验（Guardrails）**
    1. **强约束输出格式：** 要求最终排障报告必须输出结构化 JSON，包含 `conclusion`（结论）、`evidence_list`（证据列表，必须引用具体工具返回的原始字段）和 `action_suggestions`（建议操作）。
    2. **代码级防幻觉校验：** 在最终结果推送给飞书/钉钉群之前，用 Go 代码提取模型输出中的所有 IP、Pod 名称、容器 ID（可通过正则匹配），去当前会话的 **MCP 工具原始返回文本池**里做 `strings.Contains` 校验。如果发现模型输出了一个从未在工具返回结果中出现过的 Pod 名或 IP，立刻触发告警降级（标红提示“部分实体未经验证”或打回重新生成）。

### 五、 面试串讲金牌话术（如何把“评测”与“优化”连起来说）
当面试官问：**“通过你刚才说的评测，你发现了什么问题？怎么优化的？”** 你可以挑其中 **2 个最具体的点** 深入讲，显得极其真实：
> “在跑那几十个历史故障回放 Case 的时候，我确实抓出了两个非常影响落地的典型 Bad Case，并做了针对性重构：
> **第一个是工具调用的‘时间换算错误’和‘死循环’问题。**
> 最初评测时我发现，工具调用的参数合法率只有 80% 左右，深究下来全错在‘时间窗口’上——大模型做 Unix 时间戳换算经常算错。而且一旦某个日志接口查出来是空数据，Eino 的 Replan 就会换个差不多的时间反复查，导致推理步数直接干满 10 步超时。
> **我的优化方案是：** 第一，改了 MCP 工具的入参设计，把绝对时间戳改成了相对告警时间的 `lookback_minutes`（向前回溯分钟数），把时间加减的逻辑全部下沉到 Go 代码里算，参数合法率直接拉到了 99%；第二，在 Eino 的 State 里加了 `ToolName + 参数哈希` 的去重拦截，外加最多 5 步的熔断机制，彻底解决了死循环问题，平均排查耗时从 25 秒降到了 9 秒左右。
> **第二个是 Milvus 检索 SOP 时的‘噪声干扰’问题。**
> 评测 Top-3 召回率时初期只有 60% 多。我看了一下 Bad Case，是因为直接拿原始告警报文去 Embedding，里面全是随机的 Pod 后缀、IP 和长堆栈，把核心的报错语义给稀释了；另外有些特定错误码纯靠向量搜不准。

> **我的优化方案是：** 在查 Milvus 之前加了一层正则清洗，把 IP、时间戳、UUID 全干掉，只留服务名和核心异常指标；同时结合了 Milvus 的标量标签过滤（先按 MySQL、Redis 等组件过滤）和混合检索，改造完之后，SOP 的 Top-3 命中率稳定在了 90% 以上。”


# 多Agent架构 Why How
### 一、 为何拆分（Why）：单 Agent 在生产排障下的三个死穴

在运维排障场景下，搞一个无所不能的“单体大 Agent”上线必挂，主要有三个根本原因：

1. **上下文与工具膨胀（Context & Tool Pollution）：**
运维底层工具极多（Prometheus、ES、Kube-API、Trace、发布平台）。如果将 20+ 个工具的 JSON Schema 全塞进同一个 Prompt，模型的**注意力会严重稀释，导致高频选错工具**（比如查堆栈时调用了查指标的接口），并且多轮排障产生的几千行日志返回会撑爆上下文。
2. **认知目标冲突（Role Cognitive Divergence）：**
“宏观决策”与“微观执行”需要截然相反的提示词策略：
* **决策规划**需要模型具备大局观、发散思维与反思纠错能力，提示词偏重“根因推理与任务拆分”；
* **日志/指标分析**需要模型极度收敛、严谨，提示词偏重“高频错误聚类、时序拐点定位与零幻觉提取”。
堆在一个 Prompt 里会导致模型既做不好规划，也看不准细节。

3. **读写权限与生产安全硬边界：**
排障分析（只读）必须全自动跑以提高时效；但排障处置（重启 Pod、熔断、扩缩容等写操作）必须拦截鉴权、甚至引入人工审批（Human-in-the-loop）。拆分才能从架构层面进行**严格的 RBAC 权限隔离**。

---

### 二、 如何拆分（How）：主从分层架构（Hierarchical Pattern）

业内最成熟的运维 Agent 拆分方案是 **“1 个主控 Agent（大脑）+ 多个垂直领域 Worker Agent（专家四肢）”**：

```
                ┌───────────────────────────────────┐
                │   Coordinator / Lead Agent        │
                │   (全局规划、动态反思 Replan、总结报告)   │
                └─────────────────┬─────────────────┘
                                  │ 派发子任务 / 收集阶段结论
        ┌─────────────────────────┼─────────────────────────┐
        ▼                         ▼                         ▼
┌───────────────────┐   ┌───────────────────┐   ┌───────────────────┐
│   Metric Agent    │   │     Log Agent     │   │   Change Agent    │
│ (专注Prometheus指标)│   │  (专注ES/Loki日志)  │   │ (专注发版/配置变更) │
└─────────┬─────────┘   └─────────┬─────────┘   └─────────┬─────────┘
          │ MCP                   │ MCP                   │ MCP
      Prometheus               ES / Loki              Git / CI/CD

```

1. **主控规划智能体（Coordinator / Lead Agent）：**
* **不挂载底层物理工具**，只保留系统拓扑视图、历史 SOP（Milvus 召回）以及子 Agent 路由工具。
* 负责**将宏观告警拆解为具体排查任务**，并根据各 Worker 的反馈执行 **Replan**（决定继续深挖日志还是转向查看发版变更），最后输出根因结论。


2. **指标专职智能体（Metric Agent）：**
* **专属工具集：** 3~4 个监控接口（如 `query_cpu_trend`, `query_qps_metrics`, `query_db_pool`）。
* **核心能力：** 分析时序曲线拐点、判断指标波动与告警时间的同步性。


3. **日志链路专职智能体（Log & Trace Agent）：**
* **专属工具集：** 2~3 个日志与分布式链路接口（如 `query_error_stack`, `query_trace_timeline`）。
* **核心能力：** 从大量堆栈中提取核心异常类（如 `JedisConnectionTimeoutException`），追踪慢调用链路下游服务。


4. **变更专职智能体（Change Agent）：**
* **专属工具集：** 部署平台与 Git 接口。
* **核心能力：** 检索故障前 30 分钟内目标服务及其上游是否有新镜像发布、配置热更新或 SQL 脚本执行。



---

### 三、 多 Agent 之间如何协作（Collaboration & Communication）

在 Go + Eino 的工程实现中，多 Agent 协同不靠随意的“自然语言群聊”，而是靠“统一上下文状态机（Shared State）+ 结构化任务/结论协议”：

#### 1. 结构化任务派发（向下分发）

Coordinator 不直接跟子 Agent 聊自然语言，而是生成强契约的 JSON Task：

```json
{
  "task_id": "task_001",
  "assigned_agent": "LogAgent",
  "service_name": "order-service",
  "lookback_minutes": 15,
  "focus_error": "ConnectionRefused"
}

```

通过 Eino 的并行节点，可以同时将 `task_001` 派给 LogAgent，`task_002` 派给 MetricAgent。
#### 2. “结论与证据”摘要回传（向上收敛，避免上下文污染）
**子 Agent 严禁将底层工具查询到的几百行原始日志/监控明细返回给主控。**
子 Agent 在各自进程内利用微调 Prompt 或正则完成聚合，只回传**高密度排查结论（Claim + Evidence）**：

```json
{
  "agent": "LogAgent",
  "status": "ANOMALY_FOUND",
  "summary": "order-service 在 14:03-14:08 突发 342 次 Redis 连接超时",
  "evidence": "redis.clients.jedis.exceptions.JedisConnectionException: Could not get a resource from the pool",
  "suggest_next_step": "CHECK_REDIS_METRICS"
}

```

#### 3. 动态反思（Replan Loop）
Coordinator 汇总各子 Agent 的简报：
* 如果 LogAgent 报告发现了大量 Redis 连接打满，Coordinator 的 Replan 逻辑触发，动态生成新一轮排查任务：指派 **MetricAgent** 去查该 Redis 实例的内存和当前连接数。
* 当证据链形成闭环（如：发版变更引入了未关连接的慢查询 $\rightarrow$ Redis 连接耗尽 $\rightarrow$ 上游 order-service 接口报 500），Coordinator 终止循环，合成最终排障报告。
