在电力现货交易或者“广东中调”这种实时性要求极高的监控大屏场景下，这道题的满分回答框架应该是这样的：

---

### 第一部分：双写一致性（先更新 DB，还是先删缓存？）

“面对 24/96 点这种高频电力曲线数据，当底层采样点发生人工修正或重新计算时，我的策略是采用**标准的旁路缓存模式（Cache Aside）**，具体做法是：**先更新 MySQL 数据库，再删除 Redis 缓存（而不是更新缓存）。**”

#### 1. 为什么是“删除”缓存，而不是“更新”缓存？

- **并发安全**：如果两个线程并发更新同一个点位的数据，由于网络延迟，更新 Redis 的顺序可能会乱序，导致缓存里存了旧的脏数据。而“删除”操作是幂等的。
    
- **懒加载（Lazy Loading）**：某些曲线图可能一天只被看一次。如果每次底层数据微调我都去重新计算并更新缓存，会浪费大量 CPU 和内存。删掉它，等下次用户真正打开前端图表查询时再去查库重建，性价比最高。
    

#### 2. 为什么是“先更新 DB，后删缓存”？（而不是反过来）

- **推演灾难**：如果先删缓存，再更新 DB。在这中间极短的时间差里，如果前端刚好发来一个查询请求，它发现缓存空了，就会去读取 DB，此时 DB 还没更新完，它读到了旧数据，并把旧数据放回了 Redis。这就导致缓存被彻底污染了。
    
- **高阶兜底方案（面试加分项）**：虽然“先 DB 后缓存”在极端情况下也有极小概率不一致，但为了追求极致的可靠性（比如核心结算数据），我们会引入**异步补偿机制**。利用 **Canal** 监听 MySQL 的 Binlog，一旦发现该表数据有变动，Canal 会把变更消息发到 RabbitMQ，再由专门的消费者去可靠地执行 Redis 的删除操作，哪怕删失败了也有重试机制保证最终一致性。
    

---

### 第二部分：缓存击穿（如何保护脆弱的 DB？）
[[缓存篇#缓存击穿]]
“在核心监控图表场景中，如果某个核心点位的曲线数据缓存刚好过期，此时并发涌入了 1000 个查询请求，这就是典型的缓存击穿。如果不做防护，MySQL 的 IO 会瞬间飙升甚至宕机。我会提供两种维度的解决方案：”
#### 方案 A：强一致性场景 —— 分布式锁（互斥锁）
如果这个曲线数据涉及资金结算，绝不允许展示错误数据：
- **做法**：在代码里发现缓存查不到数据时，不立刻去查库。而是先用 Redis 的 `SETNX`（或 Redisson）抢一把分布式锁。
- **效果**：1000 个请求里，只有 1 个请求能抢到锁，它去缓慢地查询 MySQL 并重建 Redis 缓存。剩下的 999 个请求稍微休眠几十毫秒后重试。这样打到数据库的请求永远只有 1 个。
#### 方案 B：高可用场景 —— 逻辑过期（Logical Expiration）
电力监控大屏往往要求“绝对的响应速度”，图表哪怕展示了一秒钟前的旧数据，也比转圈圈卡死要强。
- **做法**：我们在 Redis 里存数据时，**不设置物理过期时间（TTL 设为永久）**，而是在 JSON 内部加一个 `expireTime` 字段。
- **效果**：当并发请求来临时，大家都从 Redis 拿到了数据。代码里判断 `expireTime` 发现时间已经过期了。此时，系统会**直接把旧数据返回给前端**保证图表秒开，同时在后台悄悄开启一个独立的线程去查 MySQL，查完后把新的带最新时间的 JSON 塞回 Redis。
# 2.RabbitMQ做工单告警的异步解藕
[[RabbitMQ]]
简历中体现你的技术栈包含了 Redis 和 RabbitMQ 。假设在你的智能 OnCall 系统或者电力后台系统中，我们使用 RabbitMQ 来做工单或告警的异步解耦。

- **我的问题：** 如果突发大规模的告警风暴，导致 RabbitMQ 消息积压严重，甚至打满了磁盘报警，你的应急处理方案是什么？另外，为了防止消息在流转过程中丢失，你通常会如何配置生产者、Broker端以及消费者的确认机制（ACK）？
**标准回答：**

> **处理告警风暴/消息积压报警：**
> 
> 1. **紧急扩容：** 临时增加消费者服务实例，或者调大消费者的并发度（提升 `prefetch_count`）。
>     
> 2. **降级与分流：** 如果是异常风暴，立刻在消费者端实施服务降级，直接返回 ACK 并将消息落入本地磁盘或紧急丢入 Redis/死信队列（DLX），先把 MQ 里的积压清空，防止把整个 Broker 拖死，后续再通过跑批脚本处理异常数据。
>     
> 3. **源头限流：** 在告警产生端（生产者）临时开启令牌桶或滑动窗口限流。
>     
> 
> **保障消息零丢失（全链路 ACK）：**
> 
> 4. **生产者侧：** 开启 `Publisher Confirms`（确保消息到达 Exchange）和 `Publisher Returns`（确保消息路由到 Queue）。
>     
> 5. **Broker侧：** 确保 Exchange、Queue 声明为持久化（durable），且消息本身设置持久化标志（`delivery_mode=2`）。如果是集群，使用仲裁队列（Quorum Queues）保证高可用。
>     
> 6. **消费者侧：** 关闭自动 ACK，改为**手动 ACK（`basicAck`）**。必须在业务逻辑（如数据库事务）完全成功提交后，才执行 ACK。同时，因为网络抖动可能导致重复消费，**必须配合 Redis 或数据库唯一索引做好幂等性控制**。


# 3.MyBatis批量降级：
## 🧐 1. 什么是 `saveOrUpdateBatch` 的正常逻辑？

当你想把 EasyExcel 解析出来的 1000 条数据写进数据库时，你调用了：

Java

```
// 默认批量大小是 1000
sw.saveOrUpdateBatch(entityList, 1000);
```

在**全都是全新数据、没有任何联合唯一索引冲突**的理想状态下，MyBatis-Plus 的底层逻辑是极其高效的：

1. 它通过 JDBC 的 `PreparedStatement.addBatch()`，把这 1000 条 `INSERT` 语句打包。
    
2. 一次性通过网络发送给 MySQL（只发生 **1 次**网络 I/O 往返）。
    
3. MySQL 内部高效地把这 1000 条数据批量写入 B+ 树的顺序页中。
    

这种状态，叫做“真正的批量插入”。

## 🌋 2. 什么是“批量降级机制”？（核心黑洞）

真正的灾难发生在这 1000 条数据里，**混入了哪怕 1 条已经在 MySQL 里存在的数据**（对于你这个项目，就是 `场景ID + 设备ID + 日期` 联合唯一索引发生了碰撞）。

这时候，MyBatis-Plus 的底层源码会发生极其痛苦的**三步倒退（降级）**：

### 🛑 第一步：乐观盲插，惨遭打脸

MyBatis-Plus 依然很乐观，它把 1000 条 `INSERT` 整体打包发给 MySQL 执行。 突然，MySQL 发现第 527 条数据的联合唯一索引已经存在了，于是立刻抛出一个大大的红字异常：**`DuplicateKeyException`（唯一键冲突）**。

### ↩️ 第二步：整个批次，被迫回滚

因为这是一个整体的批量操作，第 527 条报错了，MySQL 无法继续往下执行，**导致这整整一个批次（1000条）的批量写入事务在瞬间全部宣告失败、整体回滚**。

### 📉 第三步：彻底降级，单条磨叽（这就是降级！）

批量打包被搞砸了，但 MyBatis-Plus 作为一个成熟的框架，它不能直接给前端报错啊，它得想办法把剩下的 999 条存进去，把那 1 条重复的更新掉。

由于它**不知道这 1000 条里到底哪一条是重复的**，它只能选择最笨、最无奈的策略——**彻底撕掉批量的外衣，退化（降级）为最原始的单条 `for` 循环！**

它的底层源码在捕获异常后，会演变成类似下面的逻辑：

Java

```
// 批量失败后，底层被迫降级为单条遍历
for (T entity : entityList) {
    try {
        // 1. 一条一条地去试着 INSERT
        executeInsert(entity); 
    } catch (DuplicateKeyException e) {
        // 2. 如果这一条报错了，说明它就是那颗“老鼠屎”
        // 3. 那就再发一次跨网络请求，去单条执行 UPDATE
        executeUpdate(entity); 
    }
}
```

## 💸 3. 降级在开发环境中带来的“技术破产”

一旦触发了这个降级，你在本地 IDEA 控制台和耗时上，就会看到我们前面讨论的恐怖连锁反应：

- **跨网络 I/O 爆炸：** 原本 1 次网络交互就能解决的事情，降级后变成了：先去 `INSERT` 1000 次，遇到冲突的再去 `UPDATE`。**1 次网络往返瞬间暴涨到了上千次！** 你的网络耗时直接从几毫秒飙升到数秒（5万条就会冲破 10 秒）。
    
- **控制台面条日志刷屏：** 你的 IDEA 窗口开始疯狂滚动单条的 `UPDATE` SQL 日志，滚屏产生残影，甚至由于本地控制台高频 I/O 导致整个 IDEA 界面假死卡顿。
    
- **Entity 对象生命周期拉长：** 这 1000 个 Java 实体对象原本发完就该被销毁（随 Minor GC 回收），现在因为卡在单条慢速的网络循环里，它们迟迟无法被释放，最终熬过了年轻代，**被迫晋升到老年代，从而引发剧烈的 Full GC（也就是你看到的内存毛刺大波浪）**。


# 4.MySQL索引

## 1. 什么情况下MySQL索引会失效？

常见索引失效场景有：

### （1）违反最左前缀原则

例如联合索引：

```sql
index(a,b,c)
```

查询：

```sql
where b=1 and c=2
```

由于联合索引在B+树中是按照：

```text
A
↓
A相同按B排序
↓
B相同按C排序
```

进行存储的。

缺少最左列A，无法确定从哪里开始查找，因此无法利用联合索引。

---

### （2）索引列参与计算或函数

例如：

```sql
where age+1=20
```

或者：

```sql
where year(create_time)=2025
```

B+树存储的是原始值。

计算后值并没有建立索引，因此无法利用索引快速定位。

---

### （3）隐式类型转换

例如：

```sql
phone varchar(11)

where phone = 13800138000
```

MySQL可能会将索引列转换：

```sql
cast(phone as signed)
```

相当于对索引列进行了函数操作。

导致索引失效。

---

### （4）前导模糊查询

```sql
where name like '%张'
```

无法确定索引扫描起点。

索引失效。

但：

```sql
where name like '张%'
```

可以利用索引。

---

### （5）范围查询后面的列失效

例如：

```sql
index(a,b,c)

where a=1
and b>10
and c=3
```

A和B能利用索引。

C无法继续利用索引定位。

---

## 2. 为什么联合索引遵循最左前缀原则？

联合索引：

```sql
index(a,b,c)
```

B+树中的排序规则是：

```text
先按A排序

A相同按B排序

B相同按C排序
```

例如：

```text
(1,1,1)
(1,2,1)
(1,3,1)

(2,1,1)
(2,2,1)
(2,3,1)
```

如果查询：

```sql
where b=2
```

由于不知道A是多少。

无法确定从哪一段开始扫描。

所以无法利用联合索引进行定位。

这就是最左前缀原则的本质。

---

## 3. index(a,b,c) 时 A、AB、ABC、AC、BC 哪些走索引？

| 查询条件 | 是否使用索引  |
| ---- | ------- |
| A    | √       |
| AB   | √       |
| ABC  | √       |
| AC   | √（部分使用） |
| BC   | ×       |

---

## A

```sql
where a=1
```

A是第一排序键。

直接利用索引定位。

---

## AB

```sql
where a=1 and b=2
```

完全符合联合索引顺序。

直接利用索引查找。

---

## ABC

```sql
where a=1 and b=2 and c=3
```

完全命中联合索引。

---

## AC

```sql
where a=1 and c=3
```

很多同学误认为失效。

实际上：

```text
A能利用索引定位

C无法利用索引继续缩小扫描范围
```

属于：

```text
部分命中索引
```

---

## BC

```sql
where b=2 and c=3
```

缺少最左列A。

无法利用联合索引定位。

真正失效。

---

## 4. 范围查询为什么会导致后面的索引失效？

联合索引：

```sql
index(a,b,c)
```

查询：

```sql
where a=1
and b>10
and c=3
```

---

执行过程：

首先：

```sql
a=1
```

定位到对应范围。

然后：

```sql

```

定位到范围起点。

但：

```text

```

对应的是一段连续区间。

例如：

```text
11
12
13
14
15
...
```

此时已经无法继续利用：

```sql
c=3
```

进行精确定位。

因此：

|字段|是否利用索引|
|---|---|
|A|√|
|B|√|
|C|×|

面试中常说：

```text
范围查询会导致联合索引截断。
```


答案：


由优化器决定。

如果：

```text

```

```text

```

即全表扫描。

面试官您好，针对 MySQL（InnoDB）的死锁问题，我结合底层锁机制、常见死锁成因、排查流程以及生产解决方案，分三个层面来回答：

  
# 5.Mysql死锁&解决方案
### 一、 常见死锁核心成因（结合具体场景）

在 InnoDB 引擎中，死锁的本质是**两个或多个事务同时持有对方所需的排他资源，并在等待队列中形成了闭环等待**。除了单行或索引交叉冲突外，生产环境中最常见的原因有以下 4 类：
#### 1. 业务并发操作同一批数据，但加锁顺序不一致（最基础、最高发）

- **成因**：业务代码在多个事务中同时操作资源 A 和 B，但由于入参未做有序化处理，导致并发时发生锁资源倒置。
- **表现**：
    - 事务 1 先更新 `id = 1`，再更新 `id = 2`；
    - 事务 2 先更新 `id = 2`，再更新 `id = 1`；
    - 并发交替执行时，事务 1 持有 1 等待 2，事务 2 持有 2 等待 1，形成死锁闭环。
#### 2. Gap Lock（间隙锁）兼容性与 Insert Intention Lock（插入意向锁）的冲突

- **成因**：在默认的 `RR` 隔离级别下，**间隙锁与间隙锁之间是互相兼容的**，两个事务可以同时对同一段空隙加 Gap 锁。但**插入意向锁与间隙锁互斥**。
- **表现**：
    - 假设表中只有 `id = 10` 和 `id = 20`，区间 `(10, 20)` 是空闲的。
    - 事务 1 执行 `DELETE FROM t WHERE id = 15`（记录不存在），在 `(10, 20)` 上加上了 Gap 锁；
    - 事务 2 执行 `DELETE FROM t WHERE id = 18`（记录不存在），同样在 `(10, 20)` 上成功获得了 Gap 锁（两者并存）；
    - 事务 1 紧接着尝试 `INSERT INTO t(id) VALUES(16)`，需要申请该区间的插入意向锁，被事务 2 的 Gap 锁阻塞；
    - 事务 2 也尝试 `INSERT INTO t(id) VALUES(17)`，同样被事务 1 的 Gap 锁阻塞。双方互等，触发死锁。
#### 3. 索引失效或更新条件未命中索引，导致行锁退化为全表范围锁

- **成因**：当执行 `UPDATE` 或 `DELETE` 语句时，如果 `WHERE` 条件未命中有效索引（如隐式类型转换、模糊匹配、无对应索引），InnoDB 会退化为全表扫描。
- **表现**：
    - 在扫描过程中，InnoDB 会对遍历到的聚簇索引每一行记录加上行锁（在 RR 级别下还会加上全部间隙锁）。
    - 哪怕两个并发更新语句原本操作的是完全不同的两行业务数据，由于整表扫描和逐行加锁的先后交错，也极易在扫描中途与对方发生锁等待冲突，从而引发死锁。

#### 4. 批量操作（Batch Insert / Update）中的行锁交替冲突

- **成因**：批量插入、更新或删除时，SQL 语句对多行记录的加锁并不是一次性原子完成的，而是在存储引擎内部**逐行扫描并逐行加锁**。
- **表现**：
    - 事务 1 批量操作数据集 `{Row A, Row B}`，先给 A 加锁，准备给 B 加锁；
    - 事务 2 此时批量操作同一批记录但顺序相反 `{Row B, Row A}`，先拿到了 B 的锁；
    - 双方在逐行申请下一把锁时发生碰撞，形成循环等待。
### 二、 线上死锁的排查思路
当线上发生死锁时，通常遵循以下标准排查步骤：
1. **查看最近一次死锁现场**：
    - 执行 `SHOW ENGINE INNODB STATUS\G`，直接定位到 `LATEST DETECTED DEADLOCK` 模块。
    - 重点看两点：
        - **TRANSACTION 1 和 TRANSACTION 2**：它们当前分别持有什么锁（如 `lock mode S/X waiting`、`rec but not gap`、`locks gap before rec`），等待哪把锁。
        - **冲突的 SQL**：确定是哪两条语句在哪个索引（`index PRIMARY` 还是辅助索引）上发生争抢。
2. **开启全局死锁持久化日志**：
    - 因为 `SHOW ENGINE INNODB STATUS` 只能看到最后一次死锁，如果死锁频繁，前面的记录会被覆盖。
    - 在生产环境设置参数：`SET GLOBAL innodb_print_all_deadlocks = ON;`，让引擎将每次死锁的完整上下文记录到 MySQL 的 `error.log` 中，方便追踪完整频次和趋势。
3. **结合 APM 与应用层链路追踪**：
    - 数据库日志往往只能打印出引发死锁的**单条 SQL**，而无法看到整段事务的前置 SQL。需要根据时间戳、连接线程 ID（Thread ID），在应用层（如 SkyWalking、Sentry、业务日志）还原出完整的事务上下文代码。

### 三、 生产环境防范与规避策略

在系统架构与编码规范层面，主要通过以下 4 个维度来解决：
1. **业务层规范加锁顺序（预防顺序死锁）**：
    - 凡是涉及同时更新或锁定多个同类实体、批量插入的业务逻辑，在应用层处理前，必须统一按固定规则（如主键 ID 升序排序）进行排序，保证所有线程对资源的访问路径一致。
2. **合理降级隔离级别（消除间隙锁死锁）**：
    - 如果业务允许，将隔离级别从默认的 `REPEATABLE READ (RR)` 调整为 `READ COMMITTED (RC)`，同时将 `binlog_format` 设置为 `ROW`。
    - 在 RC 级别下，除了唯一性约束检查等少数瞬时阶段外，大部分 Gap Lock 和 Next-Key Lock 会被关闭，只保留记录锁，能从根源上消除约 80% 由间隙锁引起的死锁。
3. **优化事务粒度，确保快进快出**：
    - 控制事务的大小，避免在事务内部包含耗时计算、外部 RPC 接口调用、大文件读写等非数据库操作，大幅缩短排他锁的持有时间。
4. **严格保障索引有效性**：
    - 确保高频更新、删除语句的 `WHERE` 条件均命中覆盖度高的高效索引，杜绝全表扫描导致的无差别锁蔓延；对慢 SQL 开启报警并定期 Review 执行计划。
5. **重试机制兜底**：
    - 死锁是高并发下不可绝对规避的概率性问题，InnoDB 默认会回滚代价较小的事务（报 MySQL 错误码 1213）。在应用层（如 Spring 的 `@Retryable`）应配置对死锁异常的短暂退避自动重试机制，提升系统整体可用性。
