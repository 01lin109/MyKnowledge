# 监控探针讲解

## Q1：介绍 HMP 监控平台以及监控探针 SDK 在其中的作用

### 面试题

你在简历里写到：

> “负责公司内部 HMP 监控平台 Java 端监控探针 SDK 开发，参与 HTTP 请求异常、数据库连接池、SQL、JVM 等应用运行指标的采集上报与集中处理链路优化。”

**请你整体介绍一下这个 HMP 监控平台，以及你负责的监控探针 SDK 在整个监控链路中处于什么位置？**
### 标准回答

我们这个 HMP 监控平台主要用于**集中采集、展示和分析集团各业务系统的运行状态**，一方面方便运维人员快速响应各种 OnCall 场景，另一方面也可以让业务系统的运行状态更加直观。
整个监控平台主要包括**运行状态数据的采集与上报、监控数据的实时展示以及告警提醒**等模块。
我参与开发的监控探针 SDK，主要处于整个监控链路中的**数据采集、处理和上报环节**。它主要为集团各个业务系统提供一套低侵入的运行状态监控方案。

SDK 会采集包括 **HTTP 请求异常、SQL 异常和慢 SQL、数据库连接池状态以及 JVM 运行指标**等数据，对采集到的数据进行一定的处理之后，再统一上报到 HMP 平台，最终由平台进行集中展示和告警。

所以从整体链路来看，可以概括为：

**业务系统 → 监控探针 SDK → 数据采集与处理 → 数据上报 → HMP 平台 → 展示与告警**

其中 SDK 的核心价值就是**尽量不修改业务系统原有代码，通过框架层面的拦截机制和配置完成监控能力的接入**。

## Q2：监控 SDK 如何低侵入地完成数据采集？

### 面试题

你刚才提到 SDK 主要负责运行状态数据的采集、处理和上报。

**那你具体讲一下，这个 SDK 是怎么做到低侵入地采集 HTTP 请求、SQL、数据库连接池以及 JVM 这些运行数据的？分别采用什么方式进行采集？**

### 标准回答

我们在数据采集上主要分为两类：**事件驱动采集和定时采集**。

对于 HTTP 请求异常、SQL 异常以及慢 SQL 这类具有明确触发条件的数据，我们采用**事件驱动的方式**进行采集。

其中 SQL 相关监控主要是在 **MyBatis 层通过 Interceptor 进行拦截**。业务系统正常执行 SQL 时，SDK 可以在 SQL 执行过程中获取相关信息，并根据配置规则判断是否属于慢 SQL 或异常 SQL。

对于需要上报的异常数据，会进一步进行数据处理，比如 **SQL 脱敏、异常信息整理、窗口聚合以及去重**等，之后通过公司内部 ESB，以异步方式上报到 HMP 平台。

对于数据库连接池和 JVM 这类运行状态指标，它们不需要等待特定业务事件触发，因此采用**定时采集**的方式。SDK 按照配置的时间间隔主动获取连接池状态、JVM 运行指标等数据，经过处理后统一进行上报。

整个 SDK 的设计目标之一就是**低侵入**。业务系统接入之后基本不需要修改原有业务代码，主要通过 SDK 提供的拦截机制和配置完成监控能力的接入。

例如可以根据生产环境的实际需求配置需要监控的异常类型、慢 SQL 时间阈值以及定时采集的时间间隔，从而实现对业务系统运行状态的监控。

整体链路可以概括为：

**业务系统 → SDK 数据采集 → 数据处理 → ESB 异步上报 → HMP 平台展示与告警**

### 关键技术点

#### 1. SQL 如何采集？

通过 **MyBatis Interceptor** 在 MyBatis 层进行拦截。

核心思路可以理解为：

**SQL 执行前记录时间 → 执行 SQL → 获取执行耗时及相关信息 → 根据规则判断 → 进入后续处理流程**

例如慢 SQL 可以根据配置的时间阈值进行判断：

**实际执行耗时 > 配置阈值 → 判定为慢 SQL → 进入异常数据处理流程**

#### 2. 为什么能够低侵入？

因为监控逻辑并不是要求业务开发人员在每个业务方法中主动增加监控代码，而是通过 SDK 在业务代码外围利用相应的框架扩展机制完成数据采集。

业务系统主要通过**引入 SDK + 配置监控参数**完成接入。

#### 3. 两类采集方式

|类型|采集对象|触发方式|
|---|---|---|
|事件驱动采集|HTTP 异常、SQL 异常、慢 SQL|特定事件发生时触发|
|定时采集|JVM、数据库连接池|按配置周期主动采集|

### 本题容易出现的追问

**追问 1：为什么说是“事件驱动采集 + 定时采集”，而不是“一拉一推”？**

更严谨的说法是按照**采集触发机制**划分为事件驱动和定时采集。

“一拉一推”容易把“采集方式”和“上报方式”两个不同维度混在一起。

**追问 2：MyBatis Interceptor 是怎么工作的？**

需要进一步解释 MyBatis 的拦截机制，以及具体拦截的位置、如何获取 SQL、如何获取执行耗时。

**追问 3：慢 SQL 怎么判断？**

核心逻辑是：

**记录 SQL 执行前时间 → SQL 执行 → 计算执行耗时 → 与配置的慢 SQL 阈值比较 → 超过阈值则进行慢 SQL 处理。**

**追问 4：SDK 为什么不需要修改业务代码？**

需要从 SDK 接入方式以及 MyBatis 等框架提供的扩展/拦截机制解释，而不是简单回答“因为用了 SDK”。

**追问 5：SQL 异常数据后续怎么处理？**

可以进一步展开：

**MyBatis 拦截 → 获取 SQL/异常信息 → SQL 脱敏 → 异常信息整理 → 窗口聚合/去重 → ESB 异步上报 → HMP**

## Q3 这个模块如何接入的系统（多益网络）（9-15）

**背景一句话**：监控探针设计为非侵入式可移植模块，靠 Spring Boot 自动装配接入，目标是"复制目录 + 配置文件即可复用，零改业务代码、零改启动类"。
  

**接入机制（三层）**：

1. **加载入口**：`META-INF/spring.factories` 注册 `EnableAutoConfiguration=MonitorAutoConfiguration`；配置类上 `@ConditionalOnProperty(hmp.monitor.enabled=true)` + `@EnableScheduling`——Apollo 开关一关整个探针 Bean 都不创建，零开销。

2. **装配方式**：不用 `@ComponentScan`，全部显式 `@Bean` 声明（避免 Bean 创建顺序问题），按依赖分 5 层：Properties → 推送适配器（`@ConditionalOnMissingBean` 允许业务覆盖）→ 采集器 → ReportService → Scheduler（`@Scheduled` 三个定时任务：系统+JVM 60s / 数据源 60s / 延时任务 120s，initial-delay 120s 等启动完再采）。

3. **SQL 监控特殊接入**：`SqlMonitorInterceptor`（MyBatis `@Intercepts` 挂 Executor 的 update/query）**不走常规 plugins 配置**，单独放 `SqlMonitorConfig`（避免与 MybatisPlusConfiguration 循环依赖），用 **ApplicationRunner 在应用完全启动后**遍历所有 `SqlSessionFactory` 逐个 `addInterceptor`，带去重检查；`@Autowired(required=false)` 可选注入——监控关闭时 Bean 不存在也不报错。

**上报通道**：三条数据源（定时快照、SQL 拦截、GlobalExceptionHandler 错误日志）汇到 `pushToHmp()`，推送策略按优先级三选一：**适配器实现 > 反射调用配置的 Bean > 跳过**。TDP 默认实现 `TdpHmpDataPushAdapter` 走已有 `EsbReqClient`（Feign）→ ESB 网关 → HMP 平台，关键设计：异步单线程 + 1000 有界队列 + DiscardOldestPolicy（宁可丢数据不 OOM 不阻塞业务）、异常全部吞掉不上抛。

**其他系统接入（必做 3 步）**：① 复制 monitor/ 目录 + spring.factories（无需改包名）；② Apollo 配 `hmp.monitor.enabled=true` + `system-code`（HMP 注册的系统唯一标识）；③ 确认 ESB 客户端在位（TDP 生态默认有 EsbReqClient；不在生态内则实现 HmpDataPushAdapter 接口或配 esb-client-bean-name 反射调用）。

  

**按需 3 项**：SQL 监控需额外复制 `SqlMonitorConfig`（最易漏）；错误日志需在已有 GlobalExceptionHandler 里调 `pushErrorLog()`（探针不带独立拦截器）；延时任务需 `task-enabled=true` + 实现 `TaskDataSource` SPI。

  

**面试金句**：整套设计做到三点——零侵入（不改业务代码不改启动类）、可移植（复制目录+配置即复用）、可降级（任何环节失败只影响监控自身，业务无感）。
# SQL脱敏状态机
  
## Q3：导致StackOverFlowError的正则是啥样的&在 Java 默认的 `java.util.regex` 实现机制下，正则回溯为什么会导致线程栈溢出而不是仅仅表现为 CPU 100% 或耗时过长的超时？
  [[#Q5 爆栈如何排查]]

**原正则（还原）**：`replaceAll("'(?:[^']|'')*'", "'?'")` 等三个 replaceAll（字面量/单行注释/多行注释）。  

你之前那个正则类似：

```regex
(?:[^']|'')*'
```

它的问题不在于“正则本身很慢”，而在于 **Java 正则引擎采用回溯式匹配**。
### 1. 正常情况下
假设 SQL：
```sql
WHERE name = 'zhangsan'
```
正则从左往右匹配：
```text
'
 ↓
z
h
a
n
g
s
a
n
'
 ↓
匹配成功
```
### 2. 遇到复杂/异常长的 SQL
这个正则里的：

```regex
(?:[^']|'')*
```

意思大概是：

> 不断匹配“非单引号字符”或者“两个单引号”。
问题在于 `*` 是**重复匹配**，而内部又存在多个可能的匹配路径。
当输入非常长，而且**最后无法成功匹配结束条件**时，回溯引擎可能不断尝试：

```text
尝试路径 A
  ↓
失败
  ↓
回退
  ↓
尝试路径 B
  ↓
失败
  ↓
继续回退
  ↓
重新组合之前匹配的内容
  ↓
……
```
于是匹配过程可能产生非常深的调用栈。
### 3. 最终为什么是 StackOverflowError？
Java 正则引擎内部的匹配过程会使用递归式的 `match()` 调用来推进某些模式。
于是可能变成：

```text
Matcher.match()
 ↓
match()
 ↓
match()
 ↓
match()
 ↓
match()
 ↓
……
```

SQL 又特别长，例如生产环境遇到几十 KB、几百 KB 甚至更复杂的 SQL，回溯深度不断增加，最终：

```text
调用栈耗尽
     ↓
StackOverflowError
```

所以它不是：

> **SQL 太长 → 一定 StackOverflowError**

而是：

> **复杂正则 + 特定输入导致大量回溯 → 匹配调用栈不断增长 → 最终 StackOverflowError。**

### 面试标准回答

> 我们之前 SQL 脱敏使用了比较复杂的正则，其中存在重复匹配和多种匹配路径。Java 的正则引擎是基于回溯的，当遇到特别长或者不满足预期结构的 SQL 时，会不断尝试和回退，导致匹配路径和调用栈快速增长。由于 Java 正则内部部分匹配过程使用递归调用，最终可能耗尽线程栈，抛出 `StackOverflowError`。所以后来我们改成单遍 FSM，通过线性扫描避免回溯，保证最坏情况下也是 O(n)。

**你要特别记住一句：**

> **真正危险的不是“正则”，而是复杂正则在回溯引擎下可能产生不可控的回溯深度。**

java 原生 `java.util.regex` 导致 `StackOverflowError` 的根本原因在于：**其内部采用了递归下降的 NFA 匹配引擎，回溯状态并非维护在堆内存的数据结构中，而是直接依赖 JVM 线程调用栈（Call Stack）来保存。**

核心逻辑其实只有一句话：**Java 自带正则回溯不是用堆内存存状态，而是靠底层的「方法递归」，直接压在 JVM 线程栈上。**

面试时直接按这三个点口语化作答即可：

- **机制是方法递归**：Java 正则引擎内部把规则拆成了节点链表，贪婪匹配下一个字符时，本质上是一直在递归调用内部的 `match()` 方法。
    
- **输入把线程栈打穿**：JVM 线程栈默认只有 1MB（`-Xss`），最多容纳几千层方法调用。探针抓到的生产 SQL 经常包含超长的文本或大批量字段，贪婪匹配一路递归探测到底，调用链深度迅速突破上限，还没来得及大量回溯，就已经触发了 `StackOverflowError`。
    
- **与 CPU 100% 的区别**：CPU 打满是因为**回溯分支呈指数级爆炸**，在反复试错狂跑；而栈溢出纯粹是因为**单条匹配调用链过深**，算力还没来得及消耗，线程栈就已经先撑爆崩溃了。
## Q4：重写的单遍状态机（FSM）划分了哪些核心状态？如何处理转义字符、注释及敏感参数边界？  
  
### 第一层：先做设计定调（展示架构与选型考虑）

> “在 Java 探针（Agent）这种对性能、内存开销极度敏感的场景下，我们没有引入像 ANTLR 或 Druid 完整的 AST 语法树解析，因为语法树不仅有额外的对象分配，还会增加探针包体积。
> 
> 我们设计的是一个**轻量级的单遍流式状态机（Scanner）**，核心思想是通过单指针单向推进，指针永不回退，确保最坏时间复杂度严格为 $O(n)$，空间复杂度为 $O(n)$（直接复用单次分配的 `StringBuilder` 缓冲）。”
### 第二层：拆解具体状态与转移闭环（正面回答状态划分）

> “具体实现上，我们抽象出了 **4 种核心状态**，由输入流中的特定触发字符驱动状态转移：
> 1. **`NORMAL`（普通 SQL 态）**：默认初始状态，遇到普通关键字、字段名原样追加到缓冲区。
> 2. **`IN_LINE_COMMENT`（单行注释态）**：当遇到连续的 `--` 字符时，状态从 `NORMAL` 转移进来。此状态下跳过字符，直到遇到 `\n` 或 `\r` 换行符时，状态重置回 `NORMAL`。
> 3. **`IN_BLOCK_COMMENT`（多行注释态）**：当遇到 `/*` 时切入此状态。同样跳过注释内容，直到匹配到闭合的 `*/` 时切回 `NORMAL`。
> 4. **`IN_STRING`（字符串字面量态）**：当遇到单引号 `'` 时切入。在进入该状态瞬间先向输出写入一个占位符 `?`，后续字符均被吞掉，直到字符串安全闭合后切回 `NORMAL`。”
### 第三层：边界防坑细节（高分点：单/双引号、反斜杠、IN列表）

> “为了做到‘不漏脱、不误脱且安全闭环’，我们在状态转移中重点解决了几个生产边界：
> - **单引号与反斜杠转义（`''` 与 `\'`）**：
>     - 在 `IN_STRING` 状态下，如果遇到反斜杠 `\`，说明后一个字符被转义，直接指针 `+2` 跳过转义对，避免 `\'` 导致字符串提前闭合；
>     - 如果遇到单引号 `'`，我们会向前预读（Lookahead）一个字符：如果是连续单引号 `''`（SQL92 转义），指针跳过这对单引号，**继续停留在 `IN_STRING` 状态**；如果是孤立单引号，才真正闭合字符串并转移回 `NORMAL`。
> - **未闭合的异常 SQL 闭环**：
>     - 如果业务 SQL 语法本身错误或被截断（比如单引号没闭合扫描到了文本末尾 `len`），循环自然终止退出，直接进入外层 `try-catch` 兜底降级，保证探针自身绝不抛出未捕获异常影响宿主业务。
> - **`IN (...)` 批量参数泛化与空格压缩**：
>     - 针对 `IN (...)` 批量参数，我们在 `NORMAL` 状态下遇到连续的 `?, ?, ?` 或者数值列表时，会做一个轻量级的折叠合并，统一折叠为 `IN (?)`，既实现脱敏，又避免因参数个数不同导致后续监控平台生成无数零散模板；
>     - 另外，我们在扫描遍历字符的同时，通过一个 `isPrevSpace` 标志位同步完成了多余连续空格的合并，避免在扫描完成后再额外调用正则 `replaceAll`，彻底做到真正的单遍线性扫描。”


### 💡 面试官视角的点评与复习建议

- 这样回答不仅严丝合缝地对应了你实际写出的 `while + if` 代码结构，而且把代码里的每个 `if` 分支升华成了**有限状态机状态的切入和切出**。
- 特别是提到“反斜杠转义预判”**和**“把未闭合 SQL 视作降级安全退出”，会给面试官一种“这个人不仅会写逻辑，而且上线前充分考虑过线上各种脏数据和边界异常”的靠谱感。
## Q5 爆栈原因
[[场景题目#2.OOM，CPU 100% 爆栈等问题如何排查解决 生产排查]]
### 核心原因总结：DB 动态规则配置（`WHERE ${rule}`）导致脱敏爆栈

#### 1. 业务根源：将“人工裸 SQL”直接当成动态配置

- **配置方式**：管理员在后台规则表（`tb_elevation_rule.rule`）中，以纯文本形式人工维护带引号的 SQL 条件片段（如 `m.merits_ext >= '90' AND u.job_rank = 'P6'`）。
    
- **隐患载体**：MyBatis 在 XML 中使用了 **`${rule}`** 原文替换通道。由于没有经过编译期语法检查，这段人工填写的 SQL 会被**原封不动地内联拼入**最终的 `BoundSql` 中。
    

#### 2. 事故触发：单引号未闭合或中英文混用

- 管理员录入时极易手滑漏打单引号（如写成 `m.merits_ext >= '90 AND ...`），或者误用了中文引号 `’`。
    
- 带有**残缺引号**的畸形 SQL 片段通过 `${}` 缝合进整条长 SQL，直接流入下层的脱敏拦截器（`Interceptor`）。
    

#### 3. 致命机制：脱敏正则陷入“终极大回溯”与递归压栈

- **贪婪吞噬**：脱敏工具原本使用匹配字符串字面量的正则表达式（如 `'(?:[^']|'')*'`），假定所有单引号都会正常闭合。面对漏闭合的单引号，正则引擎误认为从 `'90` 开始直到整条 SQL 结尾的所有字符（包含后续大量 JOIN、WHERE 条件），**全都是单引号内部的内容**。
    
- **匹配失败触发回溯**：吞噬到 SQL 末尾仍未找到闭合标记，Java 的 NFA 正则引擎判定当前分支匹配失败，启动全局深度回溯。
    
- **JVM 栈帧击穿**：Java 正则引擎底层的量词与回溯是通过**递归方法调用**（如 `Pattern$GroupCurly.match`）实现的。回溯整条 SQL 剩余的上千个字符需要压入数千到上万层方法栈帧，瞬间击穿 JVM 默认的线程栈上限（`-Xss1m`），直接抛出 **`StackOverflowError`**。
    

#### 4. 架构定性与解决启示

- **反模式定性**：这是典型的“不可信外部输入破坏了系统语法假设”——脱敏组件默认传入的是合法 SQL，而 DB 人工配置打破了闭合完整性。
    
- **重构必要性**：调大 `-Xss` 治标不治本；**改用有限状态机（FSM）单趟线性扫描**后，指针只向前走，遇到未闭合引号也仅当成普通文本消费至结尾，调用栈深度恒定为 **$O(1)$**，彻底免疫残缺文本带来的爆栈风险。

### 1️⃣ 先亮设计原则：Key = 结构化特征，不是文本

> 动态变量（时间戳、traceId、用户ID）全都只进 `errorSummary` / `errorStack` 这些**描述性字段**，它们不参与 Key 计算。Key 只由两个语义特征拼成：**“什么异常”（errorClass）+ “在哪里发生”（errorMethod）**，格式 `errorClass|errorMethod`。同样的 NPE，消息里带多少个动态 ID 都不影响命中；只有“异常类型或出错位置变了”才算新问题。
### 2️⃣ 分路径讲特征提取（体现深度）

**SQL 异常/慢SQL 路径**（MyBatis 拦截器 → SqlMonitorCollector）：

- `errorClass`：不拿 MyBatis 抛上来的表面异常，先**解包**——穿透 `InvocationTargetException` / `PersistenceException` / `MyBatisSystemException` 这些无信息量的包装层，拿到真实根因（如 `SQLSyntaxErrorException`）。包装类异常通常消息为空或是套话，不解包会导致“所有 SQL 错误都被归成一类”或“永远命中不了”
- `errorMethod`：Mapper 的短 ID，如 `OrderMapper.updateStatus`。SQL 文本虽然做了脱敏，但**也不参与 Key**（同样的 SQL 不同参数本身就是同一个 statement）

**HTTP 系统异常路径**（GlobalExceptionHandler 兜底）：

- `errorClass`：`findRootCause()` 沿 cause 链走到最内层拿根因类
- `errorMethod`：**关键设计——取的是堆栈里第一个“业务代码帧”** `pkg.Class.method(File.java:142)`，提取时显式跳过 JDK 反射、Spring AOP/CGLIB、MyBatis、监控组件自己的帧

这一步直接为第 3 问做了铺垫。

### 3️⃣ 回答“误伤”问题（这是本题的得分点）

> 我们防误伤的核心手段就是**用“业务调用点”而不是“异常抛出点”做定位特征**。

- `DbUtil` 这种工具类抛异常时，堆栈里 `DbUtil.query()` 只是中间帧；我们的 `extractCallerLocation` 会**跳过框架/工具类所在的下层帧，取第一个业务帧**。所以 A 业务和 B 业务分别调 `DbUtil` 出了同类异常，它们的 `errorMethod` 是各自的 `AService.xxx(AService.java:50)` 和 `BService.xxx(...)`——**Key 天然不同，不会被合并**。这正是当初不简单取 `e.getStackTrace()[0]` 的原因：第一帧往往就是那个“公共底层类”，取它必然误伤
- SQL 路径同理：特征是 Mapper 方法维度（`UserMapper.selectById`），不同 Mapper 之间不会互相合并

然后**主动承认取舍**（面试加分项）：

- 粒度选的是“异常类 + 位置”，不是“异常类 + 位置 + 消息指纹”。代价是：HTTP 路径同一方法同一行抛出的同类异常，不管业务原因是否相同都会合并；SQL 路径两个不同业务流调同一个 Mapper 方法出同类错误也会合并。这是有意的权衡——监控告警关心的是“哪里出了什么问题”，30 秒窗口内合并成 `occurCount=N` 反而更可读；如果想再细分，可以把 `requestUrl` 纳入 Key，但要评估窗口数量膨胀（我们有 `errorDedupMaxPending=200` 的缓存上限兜底，超限降级为实时推送，不会 OOM）
- 兜底逻辑：位置信息缺失时 Key 退化为仅 `errorClass`（粗但不漏）；两个都没有就直接跳过去重走实时推送

### 4️⃣ 收尾：Key 之后的故事（一句话带过）

> Key 命中后不存第二条 DTO，只对窗口 `recordRepeat()`（occurCount++、刷新 lastOccurTime），到期 flush 时用首条 DTO 的完整内容 + 聚合计数合成一条上报——这就是“首报详情 + N 次计数”的 N→1 模型。

## Q7**并发、边界与内存安全（高并发健壮性）**：
在 30s 窗口临界点，当延迟调度线程触发“读取并上报该异常”的同时，恰好又有新的相同异常打进来，你们是如何设计状态流转以保证既不丢数据、又不会造成内存泄漏（Map 元素无限堆积）的？

**1. 30 秒窗口临界点并发：如何保证不丢数据、不死锁、不脏写？**
- **三阶段归属清晰**：
    - **旧窗口活跃态（Active）**：新异常命中，在窗口对象锁内安全执行 `occurCount++`，等 30 秒到期统一上报。
    - **正在刷出态（Flushing）**：在极窄时间窗口内，若累加恰好发生在快照之后、移除之前，计数会少算 1 次，但**问题事实和完整首报内容已安全发出**，不影响告警；若累加发生在快照前，则直接计入本次上报。
    - **已移除态（Removed）**：并发写入直接 miss，通过 `putIfAbsent` 原子创建新窗口，移入下一个 30 秒周期，数据绝不丢失。
- **并发控制与安全**：
    - **无死锁**：锁粒度仅限于**单个窗口实例**，临界区只有纳秒级内存操作，**网络推送 I/O 严格置于锁外**，彻底打破死锁条件。
    - **CAS 防误删**：移除旧窗口时使用 `ConcurrentHashMap.remove(key, window)` 的**双参数原子方法**，确保只删当前旧对象，绝不误删并发新建的同 Key 窗口。

**2. 遭遇非同类异常轰炸：如何防止探针 OOM？**
核心策略总结为“种类封顶、内存恒定、寿命自限、降级有界”：
- **种类封顶（硬闸门）**：通过 `maxPending`（默认 200）限制 Map 中不同 Key 的最大数量。达到上限后，新 Key 不再建窗，直接降级。
- **内存与次数解耦**：窗口只存 1 个 DTO 引用与一个 `int` 计数器，同一 Key 即使出现 100 万次，内存消耗也恒定在 MB 级。
- **寿命自限**：每个窗口创建时就绑定延迟任务，30 秒必执行移除，不存在无界常驻对象。
- **下游降级有界**：超限流量走实时推送通道，推送底层采用**固定单线程 + 有界阻塞队列（容量 1000）+ 丢弃最老任务策略（`DiscardOldestPolicy`）**，在极限风暴下主动舍弃冗余监控，死保宿主 JVM 内存安全。

- **标准回答**：
    > “如果系统对内存上限有极致严苛的要求，单纯依赖 `size()` 确实存在瞬时并发溢出。
    > 更严谨的工程解法是引入一个与 Map 配套的 **`AtomicInteger activeKeyCount`**：
    > 1. 在真正建窗前，先通过 CAS 对计数器进行递增预扣；
    > 2. 只有 CAS 累加成功且未超限的线程，才允许执行 `putIfAbsent`；
    > 3. CAS 失败或已超限的线程直接打入降级队列。
    > 这样便能将瞬时并发误差彻底锁定为 0，杜绝任何击穿可能。”

**追问二：既然只累加计数，为什么不用 LongAdder 而是加 synchronized 锁？**
- **面试官发难**：
    “单纯为了实现 `occurCount++`，直接用原生的 `AtomicInteger` 或并发吞吐更高的 `LongAdder` 即可，为什么还要在窗口上加重量级的 `synchronized` 锁？”
- **标准回答**：
    > “之所以必须用锁，是因为窗口状态的流转是一个**强一致的复合操作（Compound Action）**，而非孤立的数值累加：
    > 1. **多字段联动**：新异常到达时，不仅要增加 `occurCount`，还需要同步刷新 `lastOccurTime`，同时校验 `flushed` 状态标志。
    > 2. **原子类无法保障复合状态**：单一的 `LongAdder` 只能保障数值递增的原子性，无法保证‘检查状态 + 递增计数 + 刷新时间戳’这一整套动作的强一致。
    > 3. **锁开销极低**：这里的锁只锁单个窗口实例，临界区仅包含几行纯内存赋值，执行耗时在纳秒级别，既杜绝了状态混乱，又不会产生锁竞争瓶颈。”
    

## Q8 聚合去重的流程（多益网络）（9-15）
**去重键**：`errorClass|errorMethod`（buildDedupeKey），任一缺失退化为仅 errorClass。语义 =「哪种异常 + 出错位置」，同一位置的同类异常才算同一问题。

**Part 1：key 字段的链路来源（异构来源 → 同一 key 空间）**

- **HTTP 链路**（GlobalExceptionHandler）：errorClass = 解包到 rootCause 后的**全限定名**；errorMethod = `extractCallerLocation()` 遍历堆栈**跳过 JDK/反射/Proxy/CGLIB/Spring/MyBatis/monitor 帧，取第一个业务帧**，格式 `pkg.Class.method。效果：不同业务方法抛同种异常是不同 key，不误聚合。
- **SQL 链路**（SqlMonitorCollector.recordSqlError）：先 `unwrapException` 解包 MyBatis/反射包装异常拿真实 DB 根因；errorClass = 根因 `getSimpleName()`；errorMethod = **`shortMapperId(mappedStatementId)`**（截短的 mapper 语句 id，如 `XxxMapper.insert`）——SQL 异常的"位置"天然是 mapper 语句而非 Java 方法。
- **设计点**：两条链路取值手段完全不同（堆栈帧 vs mapper id），但对齐到同一语义后共用一套 map 去重。

### 节点①：buildDedupeKey() — “什么算同一个问题”


```java
return ec + "|" + em;   // errorClass|errorMethod
```

- 完整键 = `异常类名|出错位置`（如 `NullPointerException|UserService.getUser(UserService.java:142)`）
- **设计取舍**：只用类名太粗（不同地方的 NPE 会被误合并）；加上方法位置就能精确到“哪个坑里的异常”。缺 errorMethod 时降级只用类名，两个都缺返回 `null`（判为“无法归类”）

### 节点②：没有有效 Key → 直接送实时上报

`return false` 后，调用方 [pushErrorLog L203-205](file:///d:/hq_work_code/tdp-server/tdp-server/tdp-server/tdp-server-webapp/src/main/java/com/huaqin/tdp/server/monitor/service/MonitorReportService.java#L203-205) 会**继续往下走** `pushToHmp()` 实时推送。

> **贯穿全程的降级原则：任何走不下去的分支，都退化为“立即推送”——宁可多报，绝不漏报。**

### 节点③：缓存满 → 直接上报（自我保护）

```java
if (pendingErrors.size() >= maxPending) { return false; }
```

`pendingErrors` 是无界 CHM，如果瞬间涌入海量**不同 key** 的异常（如被扫描器打出一千种不同的 NPE 位置），窗口本身会变成内存泄漏点。所以设了 `errorDedupMaxPending` 上限，超限的新错误放弃聚合、直接实时推送——**牺牲聚合换可用性**。

### 节点④：get() 命中窗口 → 次数+1（快路径）

```java
ErrorWindow existing = pendingErrors.get(dedupeKey);
if (existing != null) { existing.recordRepeat(); return true; }
```

- CHM 的 `get()` 是**无锁读**，绝大多数异常（重复发生型）都走这条快路径，无 CAS 开销
- `recordRepeat()`是 `synchronized` 的：`occurCount++` 是“读-改-写”三步，volatile 只保证可见性不保证原子性，多线程同时 `++` 会丢计数，所以这里用方法锁
- `return true` → `pushErrorLog` 直接 return，**这条异常就被窗口“吸收”了**——不推 ESB，只等窗口到期一起算总账

### 节点⑤：未命中 → 创建窗口 + putIfAbsent（并发正确性的核心）
```java
ErrorWindow raceWinner = pendingErrors.putIfAbsent(dedupeKey, newWindow);
if (raceWinner != null) { raceWinner.recordRepeat(); return true; }
```

**为什么必须 `putIfAbsent` 而不是 `get()` 判空再 `put()`？**

`get` 和 `put` 之间存在时间间隙。两个线程几乎同时处理同类首条异常时：

```
线程A: get() → null ──────┐
线程B: get() → null ──┐   │
                      ↓   ↓
线程B: put(窗口B) → 线程A: put(窗口A)  ← A覆盖B！B窗口里的计数全丢
```

`putIfAbsent` 把“检查+放入”合成一个**原子操作**：
- 返回 `null` → 我是第一个放入的（竞争成功）
- 返回非 null（`raceWinner`）→ 别人抢先了（竞争失败），把当前 DTO 计到**赢家窗口**里 `recordRepeat()`

失败方什么都不丢、也不需要重试——这就是无锁编程里典型的“输家并入赢家”模式。

### 节点⑥：竞争成功 → 定时 30 秒

```java
long delaySeconds = Math.max(windowSeconds, 1L);
flushScheduler.schedule(() -> flushWindow(dedupeKey, newWindow), delaySeconds, TimeUnit.SECONDS);
```

两个关键点：
- **只有赢家调度定时器**，输家不调度——否则一个窗口会注册 N 个重复任务。这就是“窗口”的定义：**第一条异常开启窗口，30 秒内所有同类异常只累加，到期统一结算**
- `Math.max(..., 1)` 防御 Apollo 配置成 0/负数导致 `schedule` 立即执行或抛异常
- 单线程 `flushScheduler` 就够了（L74-78）：刷出只是组 DTO + 推送，不需要并发
==（竞争失败）累加到别人的窗口” = 我的窗口对象竞争失败成了垃圾（无所谓，反正同类异常信息在赢家窗口里已有一份），但**“这个异常发生过一次”的事实不能跟着陪葬**，所以要调用赢家的`recordRepeat()` 把这次发生记到赢家的账本上。竞争只决定“谁是窗口主人”，不决定“这次异常算不算数”。==
### 节点⑦：flushWindow() — 到期结算

**第一步：幂等防重刷**（L461-466）

```java
synchronized (window) {
    if (window.flushed) return;
    window.flushed = true;
}
```

极端竞态下可能有两个触发源（如停机时 `shutdownDedupScheduler()` 强制刷出 + 定时任务同时到期），`flushed` 标志保证**同一窗口只上报一次**——先抢到锁的置位，后来的直接退出。

**第二步：N→1 合并**（L468-490）

- 复用 `firstDto`（第一条异常的完整堆栈/URL/clientIp/traceId）——** detailed 信息只留第一份，因为 N 条同类异常的堆栈几乎相同，没必要存 N 份**
- 只覆盖 4 个聚合字段：`occurCount`（发生 N 次）、`firstOccurTime`、`lastOccurTime`、`collectTime`——**N 次压缩成 1 条后，次数和首次/末次时间信息全部保留**，这就是 N→1 不丢信息的关键

**第三步：条件移除**（L502）

```java
pendingErrors.remove(dedupeKey, window);
```

用**双参 CAS 版本**的 remove：只有 map 里的 value 还是这个 window 引用时才删除。防的是“flush 执行期间该 key 被别的东西重建”的假想场景——单参 remove 会误删新窗口，双参只删自己那个。

---

### 两条设计主线（面试可总结）

1. **并发正确性靠三层原子操作分层**：`get()` 做无锁快路径 → `putIfAbsent()` 解决创建竞态 → `remove(key,value)` 做条件删除；配 `volatile`（可见性）+ `synchronized recordRepeat`（计数原子性）+ `flushed` 标志（幂等）
2. **降级策略贯穿始终**：key 无效→实时推、缓存满→实时推、任何异常→实时推，**聚合是优化，可靠性兜底永远在场**——监控组件自身的原则是“不能因为去重把错误丢了”
# HTTP请求链路

###  **Q1：你的异常监控上报里是怎么拿到客户端 IP 的？为什么要上报它？**

---

**先说背景**：我们服务的异常监控链路里，全局异常处理器捕获到系统级异常后，会组装一个错误日志 DTO 异步推送到监控平台。这个 DTO 里除了堆栈、错误码、请求 URL，还专门带了一个 clientIp 字段——这个字段的获取和用途，正好能讲清楚“怎么拿”和“为什么拿”这两件事。

### 一、怎么拿：三级降级策略

获取客户端 IP 的核心难点在于：**生产环境请求几乎都经过反向代理，服务端 `getRemoteAddr()` 拿到的是网关 IP，不是真实客户端**。所以我们按优先级降级：

```
X-Forwarded-For → X-Real-IP → request.getRemoteAddr()
```

1. **优先取 `X-Forwarded-For`**：反代链路的标准头，格式是 `客户端IP, 代理1, 代理2...`，如果出现多段逗号，取第一段就是原始客户端，每经过一跳向后追加；
2. **取不到（null/空/"unknown"）就降级到 `X-Real-IP`**：nginx 常用 `proxy_set_header X-Real-IP $remote_addr` 单独设置的头部，通常直接就是真实 IP；
3. **都没有就兜底 `request.getRemoteAddr()`**：直连场景下这是真实客户端，反代场景下是网关 IP——虽然不理想，但保证字段不缺失。

实现细节上有两个坑要注意：一是某些代理在拿不到真实 IP 时会塞字符串 `"unknown"` 而不是 null，必须单独判断；二是整个方法要包 try-catch，**取 IP 失败绝不能影响异常上报主链路**，失败了就返回 "unknown" 占位。

### 二、为什么拿：给告警装上“流量来源”维度

只有堆栈，你只知道“**哪行代码错了**”；加上 clientIp，才知道“**谁的请求触发的**”。具体有三个用途：

1. **责任方判定**——排查告警时第一件事就是分清是服务端 bug 还是调用方问题：如果是某个固定 IP 高频触发异常，大概率是调用方传参有脏数据；如果是大量不同 IP 同时触发，那才是服务端真出事了；
2. **问题复现与追踪**——clientIp + 请求 URL + 请求方法构成完整请求画像，运维可以拿着 IP 去网关日志反查这次请求的完整出入参，快速定位到具体用户或上游系统；
3. **告警降噪**——如果某类异常总来自同一个调用方，说明是预期内的常态行为，可以评估把它加进排除列表，避免飞书告警轰炸。

### 三、主动暴露一个安全边界（加分项）

最后要主动说明：**XFF 是客户端可伪造的头**，攻击者可以随意添加伪造 IP。所以这套逻辑的前提是——入口处的 nginx 必须**覆盖**（而非追加）XFF 头，内层服务只信任自己代理写入的那一跳。脱离这个前提直接信任 XFF，就存在 IP 伪造风险，这也是这个知识点最容易踩的坑。

---

**一句话收尾**：技术方案上用 XFF → X-Real-IP → RemoteAddr 三级降级解决反代环境取真实 IP 的问题；业务价值上让告警从“知道错在哪”升级为“知道错在哪 + 谁触发的”，实现告警的闭环处理。
