# 1.滑动拼图验证码破解与设计（9-15）
把滑动验证码的攻防逻辑浓缩为“三步看破”和“三步设计”：
**一、黑产怎么破（就两步）**
1. **找缺口位置：** 拿背景图用 OpenCV（模板匹配/边缘检测）扫一下，或者用轻量图像模型，直接算出缺口离左边的距离 $X$。

2. **模拟人手拖动：** 脚本不能瞬间移过去（太假），他们会用数学曲线（比如贝塞尔曲线）生成“先慢 $\to$ 加速 $\to$ 减速微调”的轨迹，骗过后台。

**二、后端怎么设计（核心三件事）**

**1. 生成与存储（防偷看）**
- 服务端随机选一张图，随机切出一个带缺口的滑块，记录缺口坐标 $X$。
    
- 坐标 $X$ 存在 Redis 里（以一个随机 Token 为 Key，设置 60 秒过期）。
    
- **绝不能给前端传 $X$**，只传打乱切碎的图片和滑块图，前端只负责拼图和记录鼠标轨迹。
    
**2. 校验轨迹与位置（防作弊）**

前端把用户的滑动轨迹序列 $[(x, y, 时间)]$ 传回来，后端主要核对三点：
- **终点误差：** 拖动终点与真实 $X$ 差距是否在允许范围内（如 $\pm 3\text{px}$ 以内）。
    
- **$Y$ 轴抖动：** 人的手拖动时 $Y$ 轴一定会上下微小抖动，如果 $Y$ 全程是一条直线，直接判定为机器。
    
- **速度变化：** 全程匀速、或者耗时小于 200ms 的，直接拉黑。
    
**3. 一次性核销（防重放）**

- 校验时用 Redis `GETDEL` 取出并立即删掉该 Token，**一次有效**，不管成功失败都无法重试。
    
- 校验通过后，给前端返回一个**有效时间只有几秒的 `ticket`**，前端拿着 `ticket` 才能去调用登录或下单接口。

# 2.OOM，CPU 100% 爆栈等问题如何排查解决(9-15)
生产排查的核心是**四步闭环**：**监控报警 $\rightarrow$ 范围评估 $\rightarrow$ 快速止血 $\rightarrow$ 留痕溯源**。
## CPU 100%的可能原因
### 1. 死循环 / 代码逻辑问题

最常见。

```
while (true) {
    // 没有退出条件
}
```

或者递归异常、算法复杂度过高，比如突然执行了一个 `O(n²)` / `O(n³)` 的操作，数据量一大 CPU 就打满。

### 2. 大量并发任务

短时间内创建大量线程、任务，或者线程池任务堆积，CPU 不断进行计算。

例如：

- 线程池配置过大
- 大量请求同时进来
- 任务执行时间过长
- 线程频繁上下文切换

### 3. GC 导致 CPU 飙高

Java 服务比较常见。

例如：

```
大量创建临时对象
       ↓
堆内存快速增长
       ↓
GC频繁发生
       ↓
GC线程大量占用CPU
       ↓
CPU 100%
```

尤其是 Full GC 频繁发生时，需要重点排查。

### 4. 正则表达式 / 序列化等计算密集型操作

比如你之前遇到的 **Java 正则回溯问题**，复杂正则面对特殊输入可能进行大量回溯，导致 CPU 长时间占用。

类似的还有：

- 大量 JSON 序列化/反序列化
- 加密/解密
- 压缩
- 大量字符串处理

### 5. 系统层面的问题

不一定是 Java 程序本身，例如：

- 某个进程异常占用 CPU
- 大量进程竞争 CPU
- 内核态 CPU 占用过高
- 驱动或系统异常
## 一、CPU 100% 专项排查步骤
核心逻辑：**定位最耗 CPU 的宿主进程 $\to$ 抓取该进程下最耗 CPU 的线程 LWP $\to$ 转 16 进制去 jstack 线程栈中检索精准代码行。**
**步骤 1：找出 CPU 飙高的 Java 进程 PID**

```
top
# 观察 %CPU 列，记下最高的 PID（假设 PID 为 18820）
```

**步骤 2：找出该进程内最耗 CPU 的线程 ID（TID / LWP）**

```
top -Hp 18820
# -H: 显示线程级别；-p: 指定进程
# 按 P 键按 CPU 排序，记录第一行的 PID（此 PID 实际上是线程 ID，假设为 18855）
```

**步骤 3：将十进制线程 ID 转为十六进制**
```
printf "%x\n" 18855
# 输出: 49a7 （JVM jstack 中的 nid 都是 16 进制，前缀通常为 0x49a7）
```

**步骤 4：通过 jstack 抓取堆栈并精准检索**

```
# 抓取堆栈并过滤目标 nid 前后 30 行
jstack 18820 | grep -A 30 "nid=0x49a7"
```

**步骤 5：分析堆栈根因（常见两类）**
1. **死循环 / 业务计算密集：** 线程状态为 `RUNNABLE`，栈顶直接指向业务代码的具体某一行（如 `while` 条件写错、未跳出的递归、正则贪婪回溯等）。
2. **频繁 Full GC 引起的 CPU 飙高：** 抓出的高耗线程名称是 `VM Thread` 或 `GC task thread#...`。说明 CPU 不是被业务占满，而是垃圾回收线程在疯狂 STW 回收内存，**此时问题本质是 OOM/内存泄漏，必须立即转向排查 GC 与堆内存**。

> **Arthas 极速平替（线上最推荐）：**
> ```
> # 一键展示最耗 CPU 的前 3 个线程堆栈
> thread -n 3
> ```

## 二、OOM（内存溢出）专项排查步骤

OOM 主要分为两类：**堆内存溢出（Java heap space）** 与 **非堆/元空间溢出（Metaspace）**。
#### 1. 堆内存溢出（Java heap space）

核心逻辑：**获取 Dump 文件 $\to$ 用 MAT 分析泄露根因（支配树与 GC Roots）。**

**步骤 1：事前防范与配置（生产必备）**
生产环境启动参数必须配置 OOM 自动 Dump，防止内存爆掉后服务挂了现场丢失：

```
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/data/logs/heapdump.hprof
```

**步骤 2：事中现场手动打 Dump（若进程未崩溃但频繁 GC、堆已满）**

```
# 1. 实时查看各代内存占比与 FGC 次数（每 1 秒刷新一次）
jstat -gcutil 18820 1000 5
# 若 O (Old 区) 持续在 99% 以上且 FGC 计数狂飙，说明堆已撑死

# 2. 紧急手动导出 Dump 镜像（注意：会引发较长的 STW，确认已摘除流量）
jmap -dump:format=b,file=/data/logs/manual_dump.hprof 18820
```

**步骤 3：本地使用 MAT（Memory Analyzer Tool）深度分析**
1. **看 Leak Suspects（内存泄漏猜想报告）：** MAT 会自动计算最可疑的大对象占用饼图，通常能直接发现“某个类的实例占用了 80% 内存”。
2. **看 Dominator Tree（支配树）：** 按对象的 Retained Heap（保留内存，即释放该对象后能回收的内存量）倒序排列，找到占用最大的对象。
3. **查 GC Roots 链（Path to GC Roots）：** 选中大对象，右键点击 `Path to GC Roots` $\to$ `exclude all phantom/weak/soft references`（排除弱引用、软引用），只看强引用链。
    - **排查结果定性：**
        - **突发大对象：** 比如分页参数传了 0 查出了全表 100 万条数据，或者未做分批的超大 Excel 导出。
        - **内存泄漏：** 静态 `Map`/ThreadLocal 没有 `remove()` 持续累加对象、或者框架连接未关导致不可回收

#### 2. 元空间溢出（Metaspace OOM）
- **现象：** `java.lang.OutOfMemoryError: Metaspace`
- **根因与排查指令：** 通常是动态生成 Class 过多且无法卸载（如 CGLIB 代理泛滥、未缓存反射模板、未被回收的自定义 ClassLoader）。
    ```
    # 监控加载的类数量
    jstat -class 18820 1000 5
    
    # Arthas 查看类加载器层级与加载类分布
    classloader -l
    ```
## 三、爆栈（StackOverflowError）专项排查步骤

核心逻辑：**定位深层调用模式 $\to$ 区分“死递归”还是“单次深递归” $\to$ 抓取触发异常的入参。**

**步骤 1：捞取第一案发现场日志**
在 Kibana/ELK 中检索关键词 `StackOverflowError`，重点观察异常堆栈的**顶部数十行与循环模式**
- **业务死递归（无限循环）：** 堆栈中出现了 $A \to B \to A \to B$ 的交替循环，或者方法 $A$ 自身循环数千行。
- **正则回溯 / 深度嵌套：** 如你的脱敏实战场景，堆栈被 `Pattern$Curly.match` 刷屏，说明是正则非确定有限状态自动机（NFA）深层递归。

**步骤 2：Arthas 线上挂载与条件拦截（抓取现场脏入参）**

普通日志往往只打印了异常类名，缺失了造成深递归的原始输入参数。利用 Arthas 的 `-e`（仅捕获异常）参数，在报错瞬间抓取现场：

```
# 监控指定方法的入参，只在抛出异常时触发抓取
watch com.xxx.service.impl.OrderServiceImpl processTree "{params[0], throwExp}" -e -x 2
```

**步骤 3：堆栈容量诊断（区分业务 BUG 与阈值不足）**

- 查看 JVM 默认线程栈大小（一般默认为 1024KB / 1MB）：
    
    ```
    java -XX:+PrintFlagsFinal -version | grep ThreadStackSize
    ```
    
- **定性判断：**
    - 如果堆栈深度超过几千层且出现重复方法：**必为代码逻辑 BUG**，严禁通过盲目调大 `-Xss` 掩盖问题。
    - 如果代码本身确实是合理深度递归（如几十层的树遍历、解析深层 JSON），评估后可适当调节启动参数 `-Xss2m`，或将递归算法重构为“显式栈迭代 / 双指针状态机”。

## 真正企业生产环境的完整套路

你可以把它背成一个非常实用的面试答案：

> **生产环境出现异常后，我一般会先通过监控确认异常的时间、影响范围和错误类型，然后优先进行止血，比如回滚、摘流量、降级、熔断等，保证核心业务先恢复。之后结合日志、TraceId、异常 StackTrace、Metrics 等信息定位具体服务和请求。如果是 Java 应用，可以使用 Arthas 查看线程栈、调用链、方法参数和线上实际代码；对于 OOM、CPU 飙高、GC 异常等 JVM 问题，则进一步结合 jstack、JFR、Heap Dump、MAT 等工具分析。定位到问题后，我会在测试环境根据生产请求或数据进行复现，确认 Root Cause，修复后通过灰度发布验证，最后进行事故复盘，补充监控、测试用例或者代码防护，避免问题再次发生。**

这段已经比较接近**真实企业 Java 后端生产事故处理的思路**了。

最重要的是你要形成一个认知：

```text
              生产事故
                  │
          ┌───────┴───────┐
          ↓               ↓
       先止血            再定位
          │               │
  回滚/降级/熔断      日志/Trace/Metrics
                          │
                    ┌─────┴─────┐
                    ↓           ↓
                  JVM          业务
                    │           │
           Arthas/JFR/jstack   SQL/Redis/MQ
                    │           │
                    └─────┬─────┘
                          ↓
                       Root Cause
                          ↓
                        修复
                          ↓
                       灰度验证
                          ↓
                         复盘
```
