### 2.1 String

String 类型的底层的数据结构实现主要是**SDS**（简单动态字符串)。SDS 和我们认识的C 字符串不太一样，之所以没有使用C语言的字符串表示，因为SDS 相比于C的原生字符串：
• SDS 不仅可以保存文本数据，还可以保存二进制数据。因为 SDS 使用len 属性的值而不是空字符来判断字符串是否结束，并且 SDS的所有API 都会以处理二进制的方式来处理SDS 存放在 bufⅡ数组里的数据。所以SDS不光能存放文本数据，而且能保存图片、音频、视频、压缩文件这样的二进制数据。
• SDS 获取字符串长度的时间复杂度是 O(1)。因为C 语言的字符串并不记录自身长度，所以获取长度的复杂度为O(n)；而SDS 结构里用len 属性记录了字符串长度，所以复杂度为O(1)。
•Redis的SDSAPI是安全的，拼接字符串不会造成缓冲区溢出。因为SDS在拼接字符串之前会检查SDS空间是否满足要求，如果空间不够会自动扩容，所以不会导致缓冲区溢出的问题。
$$
（SDS 的拼接函数（如 sdscat）在操作时，内部逻辑完全不同。它的安全体现在 先检查，再扩容，最后写入。）
$$

```c
/* 注意：__attribute__ ((__packed__)) 的作用是告诉编译器取消结构体对齐优化，

 * 紧凑排列内存，这样可以直接通过 (char*)sh - 1 这种偏移操作找到 flags。 */

struct __attribute__ ((__packed__)) sdshdr8 {
    uint8_t len;          /* 已使用的字节长度 (String length) */
    uint8_t alloc;        /* 已分配的总长度 (不包含终止符 \0) */
    unsigned char flags;  /* 低3位表示类型 (sdshdr8/16/32等)，高5位未使用 */
    char buf[];           /* 字符数组，真正存放数据的地方 */
};

struct __attribute__ ((__packed__)) sdshdr16 {
    uint16_t len;
    uint16_t alloc;
    unsigned char flags;
    char buf[];
};

struct __attribute__ ((__packed__)) sdshdr32 {
    uint32_t len;
    uint32_t alloc;
    unsigned char flags;
    char buf[];
};
```

### 2.2list --双向链表 & 压缩列表

List 类型的底层数据结构是由**双向链表或压缩列表**实现的:
● 如果列表的元素个数小于 512 个（默认值，可由list-max-ziplist-entries 配置)，列表每个元素的值都小于 64字节（默认值，可由list-max-ziplist-value 配置），Redis 会使用压缩列表作为List 类型的底层数据结构;
●如果列表的元素不满足上面的条件，Redis 会使用双向链表作为 List 类型的底层数据结构;
但是在Redis 3.2版本之后，List数据类型底层数据结构就只由quicklist 实现了，替代了双向链表和压缩列表。

在 Redis 中，`List` 对象的底层实现经历了几次重要的演解。为了平衡**内存效率**（省钱）和**操作性能**（快），Redis 开发者设计了非常巧妙的数据结构。

我们要讨论的两种核心结构是：**双向链表 (Adlist)** 和 **压缩列表 (ZipList)**。

------

#### 2.2.1. 双向链表 (Adlist - Linked List)

这是最符合直觉的链表实现。在 Redis 早期版本中，当 `List` 包含的元素较多或单个元素很长时，就会使用它。

**结构定义**

Redis 定义了一个 `listNode` 结构表示节点，以及一个 `list` 结构来管理整条链表：

```c
typedef struct listNode {
    struct listNode *prev; // 前驱节点
    struct listNode *next; // 后续节点
    void *value;           // 节点值（void* 指针，可以存任何内容）
} listNode;

typedef struct list {
    listNode *head;     // 表头
    listNode *tail;     // 表尾
    unsigned long len;  // 节点数量
    // 还有一些函数指针，用于复制、释放和比对节点值
} list;
```

 **特点**

- **双端：** 获取 `prev` 和 `next` 的时间复杂度都是 $O(1)$。
- **无环：** 表头的 `prev` 和表尾的 `next` 都指向 `NULL`。
- **带长度计数：** 获取链表长度的时间复杂度为 $O(1)$。
- **多态：** 使用 `void*` 指针，可以保存不同类型的值。

 **缺点（致命伤）**

- **内存碎片：** 每个节点都是独立分配的内存，在内存中不连续，容易产生碎片。
- **额外开销：** 每个节点需要维护两个指针（16 字节，64 位系统下）。如果你的数据本身只有 1 字节（比如存一个 'a'），为了存这 1 字节，你得额外花 16 字节存指针，**内存利用率极低**。

#### 2.2.2压缩列表

为了解决双向链表太费内存的问题，Redis 开发了 **ZipList**。它不是通过指针连接的，而是一块**连续的内存。**

##### 结构布局

ZipList 就像是一个经过特殊设计的“字节数组”：

| **zlbytes** | **zltail** | **zllen** | **entry1** | **entry2** | **...** | **zlend** |
| ----------- | ---------- | --------- | ---------- | ---------- | ------- | --------- |
|             |            |           |            |            |         |           |

- **zlbytes:** 整个压缩列表占用的字节数。
- **zltail:** 记录到最后一个节点的偏移量（方便实现从后往前遍历）。
- **zllen:** 节点数量。
- **entry:** 真正存数据的地方。
- **zlend:** 特殊标记 `0xFF`，表示列表结束。

##### 每一个 Entry 的精妙之处

为了能实现双向遍历，每个 `entry` 包含两部分关键信息：

1. **previous_entry_length:** 前一个节点的长度。有了它，当前指针减去这个长度，就能跳到前一个节点（实现回溯）。
2. **encoding:** 记录当前数据是字符串还是整数，以及占用的长度。
3. **content:** 实际数据。

##### 优点

- **极致省钱：** 没有指针开销，数据紧挨着存放，内存利用率极高。
- **缓存友好：** 因为内存连续，CPU 缓存命中率（Cache Hit）比普通链表高得多。

##### 缺点

- **连锁更新（Cascading Update）：** 如果你往中间插入一个节点，导致后面节点的 `previous_entry_length` 字段需要扩容（比如从 1 字节变 5 字节），这可能引发连续的内存分配和拷贝。
- **不适合大数据量：** 修改操作需要重新分配内存并拷贝，数据量大时性能会急剧下降。

#### 2.2.3. 现在的 List 底层用什么？(QuickList)

你可能在想：既然双向链表费空间，压缩列表大数据量性能差，那 Redis 怎么选？

**答案是：全都要。**

从 Redis 3.2 开始，`List` 的底层统一变成了 **QuickList（快速列表）**。

- **QuickList 的逻辑：** 它是一个双向链表，但链表里的每一个 `listNode` 内部不再只存一个值，而是存一个 **ZipList**。
- **设计思想：** 结合了双向链表的“拆分”能力（避免大块内存申请）和 ZipList 的“压缩”能力（节省小数据的指针开销）。

### 2.3 Hash

在 Redis 7.0 之前，`Hash` 的底层主要由 **ZipList（压缩列表）** 和 **HashTable（哈希表）** 组成。而在 7.0 之后，ZipList 被替换成了性能更优、逻辑更简单的 **Listpack（紧凑列表）**。

------

1. 紧凑型实现：ZipList / Listpack

在 Redis 里，**listpack 和 ziplist 的对比是一个非常经典的面试点**，本质是“老压缩结构 vs 新压缩结构”的升级。

我帮你从**结构、性能、问题、使用场景**几个维度讲清楚👇

------

 一、核心一句话总结

> **listpack = ziplist 的升级版，解决了连锁更新问题，结构更简单、更安全**

------

 二、结构对比（重点）

 🔴 ziplist 结构

```
| zlbytes | zltail | zllen | entry | entry | ... | zlend |
```

每个 entry：

```
| prevlen | encoding | data |
```

特点：

- `prevlen`：记录前一个节点长度（关键点！）
- 支持从后往前遍历

------

🟢 listpack 结构

```
| total_bytes | num_elements | entry | entry | ... | end |
```

每个 entry：

```
| encoding | data | len |
```

特点：

- ❌ 没有 prevlen
- ✅ 用自身长度 len 支持反向遍历

------

三、最核心区别（面试必答）

 ❗1. 是否有 prevlen 字段

| 对比项     | ziplist      | listpack |
| ---------- | ------------ | -------- |
| 前节点长度 | ✅ 有 prevlen | ❌ 没有   |

👉 这点直接决定了一个重大问题 👇

------

 ❗2. 连锁更新问题（核心痛点）

ziplist 的问题：

如果你插入一个大元素：

```
entryA → entryB → entryC
```

当 entryA 变大：

- entryB 的 prevlen 可能从 1 字节变 5 字节
- entryC 也要变
- ……

👉 **引发连锁更新（cascade update）**
 👉 最坏 O(n²)

------

listpack 的解决方案：

👉 **直接取消 prevlen**

改成：

- 每个 entry 自己记录长度
- 反向遍历靠 len

👉 不会影响其他节点
 👉 **彻底消除连锁更新**

------

 四、内存 & 性能对比

| 维度     | ziplist              | listpack           |
| -------- | -------------------- | ------------------ |
| 内存占用 | 较小                 | 更小（结构更紧凑） |
| 插入性能 | 可能退化（连锁更新） | 稳定               |
| 查找性能 | O(n)                 | O(n)               |
| 遍历性能 | 快                   | 更快（cache友好）  |
| 安全性   | 较差（越界风险）     | 更安全             |

当你的 Hash 对象包含的键值对较少，且每个元素的长度较小时，Redis 会使用这种连续内存结构。

- **存储方式：** 键（Key）和值（Value）作为两个相邻的节点（Entry）紧挨着存放。
- **结构示例：** `[zlbytes, zltail, zllen, key1, value1, key2, value2, ..., zlend]`。
- **查询逻辑：** 由于是连续内存，查询时需要进行**遍历**。$O(n)$ 的复杂度在数据量极小（默认 512 个以内）时，由于 CPU 缓存命中率极高，性能甚至优于 HashTable。
- **Listpack 的进化：** ZipList 的 `previous_entry_length` 会导致“连锁更新”，而 Listpack 改为记录当前节点的长度，彻底解决了这个问题。

------

#### 2. 标准实现：HashTable (dict)

当 Hash 对象的元素变多，或者某个字符串特别长时，Redis 会将其“升级”（转换）为 HashTable。在 Redis 源码中，这被称为 `dict`（字典）。

#### 核心结构

Redis 的 HashTable 采用**链地址法**来解决哈希冲突，其结构体包含：

- **两个哈希表（ht[0], ht[1]）：** 正常情况下只使用 `ht[0]`，`ht[1]` 专门用于 **渐进式 rehash**。
- **dictEntry 节点：** 包含 `key`、`val` 和指向下一个节点的 `next` 指针。

```C
typedef struct dictEntry {
    void *key;
    union {
        void *val;
        uint64_t u64;
        int64_t s64;
    } v;
    struct dictEntry *next; // 指向下一个哈希节点，形成单向链表
} dictEntry;
```

------

#### 3. 核心机制：渐进式 rehash (Progressive Rehash)

这是 Redis 能够保持高性能的关键。传统的 HashTable 在扩容（rehash）时，往往需要一次性将所有数据迁移到新表，这会导致服务器在瞬时产生严重的阻塞（停顿）。

**Redis 的做法是“分而治之”：**

1. **触发：** 当负载因子（used/size）过大，Redis 分配一个两倍于原表大小的 `ht[1]`。
2. **搬迁：** Redis 不立刻搬迁数据。在后续的每一次对该 Hash 的**增删改查**操作中，除了执行对应操作，还会顺带将 `ht[0]` 在 `rehashidx` 索引上的所有键值对搬迁到 `ht[1]`。
3. **定时辅助：** Redis 还有后台定时任务，在服务器空闲时主动搬迁一部分数据。
4. **完成：** 随着操作的进行，`ht[0]` 最终变为空表，此时将 `ht[1]` 切换为 `ht[0]`，释放旧内存。

**查询逻辑的变化：** 在 rehash 期间，查询操作会先在 `ht[0]` 找，找不到再去 `ht[1]` 找。而新增操作则直接写入 `ht[1]`。

------

#### 4. 总结与应用思考

| **特性**     | **ZipList / Listpack (压缩列表)** | **HashTable (哈希表)**           |
| ------------ | --------------------------------- | -------------------------------- |
| **内存开销** | 极低（没有指针，紧凑排列）        | 较高（每个节点都有指针开销）     |
| **查询效率** | $O(n)$，适合小数据量              | $O(1)$，适合大数据量             |
| **典型场景** | 存储配置信息、用户基本信息        | 存储大规模映射关系、社交关注列表 |

### 2.4Set的底层实现

Set类型的底层数据结构是由哈希表或整数集合实现的:
● 如果集合中的元素都是整数且元素个数小于 512（默认值，set-maxintset-entries配置）个，Redis 会使用整数集合作为Set类型的底层数据结构;
• 如果集合中的元素不满足上面条件，则 Redis 使用哈希表作为 Set 类型的底层数据结构。

### 2.5 ZSet的实现

Zset 类型的底层数据结构是由**压缩列表或跳表**实现的:
⚫ 如果有序集合的元素个数小于128个，并且每个元素的值小于 64 字节时，Redis 会使用压缩列表作为Zset类型的底层数据结构；
● 如果有序集合的元素不满足上面的条件，Redis 会使用跳表作为 Zset类型的底层数据结构;
在 Redis7.0中，压缩列表数据结构已经废弃了，交由**Iistpack**数据结构来实现了。
