#八股 #并发 
# 1.Redis为什么那么快（高并发）

 ### 1. 纯内存操作（速度基石）

这是最根本的原因。Redis 的所有数据都存储在内存中，读写操作完全不涉及磁盘 I/O。

- **对比：** 磁盘寻道时间通常在毫秒（ms）级别，而内存访问延迟在纳秒（ns）级别。
- **结果：** 操作内存的速度比操作磁盘快几万倍，瓶颈不在硬盘而在网络和内存带宽。

### 2. 非阻塞 I/O 多路复用（高效率处理连接）

这是 Redis 能够同时处理成千上万个连接的秘诀。Redis 使用了 **epoll**（Linux 下）技术。

- **原理：** 单个线程通过 epoll 同时监控成千上万个 Socket 连接。它不会死等某个连接的数据，而是谁有数据发过来了，就去处理谁。
- **形象比喻：** 就像一个餐厅服务员（单线程），不用等每一桌客人点菜（阻塞 I/O），而是在前台盯着。哪一桌客人招手了（epoll 通知），他就过去记个菜单，然后迅速去下一桌。

### 3. 避免了多线程的上下文切换与锁竞争（最聪明的平衡）

很多人误以为线程越多越好，但线程是有代价的：

- **上下文切换：** CPU 从线程 A 切换到线程 B 需要保存和加载状态，这非常耗时。
- **锁的消耗：** 如果是多线程，操作同一个 Key 时必须加锁（如 Mutex）来保证数据安全。加锁、释放锁、等待锁会造成巨大的性能损耗。
- **Redis 的选择：** 采用**单线程模型处理核心网络请求和命令**，彻底避免了死锁和复杂的同步机制，代码执行效率极高。

### 4. 专为性能设计的高效数据结构

Redis 并没有直接使用普通的 Java/Go 数据结构，而是进行了大量的深度优化：

- **SDS (Simple Dynamic String)：** 相比 C 语言的字符串，获取长度的时间复杂度是 $O(1)$，且减少了内存分配次数。
- **跳表 (SkipList)：** 用于 ZSet，实现了平均 $O(\log N)$ 的查找效率，性能媲美平衡树但实现更简单。
- **压缩列表 (ZipList/listpack)：** 在数据量小时，通过紧凑的内存布局节省空间，提升 CPU 缓存命中率。
