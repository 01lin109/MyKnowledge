## 1. final 的可见性 vs volatile 的可见性

你把这两个记混了很常见，因为它们都涉及 **“可见”** 这个词，但底层机制和解决的问题完全不同。

- **`volatile` 的可见性（动态、持续的）：** 解决的是**多线程并发修改**的问题。当一个线程修改了 `volatile` 变量，其他线程能够_立刻_看到最新值。它依赖的是 CPU 的内存屏障（Memory Barrier）和缓存一致性协议。
    
- **`final` 的可见性（静态、一次性的）：** 准确来说叫 **“安全发布（Safe Publication）”**。
    
    - **问题背景：** 在多线程下，由于 CPU 指令重排，一个线程可能刚给对象分配了内存、还没执行完构造函数（没初始化完 `final` 变量），另一个线程就拿到了这个对象的引用，结果读到了 `final` 变量的默认值（比如 `0` 或 `null`）。
        
    - **底层原理：** JVM 规定，写 `final` 域的重排序规则会禁止把 `final` 域的写重排序到构造函数之外。
        
    - **大白话：** 只要对象构造完成了，其他线程**第一次**拿到这个对象引用时，看到的 `final` 变量绝对是初始化好的正确值，绝对不会读到“半成品”。
        

## 2. 构造函数里调用 this 会有什么问题？

这通常指的是 **“this 引用逃逸（this reference escape）”**。

### 核心风险

在构造函数还没有完全执行完毕（对象还没完全初始化好）的时候，就把当前对象的引用（`this`）暴露给了外部。

### 常见场景：

Java

```
public class EventListener {
    private final int value;

    public EventListener(EventSource source) {
        // 1. 注册监听器，把自己的 this 传了出去
        source.registerListener(new Listener() {
            public void onEvent(Object obj) {
                // 3. 外部线程可能在对象还没建完时就触发了这个事件，访问了 value
                System.out.println(value); 
            }
        });
        
        // 2. 构造函数的最后一步才初始化变量
        this.value = 42; 
    }
}
```

### 带来的后果

其他线程如果通过这个提早暴露的 `this` 引用去访问该对象，可能会读到未初始化的默认值（结合第一题，甚至连 `final` 的安全发布屏障都会失效），从而引发极其隐蔽的并发 Bug。

## 3. G1 和 ZGC 垃圾回收器

面试官问的 G1 的“两个 collect”，大概率是指 G1 的 **垃圾回收模式（Mixed GC & Full GC）** 或者它的核心组件。

### G1 (Garbage-First) 核心点（标记-整理）

- **内存布局：** 把堆内存拆分成了几千个大小相等的独立区域（**Region**），逻辑上保留了年轻代（Eden/Survivor）和老年代（Old），但它们不再是连续的。
    
- **G1 的两个主要收集阶段/模式：**
    
    1. **Young GC：** 选定所有年轻代 Region 进行回收。
        
    2. **Mixed GC（混合回收）：** 当老年代占比达到阈值时触发。它会回收**所有的年轻代 Region** + **部分回收价值最高的老年代 Region**（这就是为什么叫 "Garbage-First"，优先选垃圾多的区域回收）。
        
    
    - _注：如果 Mixed GC 赶不上内存分配的速度，G1 就会退化成单线程的 **Full GC**，带来极长的 STW（Stop-The-World）。_
        
#### 1. Collection Set (CSet) —— “待回收的区域集合”

- **是什么：** 顾名思义，就是**在当前这次垃圾回收中，有哪些 Region 将会被清理**。
    
- **里面装了啥：**
    
    - 如果是 **Young GC**：CSet 里面只包含**所有的年轻代 Region**（Eden 和 Survivor）。
        
    - 如果是 **Mixed GC**：CSet 里面除了包含**所有的年轻代 Region**，还会包含**一部分筛选出来的、垃圾最多、回收效率最高的老年代 Region**。
        
- **大白话：** 就像环卫工人的“垃圾清运路线图”，今天这趟车重点去哪几个小区收垃圾，这几个小区就是 CSet。
    

#### 2. Remembered Set (RSet) —— “记忆集”（你听到的 memory 大概就是它）

这个是全场最硬的核心点，也是面试官最想考你的。

- **为什么需要它（背景）：** G1 的核心思想是**分区域（Region）回收**。假设 G1 现在只想回收 Region A（年轻代）。但是，可能有一个老年代的对象在 Region B 里面，它的某根指针正指向着 Region A 里的某个对象。 如果 G1 只扫描 Region A，就会漏掉 Region B 对它的引用，误以为 Region A 里的对象是死掉的，直接给回收了，这就会导致程序崩溃！ **那怎么办？** 难道每次回收 Region A，都要把整个老年代（Region B、C、D...）全部扫描一遍吗？如果全扫描，那分 Region 隔离就没有任何意义了，性能直接雪崩。
    
- **它是怎么解决的：** **RSet 就是为了解决“跨Region引用”的问题。** G1 给**每一个 Region** 都配备了一个秘书，这个秘书拿的代码本就叫 **RSet**。 **它的核心逻辑是：“谁引用了我？”** 比如，老年代 Region B 里的对象引用了年轻代 Region A 里的对象，那么 Region A 的 RSet 里面就会记录下：_“Region B 引用了我。”_
    
- **工作流程：** 当 G1 要回收 Region A 的时候，它不需要扫描整个堆，只需要去看 **Region A 自己的 RSet**。一看，哦，只有 Region B 引用了我，那 G1 就只去扫描 Region B 里的那一小块地方（通过 Card Table 卡表精确定位）。
    

> **一句话总结 RSet 的代价：** 它是典型的**空间换时间**。有了 RSet，G1 在回收时速度极快（STW 时间短），但代价是每个 Region 都要维护一份 RSet，这会额外消耗堆内存的 5% ~ 20% 来存这些引用关系。
### ZGC (Z Garbage Collector) 核心点

- **超低延迟：** 专门为了大内存（TB级）**和**低延迟（停顿控制在10ms甚至1ms以内）设计。
    
- **大招：并发标记和并发转移。** 传统回收器在“移动对象”（整理内存碎片）时必须 STW。而 ZGC 借助了染色指针（Colored Pointers）**和**读屏障（Load Barriers）技术，实现了在垃圾回收、移动对象的同时，用户线程还能并发执行。
    

## 4. Hash 映射的原理

以 Java 的 `HashMap` 为例，它的核心原理可以概括为：**数组 + 链表/红黑树**，通过哈希算法实现 $O(1)$ 级别的快速查找。

整个映射和存储流程分为以下四步：

1. **计算 Hash 值（Hash Function）：**
    
    - 调用对象的 `hashCode()` 方法拿到原始哈希码。
        
    - 进行**扰动函数**处理（将高16位与低16位进行异或 `h ^ (h >>> 16)`），让哈希分布更均匀，减少后续的哈希冲突。
        
2. **路由寻址（找到数组下标）：**
    
    - 用计算出的哈希值对数组长度取模。代码中为了追求极致性能，采用位运算：`(n - 1) & hash`（这也是为什么 HashMap 的数组长度必须是 2 的幂次方）。
        
3. **解决哈希冲突（Hash Collision）：**
    
    - 不同的 Key 可能会计算出相同的数组下标。
        
    - **JDK 8 之前：** 采用**拉链法**，冲突的节点会排成一条单向链表。
        
    - **JDK 8 之后：** 当链表长度大于 `8` 且数组长度大于等于 `64` 时，链表会转换为**红黑树**，将最坏情况下的查找时间复杂度从 $O(n)$ 降到了 $O(\log n)$。
        
4. **扩容机制（Resize）：**
    
    - 当元素个数超过 `数组长度 * 加载因子`（默认 0.75）时，数组会扩容为原来的 2 倍，并把所有元素重新搬移、重新计算位置（Rehash）。

# 5.内存屏障
## 1. final 变量的内存屏障：只管“出厂安全”

`final` 的内存屏障非常纯粹，它只负责一件事：**保证对象在构造函数结束、被其他线程看见之前，它的 `final` 成员变量已经完全写完了。**

JMM（Java 内存模型）对 `final` 的写和读分别加了不同的屏障：

### 写 final 域的重排序规则

- **操作：** 在构造函数内，对一个 `final` 域的写入，与随后把这个被构造对象的引用赋值给一个引用变量，这两个操作之间会插入一个 **`StoreStore` 屏障**。
    
- **大白话：** `StoreStore` 相当于一个硬性规定 —— **“必须等前面的写操作（`final` 变量初始化）全部完成，才能执行后面的写操作（把对象引用暴露出去）”**。这就彻底杜绝了其他线程拿到一个“半成品”对象的可能。
    

### 读 final 域的重排序规则

- **操作：** 在在一个线程初次读一个包含 `final` 域的对象引用，与随后初次读这个 `final` 域之间，会插入一个 **`LoadLoad` 屏障**。
    
- **大白话：** 保证在读 `final` 变量的值之前，一定会先读到这个对象的引用。
    

> **总结：** `final` 的内存屏障是**一锤子买卖**。它只在对象**初始化创建**的时候生效。一旦对象构造完毕，后续你哪怕读它一万次，也不需要再过内存屏障了。

## 2. volatile 的内存屏障：管的是“全生命周期的动态同步”

跟 `final` 相比，`volatile` 的内存屏障就频繁、复杂得多。只要涉及 `volatile` 变量的**每一次读、每一次写**，都会触发内存屏障。

为了实现 `volatile` 的**可见性**和**有序性**（禁止重排序），JMM 在每个 `volatile` 读写周围筑起了四道高墙：

### 1. 在每个 volatile 写操作的前后：

- **前面插入 `StoreStore` 屏障：** 禁止上面的普通写和下面的 `volatile` 写重排序。保证前面所有的普通写，在当前 `volatile` 写之前已经刷新回主内存。
    
- **后面插入 `StoreLoad` 屏障：** **这是最重的一个屏障！** 它会强制刷新 CPU 缓存，让这次 `volatile` 写的数据立刻对其他 CPU 核心可见，并且防止后面的 `volatile` 读/写重排序。
    

### 2. 在每个 volatile 读操作的后面：

- **后面插入 `LoadLoad` 屏障：** 禁止下面的普通读和上面的 `volatile` 读重排序。
    
- **后面插入 `LoadStore` 屏障：** 禁止下面的普通写和上面的 `volatile` 读重排序。
    

## 3. 一图对比：它们到底差在哪？

为了让你在面试时能形成画面感，我们用一张表把它们的底层区别拉满：

|**特性**|**final 的内存屏障**|**volatile 的内存屏障**|
|---|---|---|
|**解决的核心问题**|对象的**安全发布**，防止读到构造未完成的半成品。|多线程并发下的**可见性**和**有序性**。|
|**影响的生命周期**|只有**构造函数执行时**（出厂那一下）。|变量被读写的**每一次、全生命周期**（只要运行就在管）。|
|**核心使用的屏障**|`StoreStore` (写) 、 `LoadLoad` (读)。|`StoreStore`, **`StoreLoad` (最核心、最重)**, `LoadLoad`, `LoadStore`。|
|**性能开销**|极低。只在初始化时拦截一次。|较高。每次读写都要过屏障，尤其是 `StoreLoad` 会引发 CPU 缓存行失效、清空流水线。|

# 6.synchronized锁升级的过程
`synchronized` 锁升级（锁膨胀）是 Java 并发高频面试题里的“压轴戏”。要彻底理清这个过程，我们需要紧扣两个核心：**Mark Word 的结构变化** 和 **CAS（Compare And Swap）的操作时机**。

## 1. 核心前置知识：什么是 Mark Word？

在 HotSpot 虚拟机中，对象在内存中的布局分为三块：对象头、实例数据和对齐填充。而**对象头**里的 **Mark Word** 就是专门用来存储对象自身运行时数据的，也是记录锁状态的地方。

在 64 位虚拟机中，Mark Word 占 8 个字节（64 个比特位）。锁升级的本质，就是这 64 位数据随着竞争激烈程度的变化而不断“变脸”的过程：

|**锁状态**|**25bit**|**31bit**|**1bit (cms)**|**4bit**|**1bit (是否偏向)**|**2bit (锁标志位)**|
|---|---|---|---|---|---|---|
|**无锁**|未使用|hashCode|未使用|分代年龄|**0**|**01**|
|**偏向锁**|**线程 ID (54bit)**|**Epoch (2bit)**|未使用|分代年龄|**1**|**01**|
|**轻量级锁**|**指向栈中锁记录（Lock Record）的指针 (62bit)**||||**00**||
|**重量级锁**|**指向互斥量（Monitor）的指针 (62bit)**||||**10**||

## 2. 锁升级的四部曲（结合 CAS 与 Mark Word）

Java 中的 `synchronized` 锁升级是不可逆的（在不考虑全局安全点垃圾回收重置的情况下），它会经历：**无锁 $\rightarrow$ 偏向锁 $\rightarrow$ 轻量级锁 $\rightarrow$ 重量级锁**。

### 第一阶段：无锁 $\rightarrow$ 偏向锁（单线程独占）

- **背景：** 大多数情况下，锁不仅不存在多线程竞争，而且总是由同一线程多次获得。为了让线程获取锁的代价更低，引入了偏向锁。
    
- **升级/获取过程：**
    
    1. 当一个线程访问同步块时，检查对象头的 Mark Word 里的**是否偏向**是不是 `0`，**锁标志位**是不是 `01`（此时是无锁状态）。
        
    2. 线程会尝试执行一次 **CAS 操作**：尝试将 Mark Word 中 54bit 的“线程ID”改成自己的线程 ID。
        
    3. **如果 CAS 成功：** 说明抢锁成功。Mark Word 的“是否偏向”变为 `1`，锁标志位依旧是 `01`。
        
    4. 以后该线程再进入和退出这个同步块时，**不需要再做任何 CAS 操作**，只需简单检查一下 Mark Word 里的线程 ID 是不是自己即可。几乎零开销。
        

### 第二阶段：偏向锁 $\rightarrow$ 轻量级锁（轻度竞争/交替执行）

- **背景：** 出现了另一个线程也想来挂号（抢锁），但此时**并没有发生强烈的冲突**，两个线程可能是交替执行的。
    
- **升级/撤销过程：**
    
    1. 线程 B 尝试获取锁，发现 Mark Word 里有偏向锁标识，且线程 ID 不是自己。
        
    2. 偏向锁不会主动释放。此时会等待 **全局安全点（Safe Point）**（在这个时间点没有字节码在执行），暂停拥有偏向锁的线程 A。
        
    3. 检查线程 A 的状态：如果线程 A 已经退出了同步块，则将锁重置为无锁状态，允许重新偏向；如果线程 A 还在同步块中，偏向锁就会**升级为轻量级锁**。
        
- **此时 Mark Word 的 CAS 变化：**
    
    - 线程 A 和线程 B 都会在各自的**栈帧**中开辟一块名为 **锁记录（Lock Record）** 的空间，把锁对象的 Mark Word 复制到 Lock Record 中（称为 Displaced Mark Word）。
        
    - 接着，线程尝试使用 **CAS 操作** 将锁对象的 Mark Word 替换为**指向自己栈帧中 Lock Record 的指针**。
        
    - **CAS 成功的线程**：获取轻量级锁成功，此时 Mark Word 的最后两位锁标志位变成 **`00`**。
        
    - **CAS 失败的线程**：说明有竞争，进入自选（自旋锁）。
        

### 第三阶段：轻量级锁 $\rightarrow$ 重量级锁（激烈竞争）

- **背景：** 竞争进一步加剧。自旋的线程在经过一定次数的自旋后，或者又来了更多的线程，轻量级锁就hold不住了。
    
- **升级/膨胀过程：**
    
    1. 没抢到锁的线程不会盲目挂起，而是先进行**自旋**（默认 10 次，现在采用自适应自旋 `Adaptive Spinning`），不断尝试通过 CAS 去修改 Mark Word 指向自己的锁记录。
        
    2. 如果自旋到了极限仍然没有抢到锁，或者在自旋期间又有第三个线程来抢锁，轻量级锁就会**膨胀为重量级锁**。
        
- **此时 Mark Word 的 CAS 变化：**
    
    - 停止自旋，将锁对象的 Mark Word 的最后两位锁标志位修改为 **`10`**（重量级锁标识）。
        
    - 将 Mark Word 前 62bit 修改为**指向堆中 Monitor 对象（管程）的指针**。
        
    - 此时，没抢到锁的线程全部进入内核态阻塞状态（EntryList），等待被操作系统唤醒。
        

## 3. 终极大总结：CAS 在其中的全景图

面试官非常喜欢问：“CAS 到底在锁升级里扮演了什么角色？”你可以用下面这句话一锤定音：

> “在 `synchronized` 的整个锁升级逻辑中，**CAS 是用来实现状态流转的『探测器』和『执行者』。**
> 
> - 在**无锁到偏向锁**时，通过一次 CAS 尝试写入自己的线程 ID；
>     
> - 在**偏向锁撤销升级**或**多个线程交替执行**时，通过 CAS 尝试将对象头指针指向自己栈帧中的锁记录（Lock Record），成功则代表获取轻量级锁；
>     
> - 在**轻量级锁阶段**，未抢到锁的线程通过自旋（多次 CAS）来死磕锁对象的 Mark Word。一旦 CAS 持续失败达到阈值，就意味着竞争失控，最终 Mark Word 被修改指向 Monitor 指针，彻底膨胀为重量级锁。”
>     

把 Mark Word 的标志位（`01` $\rightarrow$ `01偏向` $\rightarrow$ `00` $\rightarrow$ `10`）和 CAS 在每个阶段的使用时机结合起来聊，这个问题的回答就达到顶配水平了。


# 7为什么舍弃偏向锁
## 1. 时代变了：多线程与高并发的普及

- **过去的背景（JDK 6 时代）：** 很多早期的 Java 代码（比如 `Vector`、`Hashtable` 或早期的 `StringBuffer`）内部到处都是 `synchronized` 锁。但在实际应用中，绝大多数情况下这些锁都只有单线程在跑。偏向锁的出现，就是为了让这些“无竞争的同步代码”跑得跟普通代码一样快。
    
- **现在的现实（现代高并发场景）：** 现在的互联网应用几乎全面拥抱了多线程高并发、线程池、微服务架构。在如今的后端开发中（比如 Spring Boot 业务、中间件），**锁在绝大多数情况下都是存在多线程交替执行或者竞争的**。偏向锁能发挥作用的“纯单线程同步”场景越来越少。
    

## 2. 致命缺陷：偏向锁的“撤销”成本极其高昂

偏向锁不是免费的午餐，它的核心设计是：**假定锁会一直偏向同一个线程，直到有另一个线程来抢锁，才会发生“锁撤销（Revocation）”。**

正是这个“锁撤销”的过程，成为了偏向锁的噩梦：

1. **必须在安全点（STW）进行：** 为了安全地修改对象头里的线程 ID，JVM 必须暂停拥有偏向锁的那个线程。而要暂停线程，就必须等待 **全局安全点（Safe Point）**，这会导致整个 JVM 发生垃圾回收级别的 **STW（Stop-The-World）** 停顿。
    
2. **复杂的撤销逻辑：** JVM 需要去遍历所有线程的栈帧，检查那个拥有锁的线程是不是还在同步块里，以此来决定是把锁重置为无锁，还是升级为轻量级锁。
    
3. **开销雪崩：** 在现代高并发架构或使用线程池（大量线程交替复用）的场景下，偏向锁会频繁发生“抢锁 $\rightarrow$ 撤销偏向 $\rightarrow$ STW $\rightarrow$ 升级”的连环反应。原本为了提升性能设计的偏向锁，反而因为**频繁的 STW** 拖慢了整个系统的吞吐量。
    

## 3. 维护代价太高，阻碍了 JVM 的演进

偏向锁为了实现这套复杂的“偏向、撤销、重偏向、批量撤销”机制，在 HotSpot 虚拟机内核里引入了极度复杂的代码逻辑。

这些复杂的代码与 JVM 后续引入的新技术（例如 **Project Loom 的虚拟线程/协程**、新的垃圾回收器 ZGC 等）产生了大量的冲突和适配成本。HotSpot 开发者们认为，为了维护一个在现代高并发下“几乎没有正向收益、反而经常带来负面负荷”的旧特性，去阻碍 JVM 代码的整体演进，是完全不划算的。
