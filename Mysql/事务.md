## 1.事务的四大特性
- 原子性（Atomicity）：一个事务中的所有操作，要么全部完成，要么全部不完成，不会结束在中间某个环节，而且事务在执行过程中发生错误，会被回滚到事务开始前的状态，就像这个事务从来没有执行过一样，就好比买一件商品，购买成功时，则给商家付了钱，商品到手；购买失败时，则商品在商家手中，消费者的钱也没花出去。
- 一致性（Consistency）：是指事务操作前和操作后，数据满足完整性约束，数据库保持一致性状态。比如，用户 A 和用户 B 在银行分别有 800 元和 600 元，总共 1400 元，用户 A 给用户 B 转账 200 元，分为两个步骤，从 A 的账户扣除 200 元和对 B 的账户增加 200 元。一致性就是要求上述步骤操作后，最后的结果是用户 A 还有 600 元，用户 B 有 800 元，总共 1400 元，而不会出现用户 A 扣除了 200 元，但用户 B 未增加的情况（该情况，用户 A 和 B 均为 600 元，总共 1200 元）。
- 隔离性（Isolation）：数据库允许多个并发事务同时对其数据进行读写和修改的能力，隔离性可以防止多个事务并发执行时由于交叉执行而导致数据的不一致，因为多个事务同时使用相同的数据时，不会相互干扰，每个事务都有一个完整的数据空间，对其他并发事务是隔离的。也就是说，消费者购买商品这个事务，是不影响其他消费者购买的。
- 持久性（Durability）：事务处理结束后，对数据的修改就是永久的，即便系统故障也不会丢失。 
**MySQL InnoDB 引擎通过什么技术来保证事务的这四个特性的呢？**
- 持久性是通过 redo log （重做日志）来保证的；
- 原子性是通过 undo log（回滚日志）来保证的；
- 隔离性是通过 MVCC（多版本并发控制） 或锁机制来保证的；
- 一致性则是通过持久性+原子性+隔离性来保证；

#### 2.3.1Mysql有哪些隔离级别
 - 读未提交（read uncommitted），指一个事务还没提交时，它做的变更就能被其他事务看到；
 - 读提交（read committed），指一个事务提交之后，它做的变更才能被其他事务看到；
 - 可重复读（repeatable read），指一个事务执行过程中看到的数据，一直跟这个事务启动时看到的数据是一致的，MySQL InnoDB 引擎的默认**隔离级别**；
 - 串行化（serializable）；会对记录加上读写[[Mysql/锁]]，在多个事务对这条记录进行读写操作时，如果发生了读写冲突的时候，后访问的事务必须等前一个事务执行完成，才能继续执行； 
 按隔离水平高低排序如下： 针对不同的隔离级别，并发事务时可能发生的现象也会不同。 也就是说：
![[Pasted image 20260422102200.png]]
  - 在「读未提交」隔离级别下，可能发生脏读、不可重复读和幻读现象；
  - 在「读提交」隔离级别下，可能发生不可重复读和幻读现象，但是不可能发生脏读现象；
  - 在「可重复读」隔离级别下，可能发生幻读现象，但是不可能脏读和不可重复读现象；
  - 在「串行化」隔离级别下，脏读、不可重复读和幻读现象都不可能会发生。
  接下来，举个具体的例子来说明这四种隔离级别，有一张账户余额表，里面有一条账户余额为 100 万的记录。然后有两个并发的事务，事务 A 只负责查询余额，事务 B 则会将我的余额改成 200 万，下面是按照时间顺序执行两个事务的行为：
  ![[Pasted image 20260421223723.png]]
  在不同隔离级别下，事务 A 执行过程中查询到的余额可能会不同：

- 在「读未提交」隔离级别下，事务 B 修改余额后，虽然没有提交事务，但是此时的余额已经可以被事务 A 看见了，于是事务 A 中余额 V1 查询的值是 200 万，余额 V2、V3 自然也是 200 万了；
- 在「读提交」隔离级别下，事务 B 修改余额后，因为没有提交事务，所以事务 A 中余额 V1 的值还是 100 万，等事务 B 提交完后，最新的余额数据才能被事务 A 看见，因此额 V2、V3 都是 200 万；
- 在「可重复读」隔离级别下，事务 A 只能看见启动事务时的数据，所以余额 V1、余额 V2 的值都是 100 万，当事务 A 提交事务后，就能看见最新的余额数据了，所以余额 V3 的值是 200 万；
- 在「串行化」隔离级别下，事务 B 在执行将余额 100 万修改为 200 万时，由于此前事务 A 执行了读操作，这样就发生了读写冲突，于是就会被锁住，直到事务 A 提交后，事务 B 才可以继续执行，所以从 A 的角度看，余额 V1、V2 的值是 100 万，余额 V3 的值是 200 万。

#### 2.3.2四种隔离级别如何实现
- 对于「读未提交」隔离级别的事务来说，因为可以读到未提交事务修改的数据，所以直接读取最新的数据就好了；
- 对于「串行化」隔离级别的事务来说，通过加读写[[Mysql/锁]]的方式来避免并行访问；
- 「读提交」隔离级别是在每个 select 都会生成一个新的 Read View，也意味着，事务期间的多次读取同一条数据，前后两次读的数据可能会出现不一致，因为可能这期间另外一个事务修改了该记录，并提交了事务。
- 「可重复读」隔离级别是启动事务时生成一个 [[#3.3 ReadView（读视图）]]，然后整个事务期间都在用这个 Read View，这样就保证了在事务期间读到的数据都是事务启动前的记录。

事务 A 和 事务 B 的 Read View 具体内容如下：
- 在事务 A 的 Read View 中，它的 `creator_trx_id` 是 51，由于 `m_ids` 不包含当前事务自身，而事务 A 又是第一个启动的事务，所以此时 `m_ids` 为空列表，`max_trx_id`（下一个将要分配的事务 id）是 52。

- 事务 B 读取小林的账户余额记录，读到余额是 100 万； 
	
- 事务 A 将小林的账户余额记录修改成 200 万，并没有提交事务；
	
- 事务 B 读取小林的账户余额记录，读到余额还是 100 万； 
	
- 事务 A 提交事务； 
	
- 事务 B 读取小林的账户余额记录，读到余额依然还是 100 万；

接下来，跟大家具体分析下。 
**第一次读：**
- 事务 B 第一次读小林的账户余额记录，在找到记录后，它会先看这条记录的 `trx_id`，此时发现 `trx_id` 为 50，比事务 B 的 Read View 中的 `min_trx_id` 值（51）还小，这意味着修改这条记录的事务早就在事务 B 启动前提交过了，所以该版本的记录对事务 B 可见的，也就是事务 B 可以获取到这条记录。 
**第一次A修改：形成版本链**
- 接着，事务 A 通过 update 语句将这条记录修改了（还未提交事务），将小林的余额改成 200 万，这时 MySQL 会记录相应的 undo log，并以链表的方式串联起来，形成版本链，如下图：
![[Pasted image 20260529172351.png]]
- 你可以在上图的「记录的字段」看到，由于事务 A修改了该记录，以前的记录就变成旧版本记录了，于是最新记录和旧版本记录通过链表的方式串起来，而且最新记录的 trx id 是事务 A的事务 id(trx id =51)。
- 然后事务 B 第二次去读取该记录，发现这条记录的 trx_id 值为 51，在事务 B的 Read View 的min trx id 和 max trx id 之间，则需要判断 trx id 值是否在 m ids 范围内，判断的结果是在的，那么说明这条记录是被还未提交的事务修改的，这时事务B并不会读取这个版本的记录。而是沿着 undo log链条往下找旧版本的记录，直到找到 trx_id 「小于」事务B的 Read View 中的 min_trx_id 值的第一条记录，所以事务 B能读取到的是 trx id 为 50 的记录，也就是小林余额是 100 万的这条记录。
- 最后，当事物 A提交事务后，由于隔离级别时「可重复读」，所以事务 B 再次读取记录时，还是基于启动事务时创建的 Read View 来判断当前版本的记录是否可见。所以，即使事物 A将小林余额修改为 200万并提交了事务， 事务 B第三次读取记录时，读到的记录都是小林余额是 100 万的这条记录
就是通过这样的方式实现了，「可重复读」隔离级别下在事务期间读到的记录都是事务启动前的记录。

# 快照读&当前读：
## 1. 快照读（Snapshot Read）—— 读历史

快照读也就是**普通的、不加锁的 `SELECT` 查询**。
### 核心机制

- **不加锁**：快照读是完全不加锁的（也就是走 MVCC 机制）。它在读数据时，**既不加共享锁，也不加排他锁**。
    
- **读的是副本/快照**：当你执行快照读时，InnoDB 会根据当前的事务隔离级别，为你生成一个“一致性视图”（Read View）。哪怕此时有别的事务正在疯狂修改这行数据，你读到的也是它**过去的某个历史版本（保存在 Undo Log 里）**。
    
- **核心优势**：极大地提升了数据库的并发性能。做到了真正的“读写不冲突”（你改你的，我读我历史快照里的，互不干扰）。
    

### 常见 SQL 语句

```sql
SELECT * FROM user WHERE id = 1;
SELECT * FROM user WHERE age > 18;
```

_(注：必须是没有任何加锁后缀的纯 SELECT)_

## 2. 当前读（Current Read）—— 读现在

当前读顾名思义，**读取的是数据库中当前最新的、最真实的数据**。并且，为了防止在你读完之后别人立马去改，**当前读会对读取到的记录进行加锁**。

### 核心机制

- **强行读最新**：它会完全无视 MVCC 的 Read View 历史快照，直接去翻看数据库里当下已经被提交的、最热乎的最新数据。
    
- **必须加锁**：当前读在读取数据时，会根据你的操作目的，对涉及的行（或间隙）强制加上**共享锁（S 锁）**或**排他锁（X 锁）**。这就意味着，一旦你“当前读”了某条数据，别的事务如果想并发修改它，就会被你的锁堵住。
    
- **核心目的**：为了保证数据的**绝对一致性**。特别是当你准备基于查出来的数据去写新数据（比如“先查余额，再扣款”）时，必须用当前读，否则就会造成数据错乱。
    

### 常见 SQL 语句

```sql
-- 1. 显式加锁的查询（S 锁）
SELECT * FROM user WHERE id = 1 FOR SHARE; -- (或 LOCK IN SHARE MODE)

-- 2. 显式加锁的查询（X 锁）
SELECT * FROM user WHERE id = 1 FOR UPDATE;

-- 3. 所有的写操作（隐式当前读，加 X 锁）
UPDATE user SET name = '张三' WHERE id = 1;
DELETE FROM user WHERE id = 1;
INSERT INTO user (id, name) VALUES (1, '张三');
```

> **为什么 `UPDATE/DELETE/INSERT` 也算当前读？**
> 
> 拿 `UPDATE` 举例：MySQL 必须先知道 `id = 1` 的这条记录**当下最新**的状态和数据是什么，然后才能在它的基础上做修改。所以它必须先执行一次“当前读”拿到最新值，再写入新值。

## 📊 一张表看懂两者的本质区别

| **维度**    | **快照读 (Snapshot Read)** | **当前读 (Current Read)**  |
| --------- | ----------------------- | ----------------------- |
| **读到的数据** | 历史版本（Undo Log 中的快照数据）   | 最新版本（当前数据库中最真实的行）       |
| **加锁情况**  | **不加锁**（无锁并发）           | **必须加锁**（S 锁或 X 锁）      |
| **底层依赖**  | 纯靠 **MVCC** 机制          | 靠 **锁机制**（行锁、间隙锁等）      |
| **并发冲突**  | **读写不冲突**（性能极高）         | **读写、写写都会冲突**（可能需要排队）   |
| **使用场景**  | 纯数据展示（报表、文章列表、个人资料查看等）  | 涉及写操作的前置条件（扣减库存、转账、抢单等） |
|           |                         |                         |
# MVCC控制下仍会发生幻读的情况：
## 情景一：先快照读，后当前读（经典的 UPDATE 借尸还魂）

这是面试和实际开发中最常遇到的幻读场景。根源在于：**事务中间执行了一句当前读（如 `UPDATE`），打破了 MVCC 之前建立的快照保护，强行把别的事务新插入的数据“捞”了过来。**

假设有一张 `user` 表，主键为 `id`。目前表里**没有** `id = 5` 的数据。

### 📊 幻读发生的全程时序

- **第一步：事务 A 开启，执行快照读**
    
    SQL
    
    ```
    SELECT * FROM user WHERE id = 5; -- 结果：空（Nothing）
    ```
    
    _说明_：此时事务 A 生成了 Read View（快照）。因为是纯快照读，**没有加任何锁**，所以它不会阻止其他事务插入。
    
- **第二步：事务 B 插入并提交**
    
    SQL
    
    ```
    INSERT INTO user(id, name) VALUES(5, 'Tom');
    COMMIT;
    ```
    
    _说明_：事务 B 顺利插入了 `id = 5` 的行并提交。
    
- **第三步：事务 A 再次执行快照读**
    
    SQL
    
    ```
    SELECT * FROM user WHERE id = 5; -- 结果：依然为空！
    ```
    
    _说明_：**到这一步为止，MVCC 是完全生效的**。虽然事务 B 提交了，但根据 MVCC 的可见性规则，事务 A 的 Read View 帮它屏蔽了这行新数据，完美保持了“可重复读”。
    
- **第四步：事务 A 执行当前读（作死操作：修改该行）**
    
    SQL
    
    ```
    UPDATE user SET name = 'Jerry' WHERE id = 5;
    -- 结果：Query OK, 1 row affected (受影响行数竟然是 1 ！)
    ```
    
    _说明_：**关键转折点！** `UPDATE` 是**当前读**，它必须去读数据库里当下最新、最真实的数据。于是，它越过了 MVCC 的快照，在磁盘上发现了事务 B 刚插入的 `id = 5`，并且成功把它改成了 'Jerry'。 这一改，这行数据的隐藏列 `DB_TRX_ID`（最后修改该行的事务 ID）就变成了**事务 A 的事务 ID**。
    
- **第五步：事务 A 再次执行快照读**
    
    SQL
    
    ```
    SELECT * FROM user WHERE id = 5; 
    -- 结果：惊现 id=5, name='Jerry' 的数据！幻读发生！
    ```
    
    _说明_：为什么又看得见了？因为根据 MVCC 规则——**自己事务修改或插入的数据，对自己永远可见**。事务 A 这时候觉得：“这行数据的修改者是我自己啊，那我当然能看懂了。”
    

这就造成了严重的逻辑前后矛盾：明明前两次查都是空，动了下手改数据，它就凭空蹦出来了。

## 情景二：两边同时插入引发的“隐式幻读”（主键冲突悖论）

这个情景在严格意义上属于**隐式幻读**。事务 A 明明通过快照读确认某条数据不存在，但在尝试插入时却被硬生生挡住，感觉像活见鬼。

假设表 `user` 中目前**没有** `id = 8` 的数据。

1. **事务 A** 开启事务，执行快照读验证：
    
    SQL
    
    ```
    SELECT * FROM user WHERE id = 8; -- 结果：空
    ```
    
    _事务 A 心想：很好，没有 id=8 的人，我可以放心用这个 id 插入。_
    
2. **事务 B** 开启事务，默默插入并直接提交：
    
    SQL
    
    ```
    INSERT INTO user(id, name) VALUES(8, 'Alex');
    COMMIT;
    ```
    
3. **事务 A** 开始执行插入：
    
    SQL
    
    ```
    INSERT INTO user(id, name) VALUES(8, 'Bob');
    ```
    
    - **结果**：竟然爆出致命错误：`ERROR 1062 (23000): Duplicate entry '8' for key 'PRIMARY'`（主键冲突）。
        
4. **事务 A** 极其纳闷，再次执行快照读确认：
    
    SQL
    
    ```
    SELECT * FROM user WHERE id = 8; -- 结果：依然为空！
    ```
    

### 为什么这也是幻读？

对于事务 A 的代码逻辑来说，这产生了极大的认知错乱：**“你（MVCC）告诉我这条数据不存在，我写进去你又说主键冲突；我再生气查一次，你居然还睁着眼说瞎话，告诉我它不存在！”** 这种由于并发插入导致的“数据感知不一致”，也是纯 MVCC 无法阻挡的幻读表现。

## 💡 终极防坑总结

通过这两个血淋淋的场景，我们可以得出一个铁律：**MVCC 的本质是乐观的、无锁的“事后控制”**（通过版本链对比）。它只能保证你在“只读不写”时的世界一片静好。

一旦你的业务逻辑涉及到“先查，如果不存在就增/改”的逻辑，纯靠 MVCC 一定会出并发问题。

### 正确的解法

必须在第一步就破坏纯 MVCC 的快照读，直接强行升级为**当前读（加间隙锁）**：


```sql
-- 事务开始的第一步就锁死这个范围
SELECT * FROM user WHERE id = 5 FOR UPDATE;
```

一旦你加了 `FOR UPDATE`，InnoDB 就会在 `id = 5` 周围筑起一道**间隙锁（Gap Lock）**。此时事务 B 再想去 `INSERT`，就会在第一步直接被阻塞挂起、原地排队，直到事务 A 提交。这样，情景一和情景二的缝隙就被彻底堵死了。

# 3.MVCC的实现原理
在没有 MVCC 之前，为了保证并发安全，通常需要加锁。但这会导致：
- **读-读并发**：没问题。
- **读-写并发**：读会阻塞写，或者写会阻塞读，性能极差。
- **关键组件：** **隐式字段、Undo Log（回滚日志） 和 ReadView（读视图）。**
### 3.1 隐式字段

在 InnoDB 存储引擎中，每一行记录除了我们定义的列外，还有两个重要的隐藏列：

- **`DB_TRX_ID`**：记录最后一次修改该行记录的**事务 ID**。
    
- **`DB_ROLL_PTR`**：**回滚指针**，指向这条记录的上一个版本（存储在 Undo Log 中[[日志#2.undo log(回滚日志)#]]）
    
![[Pasted image 20260422105510.png]]
### 3.2 Undo Log（版本链）[[日志#2.undo log(回滚日志)]]

当一个事务修改某行数据时，InnoDB 会把旧版本的数据拷贝到 Undo Log 中。 通过隐藏列中的 `DB_ROLL_PTR` 指针，将这些旧版本串联起来，形成一个**版本链**。链表的头部是最新的记录，尾部是最旧的记录。
### 3.3 ReadView（读视图）
这是 MVCC 判断“哪个版本对当前事务可见”的依据。当事务执行快照读（普通的 `SELECT`）时，会产生一个 ReadView。 ReadView 中包含四个核心字段：

![[Pasted image 20260422103338.png]]

| **属性**               | **含义**                                                     |
| -------------------- | ---------------------------------------------------------- |
| **`m_ids`**          | 在生成 ReadView 时，当前系统中**活跃且未提交**的事务 ID 列表。                   |
| **`min_trx_id`**     | `m_ids` 中的最小值，即当前**最老**的一个未提交事务的 ID。                       |
| **`max_trx_id`**     | 系统中**即将分配**给下一个事务的 ID 值（注意：不是 `m_ids` 的最大值，而是最大事务 ID + 1）。 |
| **`creator_trx_id`** | 创建这个 ReadView 的**当前事务 ID**。                                |
创建Read View的时候可以将trx_id划分为三种情况
![[Pasted image 20260422104124.png]]
一个事务去访问记录的时候，除了「**自己的更新记录总是可见**（这里说明 trx_id == creator_trx_id 就是可见的）」之外，还有这几种情况： 
- 如果记录的 trx_id 值**小于** Read View 中的 `min_trx_id` 值，表示这个版本的记录是在创建 Read View **前已经提交的事务**生成的，所以该版本的记录对当前事务**可见**。
- 如果记录的 trx_id 值**大于**等于 Read View 中的 `max_trx_id` 值，表示这个版本的记录是在创建 Read View **后才启动的事务**生成的，所以该版本的记录对当前事务**不可见**。
- 如果记录的 trx_id 值在 Read View 的 `min_trx_id` 和 `max_trx_id` 之间，需要判断 trx_id 是否在 `m_ids` 列表中：
- 如果记录的 trx_id **在** `m_ids` 列表中，表示生成该版本记录的活跃事务依然活跃着（还没提交事务），所以该版本的记录对当前事务**不可见**。
- 如果记录的 trx_id **不在** `m_ids` 列表中，表示生成该版本记录的活跃事务已经被提交，所以该版本的记录对当前事务**可见**。 
如果满足不可见->通过[[日志#2.undo log(回滚日志)#2.2 实现 MVCC（多版本并发控制）—— “时空穿梭机”]]去找可见数据
这种通过「版本链」来控制并发事务访问同一个记录时的行为就叫 **MVCC（多版本并发控制）**。


# 4.分布式事务

## 一、 为什么需要分布式事务？（必要性）

在传统**单体架构**下，所有数据存在于同一个数据库中，利用关系型数据库自带的本地事务（ACID）即可轻松保证数据的正确性。

但在**微服务/分布式架构**下，业务链路跨越网络，被拆分成了多个独立的微服务和异构数据库。例如“用户下单”场景：

1. **订单服务** $\rightarrow$ 在 `Order_DB` 中创建订单。
    
2. **库存服务** $\rightarrow$ 在 `Stock_DB` 中扣减库存。
    
3. **账户服务** $\rightarrow$ 在 `Account_DB` 中扣减余额。
    

### 核心痛点：网络不可靠与数据孤岛

在分布式系统中，**网络超时、机器宕机、服务内部异常**是常态。一旦订单服务成功，而库存服务由于网络抖动失败，就会导致“订单已生成但库存未扣”的严重资损或数据不一致问题。

> **核心定义**：分布式事务存在的必要性，就是保证在**分布式环境（跨网络、跨数据源）**中，多个异构节点上的数据变更要么**全部成功**，要么**全部失败**，维持系统数据的**最终一致性**。

## 二、 理论基石：从 ACID 到 CAP 与 BASE

分布式事务的核心在于**如何在系统性能与一致性之间做出妥协**。

### 1. CAP 定理

- **C (Consistency - 强一致性)**：所有节点在同一时刻看到的数据完全一致。
    
- **A (Availability - 可用性)**：每个请求都能收到非错误的响应（但不保证获取的是最新数据）。
    
- **P (Partition tolerance - 分区容错性)**：系统由于网络原因导致部分节点失联时，仍能继续运行。
    

> **权衡法则**：在分布式网络中，网络分区（P）是必然发生的。因此，架构师必须在 **CP**（为了强一致，宁可拒绝服务）和 **AP**（为了高可用，允许数据暂时不一致）之间做抉择。

### 2. BASE 理论（AP 的延伸）

现代互联网高并发系统大多遵循 BASE 理论：

- **BA (Basically Available - 基本可用)**：系统故障时，允许损失部分可用性（如响应延迟、服务降级）。
    
- **S (Soft state - 软状态)**：允许系统中的数据存在中间状态，该状态不影响整体可用性。
    
- **E (Eventually consistent - 最终一致性)**：数据不需要实时强一致，但在一段时间后，所有节点的数据最终会达到一致。
    

## 三、 五大核心实现方案（原理链拆解）

根据一致性强弱，分布式事务方案可分为**刚性事务（追求强一致 CP）**和**柔性事务（追求最终一致 AP）**。

### 1. 2PC（Two-Phase Commit - 二阶段提交）—— 刚性事务

引入独立的“协调者（Coordinator）”来管理多个“参与者（Participant）”。

- **一阶段（Prepare）**：协调者询问所有参与者是否准备好。参与者执行本地事务、锁定资源，并反馈 Yes/No。
    
- **二阶段（Commit）**：若全员 Yes，协调者下发 Commit 指令；若有任意一个 No 或超时，下发 Rollback 指令。
    
- **致命缺陷**：**同步阻塞**（锁资源时间长）、**单点故障**（协调者挂了参与者会无限等待）、网络分区可能导致**数据不一致**。
    

### 2. Seata AT 模式（Automatic Transaction）—— 无感刚性/准强一致事务

**AT 模式是目前微服务生态（如 Java Spring Cloud）应用最广的方案，它完美契合了“无感事务”的理念。**

- **技术本质**：基于代理数据源（`DataSourceProxy`），在数据访问层（DAO）隐式拦截 SQL，自动生成逆序回滚日志。
    
- **一阶段（执行）**：
    
    1. 拦截业务 SQL（如 `UPDATE`）。
        
    2. 自动查询并记录修改前的行快照 —— **前镜像（Before Image）**。
        
    3. 执行业务 SQL，随后查询并记录修改后的快照 —— **后镜像（After Image）**。
        
    4. 将前后镜像打包成 JSON，作为 `undo_log` 与业务数据在**同一个本地事务中提交**，并向全局协调器（TC）申请**全局锁**，随后释放本地锁。
        
- **二阶段（提交/回滚）**：
    
    - **全局提交**：异步、批量删除对应的 `undo_log`，主业务无感。
        
    - **全局回滚**：校验后镜像与当前数据库真实数据是否一致（防脏写）。若一致，利用前镜像反向生成 `UPDATE` 语句还原数据。
        
- **优缺点**：**零业务代码侵入**（仅需一个 `@GlobalTransactional` 注解）；但在**高并发热点数据**场景下，全局锁竞争会导致严重的并发瓶颈，且仅支持关系型数据库。
    

### 3. TCC（Try-Confirm-Cancel）—— 柔性事务

应用层的二阶段提交，属于**补偿型**事务，需要业务层硬编码提供三个接口：

- **Try**：业务检查与**资源预留**（如：不直接扣款，而是冻结账户里的 100 元）。
    
- **Confirm**：真正执行业务。直接使用 Try 阶段预留的资源（Try 成功，Confirm 理论上必须成功）。
    
- **Cancel**：释放预留资源。若有节点失败，执行 Cancel 接口进行逆序回滚（如解冻那 100 元）。
    
- **优缺点**：资源锁定粒度由业务决定，性能优于 2PC/AT；但**业务侵入性极大**，开发成本成倍增加。
    

### 4. Saga 模式 —— 长事务柔性方案

适用于业务链路长、涉及第三方外部系统的场景。将一个大事务拆分成若干个本地局部事务（$T_1, T_2, ..., T_n$），每个局部事务都有一个对应的逆序正向补偿事务（$C_1, C_2, ..., C_n$）。

- **正常流程**：依次执行 $T_1 \rightarrow T_2 \rightarrow T_3$。
    
- **异常流程**：若 $T_3$ 失败，Saga 引擎会逆序执行补偿：$C_2 \rightarrow C_1$，把之前成功的数据改回去。
    
- **优缺点**：并发性能高，无锁阻碍，适合跨机构调用（如调用支付宝、物流接口）；但缺乏隔离性，可能存在超卖等中间状态。
    

### 5. MQ 事务消息 —— 可靠消息最终一致性

互联网高并发场景最常用的异步解耦方案，以支持事务消息的消息队列（如 RocketMQ）为核心。

- **原理链路**：
    
    1. 事务发起方发送一个 **Half Message（半消息）** 到 MQ（此时消费者不可见）。
        
    2. 发起方执行**本地事务**（如创建订单）。
        
    3. 发起方根据本地事务结果，向 MQ 发送 **Commit** 或 **Rollback** 指令。
        
    4. 若为 Commit，消息对下游可见，库存服务（消费者）拉取消息并执行扣减。
        
    5. 若下游消费失败，MQ 会不断发起**指数退避重试**；若持续失败则进入死信队列，触发人工介入。
        

## 四、 最佳实践范式与选型指南

### 1. 核心原则：能不用就不用（避免设计）

**最好的分布式事务，就是没有分布式事务。**

- **合理划分微服务**：对一致性要求极高且频繁交互的业务（如订单与订单明细），应合并为一个服务、一个数据库，降级为本地事务。
    
- **合理利用分库分表键**：利用 DDD 聚合根思想，将需要保证强一致的数据通过相同的 Sharding Key 路由到同一个数据库分片。
    

### 2. 分布式事务技术选型矩阵

|**业务场景**|**一致性要求**|**推荐方案**|**核心理由**|
|---|---|---|---|
|**企业后台/常规微服务**|准强一致性|**Seata AT 模式**|开发效率第一，业务量中等，零代码侵入。|
|**金融支付/核心资产账目**|强一致性|**TCC**|资金安全高于一切，必须在应用层精确冻结与控制资源。|
|**高并发 C 端链路（如电商下单）**|最终一致性|**MQ 事务消息**|异步解耦，高并发吞吐量优先，允许秒级延迟。|
|**跨第三方系统/复杂长流程**|最终一致性|**Saga 模式**|无法改造第三方接口，只能提供事后逆序补偿。|

### 3. “无感事务”机制在分布式中的落地

要真正让团队开发人员对分布式事务“无感”，底层的架构组件（AOP/中间件）必须在基础设施层强行拦截并处理好以下**三大魔鬼细节**：

- **幂等性（Idempotency）**：无论是 TCC 的 Confirm/Cancel 还是 MQ 的消费者，网络超时都会导致接口被多次调用。必须在底层拦截器中通过 **全局全局事务 ID (XID) + 业务唯一键** 做防重校验。
    
- **空回滚（Empty Rollback）**：在一阶段 Try 接口因为网络拥堵压根没执行，但分布式管理器超时触发了 Cancel/Saga 回滚时，回滚接口必须通过底层控制表识别出“一阶段未成功执行”，直接允许空回滚，而不是抛错。
    
- **悬挂问题（Anti-Suspension）**：卡住的 Try 请求在 Cancel 接口执行完（空回滚）之后才送达。无感组件必须在 Try 接口进入前检查该 `XID` 的状态，若已取消，则直接拒绝该延迟到达的 Try 请求。
    

### 4. 终极兜底：自动化对账与人工干预

在分布式领域，没有 100% 完美的硬编码。光纤被挖断、机房断电等不可抗力都会打破一致性。

- 必须建立独立的**自动化定时对账系统**（T+1 或 H+1），通过旁路数据比对发现不一致。
    
- 对账系统发现问题后，优先调用**自动化修复脚本/反向冲正流**进行修正。
    
- 极端大额异常直接触发告警，转由**人工运维/客服介入**手动对账和冲正。
