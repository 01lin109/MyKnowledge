## 索引常见面试题：
#### 1.为什么Mysql的InnoDB要选择B+Tree来做索引的数据结构
**1、B+Tree vs B Tree**
B+Tree只在叶子节点存储数据，而B树的非叶子节点也要存储数据，所以B+Tree的单个节点的数据量更，在相同的磁盘∕O次数下，就能查询更多的节点。
另外，B+Tree叶节点采的是双链表连接，适合MySQL中常见的基于范围的顺序查找，B树法做到这一点。
**2、B+Tree vs二叉树**
对于有N个叶子节点的B+Tree，其搜索复杂度为o(logdN），其中d表示节点允许的最子节点个数为d个。
在实际的应当中，d值是于100的，这样就保证了，即使数据达到千万级别时，B+Tree的度依然维持在3~4层左右，也就是说一次数据查询操作只需要做3~4次的磁盘1/O操作就能查询到目标数据。而叉树的每个父节点的子节点个数只能是2个，意味着其搜索复杂度为0(logN），这已经比B+Tree出不少，因此叉树检索到标数据所经历的磁盘l/O次数要更多。
**3、B+Tree Vs Hash**
Hash 在做等值查询的时候效率贼快，搜索复杂度为O(1)。
但是Hash表不适合做范围查询，它更适合做等值的查询，这也是B+Tree索引要比Hash表索引有着更广泛的适场景的原因。

#### 2.回表
**回表**是指在通过二级索引（Secondary Index）查到主键值后，由于索引中不包含查询所需的全部字段，MySQL 必须拿着主键值再去聚簇索引（Clustered Index）里查一遍完整的行记录。
如何解决：
**会导致回表的场景：**
即便你给查询列建立了索引，以下场景依然会触发回表：
-  A. 非覆盖索引查询（最常见）
这是回表的最直接原因。当你查询的字段没有全部包含在索引中时，就会发生回表。
- **例子**：索引为 `idx_user(name)`。
    
- **查询**：`SELECT name, age FROM users WHERE name = 'Zhang';`
    
- **原因**：索引里只有 `name` 和 `ID`，没有 `age`，所以必须回表。
- B. 使用 `SELECT *`

在生产环境中使用 `SELECT *` 是性能杀手，因为它几乎注定了无法命中覆盖索引。
- **影响**：即使你过滤条件的字段有索引，但由于 `*` 包含了大量非索引列，数据库不得不回表获取所有字段。
**解决：**
- 核心方案：覆盖索引（Covering Index）
**覆盖索引**是避免回表最有效的方法。其思路是将查询频繁的字段直接加入到索引中。
- **优化方案**：如果经常根据 `name` 查 `age`，将单列索引 `idx(name)` 改为联合索引 `idx(name, age)`。
    
- **结果**：索引页中已经包含了所需的所有数据，MySQL 直接从索引中返回结果，不再去查主键索引。
## 1.索引是什么
索引的定义就是帮助存储引擎快速获取数据的一种数据结构，形象的说就是索引是数据的目录。
所谓的存储引擎，说了就是如何存储数据、如何为存储的数据建索引和如何更新、查询数据等技术的实现法。MySQL存储引擎有MyISAM、InnoDB、Memory，其中InnoDB是在MySQL5.5之后成为默认的存储引擎。
## 2.索引的分类：
- 按「数据结构」分类：B+tree索引、Hash索引、Full-text索引。
- 按「物理存储」分类：聚簇索引（主键索引）、二级索引（辅助索引）。
- 按「字段特性」分类：主键索引、唯一索引、普通索引、前缀索引。
- 按「字段个数」分类：单列索引、联合索引。
### 2.1按数据结构分类：
从数据结构的度来看，MySQL常见索引有B+Tree索引、HASH索引、Full-Text索引。
每种存储引擎持的索引类型不定相同，我在表中总结了MySQL常的存储引擎InnoDB、MyISAM和Memory分别支持的索引类型。
![[Pasted image 20260503212714.png]]InnoDB是在MySQL5.5之后成为默认的MySQL存储引擎，B+Tree索引类型也是MySQL存储引擎采最多的索引类型。
在创建表时，InnoDB存储引擎会根据不同的场景选择不同的列作为索引：
- 如果有主键，默认会使主键作为聚簇索引的索引键（key）；
- 如果没有主键，就选择第个不包含NULL值的唯列作为聚簇索引的索引键（key）；
- 在上两个都没有的情况下，InnoDB将动成个隐式增id列作为聚簇索引的索引键（key）；
其它索引都属于辅助索引(Secondary Index），也被称为**二级索引或非聚簇索引**。创建的主键索引和级索引默认使用的是B+Tree索引。

#### 2.1.1B+Tree索引
![[Pasted image 20260506103601.png]]
B+Tree存储千万级的数据只需要3-4层高度就可以满足，这意味着从千万级的表查询目标数据最多需要3-4次磁盘I/O，所以B+Tree相比于B树和二叉树来说，最大的优势在于查询效率很，因为即使在数据量很大的情况，查询一个数据的磁盘O依然维持在3-4次。

**通过二级索引查询商品数据的过程**
- 主键索引的B+Tree和二级索引的B+Tree区别如下：
- 主键索引的B+Tree的叶子节点存放的是实际数据，所有完整的用户记录都存放在主键索引的B+Tree的叶子节点里；
- 二级索引的B+Tree的叶子节点存放的是主键值，而不是实际数据。

### 2.2按物理存储分
从物理存储的度来看，索引分为聚簇索引（主键索引）、级索引（辅助索引）。
这两个区别在前也提到了：
- 主键索引的B+Tree的叶子节点存放的是实际数据，所有完整的用户记录都存放在主键索引的B+Tree的叶子节点里；
- 二级索引的B+Tree的叶子节点存放的是主键值，不是实际数据。
所以，在查询时使用了二级索引，如果查询的数据能在二级索引查询的到，那么就不需要回表，这个过程就是覆盖索引。如果查询的数据不在级索引，就会先检索级索引，找到对应的叶节点，获取到主键值后，然后再检索主键索引，就能查询到数据了，这个过程就是回表。
### 2.3按字段特性分类
从字段特性的角度来看，索引分为主键索引、唯一索引、普通索引、前缀索引。
从字段特性的角度来看，这四种索引分别承担着**数据约束**和**检索加速**的不同职责。以下是它们的简要对比：
##### 1. 主键索引 (Primary Key Index)

- **特性**：它是表中每一行的唯一标识。一个表**有且只能有一个**主键。
    
- **约束**：索引列的值必须唯一，且**不允许为 NULL**。
    
- **物理实现**：在 InnoDB 存储引擎中，主键索引即**聚簇索引**。行数据直接存储在主键索引的叶子节点上，因此根据主键查询的速度是最快的。
    

##### 2. 唯一索引 (Unique Index)

- **特性**：主要目的是为了防止数据重复。
    
- **约束**：索引列的值必须唯一，但**允许为 NULL**（且可以存在多个 NULL，因为数据库认为 NULL 不等于 NULL）。
    
- **应用**：常用于业务上要求唯一的字段，如身份证号、手机号或邮箱，确保数据的一致性。
    

##### 3. 普通索引 (Normal/Secondary Index)

- **特性**：没有任何约束，纯粹是为了**加速查询**。
    
- **约束**：允许值重复，允许为 NULL。
    
- **应用**：这是最常用的索引类型。当你发现某个字段经常出现在 `WHERE` 条件、`ORDER BY` 或 `GROUP BY` 中，但它又不具备唯一性时（如“姓名”、“城市”、“状态”），就会建立普通索引。
##### 4. 前缀索引 (Prefix Index)
- **特性**：它是普通索引的一种特殊形式，只对字符串（如 `VARCHAR`、`TEXT`）的**前一部分字符**建立索引。
- **优点**：
    - **节省空间**：索引只存前几个字符，占用的磁盘空间更小。
        
    - **效率高**：更小的索引意味着更快的插入速度和更少的内存占用。
- **缺点**：无法用于 `ORDER BY` 或 `GROUP BY`，且**无法实现覆盖索引**（因为索引中不含完整字段值，必须回表验证）。
- **示例**：`ALTER TABLE users ADD INDEX idx_email(email(10));` —— 仅对邮箱的前 10 个字符建索引。
---

##### 快速对比表

|**索引类型**|**唯一性限制**|**允许为 NULL**|**数量限制**|**主要用途**|
|---|---|---|---|---|
|**主键索引**|强制唯一|否|一个表仅一个|唯一标识一行，数据物理排序|
|**唯一索引**|强制唯一|是|不限|保证业务数据唯一性|
|**普通索引**|无|是|不限|提高检索性能|
|**前缀索引**|无|是|不限|针对长字符串，节省空间|

在选择时，通常遵循：**能唯一则唯一（Unique），需加速则普通（Normal），字段太长选前缀（Prefix）。**

### 2.4按字段个数分类
从字段个数的度来看，索引分为单列索引、联合索引（复合索引）。
• 建在单列上的索引称为单列索引，比如主键索引；
• 建立在多列上的索引称为联合索引；
#### 2.4.1联合索引
将多个字段组合形成一个索引
```
create index index_product_to_name on product(product_no,name)
```
![[Pasted image 20260506105951.png]]
可以看到，联合索引的非叶节点两个字段的值作为B+Tree的key值。当在联合索引查询数据时，先按product_no字段比较，在product_no相同的情况下再按name字段比较。
也就是说，联合索引查询的B+Tree是先按product_no进排序，然后再product_no相同的情况再按name字段排序。
因此，使用联合索引时，存在**最左匹配原则**，也就是按照最左优先的方式进行索引的匹配。在使用联合索引进查询的时候，如果不遵循「最左匹配原则」，联合索引会失效，这样就法利到索引快速查询的特性了。

> [!最左匹配原则] 最左匹配原则
> 如，如果创建了个 （a，b，c）联合索引，如果查询条件是以下这种，就可以匹配上联合索引：
• where a=1;
• where a=1 and b=2 and c=3;
•where a=1 and b=2;
需要注意的是，因为有查询优化器，所以a字段在where句的顺序并不重要。
但是，如果查询条件是以下这种，因为不符合最左匹配原则，所以就法匹配上联合索引，联合索引就会失效：
• where b=2;
• where c=3;
• where b=2 and c=3;
上面这些查询条件之所以会失效，是因为（a，b，c）联合索引，是先按a排序，在a相同的情况再按b排序，在b相同的情况再按c排序。所以，**b和c是全局无序**，局部相对有序的，这样在没有遵循最左匹配原则的情况下，是无法利到索引的。![[Pasted image 20260506110303.png]]可以看到，a是全局有序的（1，2,2,3，4,5,6,7,8），而**b是全局是无序**的（12，7，8，2，3，8，10，5，2）。因此，直接执whereb=2这种查询条件没有办法利联合索引的，利索引的前提是索引里的key是有序的。
只有在a相同的情况才，b才是有序的，比如a等于2的时候，b的值为（7，8），这时就是有序的，这个有序状态是局部的，因此，执wherea=2andb=7是a和b字段能用到联合索引的，也就是联合索引生效了。
##### 2.4.1.1联合索引范围查询
联合索引有一些特殊情况，并不是查询过程使用了联合索引查询，就代表联合索引中的所有字段都到了联合索引进索引查询，也就是可能存在部分字段到联合索引的B+Tree，部分字段没有到联合索引的B+Tree的情况。
这种特殊情况就发生在范围查询。联合索引的最左匹配原则会一直向右匹配直到遇到「范围查询」就会停止匹配。也就是范围查询的字段可以用到联合索引，但是在范围查询字段的后面的字段无法用到联合索引。

> [!联合索引范围查询实例]  Q1
> select * from table where a>1 and b=2联合索引 (a,b）哪个字段用到了联合索引|的 B+Tree?

由于联合索引（二级索引）是先按照a字段的值排序的，所以符合a>1条件的二级索引记录肯定是相邻，于是在进索引扫描的时候，可以定位到符合a>1条件的第条记录，然后沿着记录所在的链表向后扫描，直到某条记录不符合a>1条件位置。所以a字段可以在联合索引的B+Tree中进索引查询。
但是在符合a>1条件的二级索引记录的范围，b字段的值是无序的。比如前面图的联合索引的B+Tree，下面这三条记录的a字段的值都符合a>1查询条件，b字段的值是无序的：
•a字段值为5的记录，该记录的b字段值为8；
• a字段值为6的记录，该记录的b字段值为10；
• a字段值为7的记录，该记录的b字段值为5；
因此，我们不能根据查询条件b=2来进步减少需要扫描的记录数量(b字段法利联合索引进索引查询的意思）。
所以在执行Q1这条查询语句的时候，对应的扫描区间是(2，+∞)，形成该扫描区间的边界条件是a>1，与b=2无关。
因此，Q1这条查询语句只有a字段到了联合索引进索引查询，b字段并没有使到联合索引。
我们也可以在执计划中的key_len知道这点，在使联合索引进查询的时候，通过key_len我们可以知道优化器具体使了多少个字段的搜索条件来形成扫描区间的边界条件。

举例个例子，a和b都是int类型且不为NULL的字段，那么Q1这条查询语句执计划如下，可以看到key_len为4字节（如果字段允许为NULL，就在字段类型占的字节数上加1，也就是5字节），说明只有a字段用到了联合索引进行索引查询，而且可以看到，即使b字段没用到联合索引，key为idx_a_b，说明Q1查询语句使用了idx_a_b联合索引。

### 3.索引下推：
现在我们知道，对于联合索引(a,b），在执行 select*from table where a>1 and b = 2 语句的时候，只有a字段能到索引，那在联合索引的B+Tree找到第个满条件的主键值（ID为2）后，还需要判断其他条件是否满（看b是否等于2），那是在联合索引判断？还是回主键索引去判断呢?
- 在MySQL5.6之前，只能从ID2（主键值）开始个个回表，到「主键索引」上找出数据，再对b字段值。
- MySQL5.6引的索引下推优化(indexcondition pushdown)，可以在联合索引遍历过程中，对联合索引中包含的字段先做判断，直接过滤掉不满条件的记录，减少回表次数。
当你的查询语句的执行计划里，出现了Extra为Using index condition，那么说明使用了索引下推的优化。

### 4.索引区分度：
另外，建联合索引时的字段顺序，对索引效率也有很大影响。越靠前的字段被用于索引过滤的概率越，实际开发作中建联合索引时，要把区分度的字段排在前面，这样区分度的字段越有可能被更多的SQL使用到。
区分度就是某个字段column不同值的个数「除以」表的总数，计算公式如下：

如，性别的区分度就很小，不适合建索引或不适合排在联合索引列的靠前的位置，UUID这类字段就比较适合做索引或排在联合索引列的靠前的位置。
因为如果索引的区分度很，假设字段的值分布均匀，那么论搜索哪个值都可能得到半的数据。在这些情况下，还不如不要索引，因为MySQL还有个查询优化器，查询优化器发现某个值出现在表的数据中的百分比（惯的百分界线是"30%"）很的时候，它一般会忽略索引，进全表扫描。

# 联合索引排序

> [!NOTE] select * from order where status = 1 order by create_time asc
> 
有的同学会认为，单独给status建个索引就可以了。
但是更好的方式给status和create_time列建一个联合索引，因为这样可以避免MySQL数据库发生件排序。
因为在查询时，如果只用到status的索引，但是这条语句还要对create_time排序，这时就要用件排序filesort，也就是在SQL执行计划中，Extra列会出现Using filesort。
所以，要利索引的有序性，在status和create_time列建联合索引，这样根据status筛选后的数据就是按照create_time排好序的，避免在件排序，提了查询效率。
在 MySQL 优化中，`filesort` 是一个经常被误解的术语。它并不一定代表“在磁盘上排序”，但它确实意味着 MySQL 无法利用索引的有序性来直接获取结果。

针对你的 SQL：`select * from order where status = 1 order by create_time asc`，我们来深度剖析一下。

---

## 1. 为什么只给 `status` 加索引会导致 `filesort`？

要理解这个问题，首先要明白 **B+Tree 索引的本质是有序的**。

- **当你只给 `status` 加索引时**：
    在该索引树中，记录是按照 `status` 的值进行排序的。对于 `status = 1` 的所有记录，它们在索引树中是聚集在一起的。
- **问题的核心**：
    虽然 `status = 1` 的记录在索引里连在一起，但在这些 `status` 相同的记录内部，**`create_time` 是乱序的**（除非你在索引中明确包含了 `create_time`）。
### 执行过程如下：

1. MySQL 通过 `status` 索引找到所有 `status = 1` 的主键 ID。
    
2. 由于你需要 `SELECT *`，MySQL 必须拿着这些 ID 回表（回聚簇索引）取完整的行数据。
    
3. **关键点**：此时取出的数据是按照 `status` 索引的顺序排好的，或者是回表时随机取出的，**它们并不是按照 `create_time` 排序的**。
    
4. 为了满足 `ORDER BY create_time`，MySQL 只能在内存（或磁盘）中将这些结果集重新进行排序。这个**重新排序的过程**就叫 `filesort`。
---
## 2. 什么是 `filesort`？

**`filesort`（文件排序）** 是指 MySQL 优化器采取的一种排序算法，用于处理那些无法通过索引直接完成的排序操作。

> **误区澄清**：`filesort` 并不一定意味着“在磁盘文件上排序”。
> 
> - 如果结果集较小，能在 `sort_buffer_size`（内存缓冲区）中装下，排序就在**内存**中完成。
>     
> - 如果结果集太大，内存装不下，才会利用**磁盘临时文件**进行外部排序。
>     

### `filesort` 的两种主要算法：

1. **双路排序（Two-Pass）**：
    
    先取出排序字段和行指针，在内存排好序后，再根据指针回表读记录。这会产生两次 I/O。
    
2. **单路排序（Single-Pass）**：
    
    一次性取出所有需要的列字段（`SELECT` 后的所有列）放入内存，直接按排序字段排序。它减少了回表次数，但更占内存，容易触发磁盘排序。
---

## 3. 如何消除这里的 `filesort`？

要消除 `filesort`，必须让索引本身就具备“先按 `status` 过滤，再按 `create_time` 排序”的特性
**解决方案：建立联合索引 `idx_status_create_time(status, create_time)`**
### 优化后的执行逻辑：

1. MySQL 进入联合索引树，找到 `status = 1` 的位置。
    
2. 由于联合索引遵循**左前缀原则**，在 `status` 相同的情况下，`create_time` 是天然有序的。
    
3. MySQL 顺着索引叶子节点的链表往下读，取出的每一条数据都已经排好序了。
    
4. **结果**：执行计划（EXPLAIN）中的 `Extra` 字段将从 `Using filesort` 变为 `Using index`（如果覆盖索引）或不再显示 filesort。
---
## 4. 生产建议

1. **查询与排序的平衡**：在设计索引时，如果 `WHERE` 过滤后的结果集很大，那么 `ORDER BY` 的字段一定要考虑加入联合索引。
    
2. **避免 `SELECT *`**：如果你建立联合索引 `(status, create_time)` 但仍然 `SELECT *`，虽然可以利用索引排序，但仍需**回表**获取其他字段。如果只查询这两个字段，则能实现**覆盖索引**，连回表都省了，性能达到极致。
    
3. **监控 `sort_buffer_size`**：如果业务中确实无法避免 `filesort`，可以适当调大该参数以确保排序尽量在内存中完成，但这只是治标不治本的方法。

# 3.索引优化
## 3.1什么时候需要索引什么时候不需要
索引最的好处是提查询速度，但是索引也是有缺点的，如：
• 需要占物理空间，数量越，占空间越；
•创建索引和维护索引要耗费时间，这种时间随着数据量的增加而增大；
• 会降低表的增删改的效率，因为每次增删改索引，B+树为了维护索引有序性，都需要进动态维护。
所以，索引不是万能钥匙，它也是根据场景来使的。
**什么时候适索引?**
• 字段有唯一性限制的，比如商品编码；
•经常于WHERE查询条件的字段，这样能够提整个表的查询速度，如果查询条件不是个字段，可以建联合索引。
- 经常用于 GROUP BY 和 ORDER BY 的字段，这样在查询的时候就不需要再去做次排序了，因为我们都已经知道了建立索引之后在B+Tree中的记录都是排序好的。
**什么时候不需要创建索引?**
- WHERE 条件， GROUP BY， ORDER BY 不到的字段，索引的价值是快速定位，如果起不到定位的字段通常是不需要创建索引的，因为索引是会占物理空间的。
- 字段中存在量重复数据，不需要创建索引，如性别字段，只有男，如果数据库表中，男的记录分布均匀，那么论搜索哪个值都可能得到半的数据。在这些情况下，还不如不要索引，因为MySQL还有一个查询优化器，查询优化器发现某个值出现在表的数据中的百分很的时候，它一般会忽略索引，进全表扫描。
- 表数据太少的时候，不需要创建索引；
- 经常更新的字段不创建索引，如不要对电商项的户余额建索引，因为索引字段频繁修改，由于要维护B+Tree的有序性，那么就需要频繁的重建索引，这个过程是会影响数据库性能的。
## 3.2索引优化的方法：
- 前缀索引优化；
- 覆盖索引优化；
- 主键索引最好是自增的；
- 防止索引失效；
### 3.2.1前缀索引优化：
前缀索引顾名思义就是使某个字段中字符串的前个字符建索引，那我们为什么需要使前缀来建索引呢?
使用前缀索引是为了减索引字段大，可以增加个索引页中存储的索引值，有效提索引的查询速度。在一些字符串的字段作为索引时，使前缀索引可以帮助我们减小索引项的。
不过，前缀索引有定的局限性，例如：
• orderby就无法使用前缀索引；
• 法把前缀索引用作覆盖索引；
### 3.2.2覆盖索引优化
覆盖索引是指SQL中query的所有字段，在索引B+Tree的叶子节点上都能找得到的那些索引，从二级索引中查询得到记录，不需要通过聚簇索引查询获得，可以避免[[#2.回表]]的操作。
假设我们只需要查询商品的名称、价格，有什么式可以避免回表呢?
我们可以建个联合索引，即「商品ID、名称、价格」作为个联合索引。如果索引中存在这些数据，查询将不会再次检索主键索引，从避免回表。
所以，使覆盖索引的好处就是，不需要查询出包含整记录的所有信息，也就减少了量的O操作。
### 3.2.3主键索引最好是自增的
我们在建表的时候，都会默认将主键索引设置为增的，具体为什么要这样做呢？什么好处?
InnoDB创建主键索引默认为聚簇索引，数据被存放在了B+Tree的叶节点上。也就是说，同个叶节点内的各个数据是按主键顺序存放的，因此，每当有条新的数据插时，数据库会根据主键将其插到对应的叶子节点中。
**如果我们使用自增主键**，那么每次插的新数据就会按**顺序**添加到当前索引节点的位置，不需要移动已有的数据，当页写满，就会动开辟个新页。因为每次插条新记录，都是追加操作，不需要重新移动数据，因此这种插入数据的法效率非常高。
**如果我们使非增主键**，由于每次插主键的索引值都是随机的，因此每次插新的数据时，就可能会插到现有数据页中间的某个位置，这将不得不移动其它数据来满足新数据的插入，甚至需要从一个页面复制数据到另外个页，我们通常将这种情况称为页分裂。页分裂还有可能会造成量的内存碎，导致索引结构不紧凑，从而影响查询效率。
举个例，假设某个数据页中的数据是1、3、5、9，且数据页满了，现在准备插个数据7，则需要把数据页分割为两个数据页：
![[Pasted image 20260506114439.png]]
出现页分裂时，需要将个页的记录移动到另外个页，性能会受到影响，同时页空间的利率下降，造成存储空间的浪费。
如果记录是顺序插的，例如插数据11，则只需开辟新的数据页，也就不会发页分裂：

因此，在使用InnoDB存储引擎时，如果没有特别的业务需求，建议使用自增字段作为主键。
另外，主键字段的度不要太，因为主键字段度越，意味着二级索引的叶子节点越、（二级索引的叶节点存放的数据是主键值），这样级索引占的空间也就越。

### 3.3索引失效的情况
索引失效通常发生在全球数据库优化器（Optimizer）认为“全表扫描比走索引更快”的时候。这往往是因为 SQL 语句的写法破坏了索引的**有序性**或**搜索逻辑**。

以下是常见的索引失效场景、原因分析及对应的解决方案：

---

#### 1. 违反最左前缀法则

- **情况**：建立了联合索引 `idx(a, b, c)`，但查询条件不包含最左侧列 `a`。
    
    - _错误示例_：`WHERE b = 2 AND c = 3`
        
- **原因**：联合索引是先按 `a` 排序，在 `a` 相同的情况下再按 `b` 排序。跳过 `a`，后面的 `b` 和 `c` 在全局来看是无序的，无法使用 B+Tree 快速定位。
    
- **解决方案**：
    
    - 查询条件中必须包含 `a`。
        
    - 或者根据实际查询频率，调整索引顺序或新增独立索引。
        

#### 2. 在索引列上使用函数或计算

- **情况**：对索引字段进行了函数处理或加减乘除。
    
    - _错误示例_：`WHERE ABS(id) = 10` 或 `WHERE id + 1 = 100`
        
- **原因**：索引树存储的是列的原始值，而不是计算后的值。经过函数计算后，新值在索引树中的位置是不可预知的。
    
- **解决方案**：
    
    - 将计算移到等号右侧：`WHERE id = 100 - 1`。
        
    - 如果是日期格式化，改用范围查询：`WHERE create_time >= '2023-01-01 00:00:00'`。
        

#### 3. 类型转换（隐式转换）

- **情况**：字段类型与查询值类型不匹配，最常见于**字符串字段查数字**。
    
    - _错误示例_：`phone` 字段是 `VARCHAR`，查询写成 `WHERE phone = 1380000`（未加引号）。
        
- **原因**：MySQL 会自动调用内置函数将字符串转为数字，这等同于在索引列上用了函数。
    
- **解决方案**：
    
    - 严格匹配类型，字符串必须加单引号：`WHERE phone = '1380000'`。
        

#### 4. 模糊查询以通配符开头

- **情况**：`LIKE` 查询使用了左模糊或全模糊。
    
    - _错误示例_：`WHERE name LIKE '%Zhang'` 或 `WHERE name LIKE '%Zhang%'`
        
- **原因**：B+Tree 索引是根据字符串的前缀来构建排序的。如果开头不确定，无法进行区间定位，只能全表扫描。
    
- **解决方案**：
    
    - 尽量使用右模糊：`LIKE 'Zhang%'`。
        
    - 如果业务必须全模糊，考虑使用全文索引（Full-text Index）或搜索引擎（如 Elasticsearch）。
        

#### 5. 范围查询导致后续列失效

- **情况**：在联合索引中，中间列使用了范围查询（`>`、`<`、`between`）。
    
    - _错误示例_：索引 `idx(status, age, name)`，查询 `WHERE status = 1 AND age > 20 AND name = 'Zhang'`。
        
- **原因**：一旦出现范围查询，该列之后的索引字段就无法再用于过滤，因为在范围结果集内，后面的字段是无序的。
    
- **解决方案**：
    
    - 设计索引时，尽量将范围查询的字段放在联合索引的**最后面**。
        

#### 6. 使用 `OR` 连接且部分列无索引

- **情况**：`WHERE a = 1 OR b = 2`，其中 `a` 有索引但 `b` 没有。
    
- **原因**：因为 `b` 必须全表扫描，所以即使 `a` 走了索引，最后还是要合并全表数据。优化器为了省事，直接全表扫描。
    
- **解决方案**：
    
    - 确保 `OR` 连接的每一个字段都建立了索引。
        

#### 7. 索引选择性太低（数据分布不均）

- **情况**：查询的字段只有少数几个取值（如：性别、状态值），且某个值占比极大。
    
    - _错误示例_：`WHERE status = 1`，而表中 90% 的数据 `status` 都是 1。
        
- **原因**：优化器通过“成本分析”发现，走索引后再回表的开销，比直接全表扫描还要大，于是放弃索引。
    
- **解决方案**：
    
    - 这种情况通常不需要索引。
        
    - 如果非要优化，可以考虑增加过滤条件，缩小结果集。
        
---

#### 总结表

| **失效场景**     | **根本原因** | **防御方案**         |
| ------------ | -------- | ---------------- |
| **违背最左匹配**   | 索引排序失效   | 遵循索引顺序或重写索引      |
| **索引列运算**    | 破坏原始值逻辑  | 计算移向等号右侧         |
| **隐式转换**     | 触发隐藏函数   | 严格匹配数据类型         |
| **左模糊查询**    | 无法定位起始点  | 仅使用右模糊 `prefix%` |
| **范围查询阻断**   | 后续字段无序   | 范围字段放联合索引末尾      |
| **OR 连接无索引** | 必须全表扫描   | 补齐所有相关字段索引       |

**排查建议**：在生产环境上线任何新 SQL 前，务必先执行 `EXPLAIN`。如果 `type` 显式为 `ALL` 或者 `index`（全索引扫描），就需要对照上述清单进行排查。
