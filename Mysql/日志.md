## 1.redo log（重做日志）
Redo log是MySQL中用于保证持久性的重要机制之一。它通过以下方式来保证持久性
1.Write-ahead logging(WAL):在事务提交之前，将事务所做的修改操作记录到redo log中，然后再将数据写入磁盘。这样即使在数据写入磁盘之前发生了宕机，系统可以通过redo log中的记录来恢复数据。
2.Redo log的顺序写入:redo log采用追加写入的方式，将redo日志记录追加到文件未尾，而不是随机写入。这样可以减少磁盘的随机I/0操作，提高写入性能。3.Checkpoint机制:MVSQL会定期将内存中的数据刷新到磁盘，同时将最新的LSN(Log SequenceNumber)记录到磁盘中，这个LSN可以确保redo log中的操作是按顺序执行的。在恢复数据时，系统会根据LSN来确定从哪个位置开始应用redo log。
## 2.undo log(回滚日志)
### 2.1 实现事务原子性（回滚）—— “后悔药”

这是 undo log 最基本的功能。事务具有原子性（Atomicity），意味着一个事务里的操作要么全成功，要么全失败。

- **逻辑日志**：undo log 记录的是**逻辑操作**。
    
    - 当你执行一条 `INSERT`，undo log 会记录一条对应的 `DELETE`。
        
    - 当你执行一条 `UPDATE`，undo log 会记录下数据被修改前的**旧值**。
        
- **回滚机制**：如果事务执行过程中报错（比如触发了 Check 约束）或者你手动执行了 `ROLLBACK`，InnoDB 就会去 undo log 里把刚才的操作“反向执行”一遍。
    

---

### 2.2 实现 MVCC（多版本并发控制）—— “时空穿梭机”

这是 undo log 比较高阶、也是最核心的作用，它让数据库能够实现**非阻塞读**。
你之前看到的那个 `roll_pointer` 指针，就像一条线，把存储在 undo log 里的不同版本的旧数据串联起来，形成了一个**版本链（Version Chain）**。
### 它是如何运作的？

1. **读写互不干扰**：当事务 A 正在修改某行数据（加了写锁），事务 B 过来读这行数据。
    
2. **构建 ReadView**：事务 B 会根据自己的“版本可见性规则”（ReadView），判断当前聚簇索引里的最新数据它能不能看。
    
3. **顺藤摸瓜**：如果最新数据是事务 A 还没提交的，事务 B 就顺着 `roll_pointer` 去 undo log 里找上一个版本，直到找到那个它“有权看到”的版本为止。
    

**结果**：即使数据正在被修改，读操作也不用等锁，而是直接去 undo log 里读“过去的数据”。

## 3. 两大作用的对比总结

| **作用**                 | **侧重点** | **解决的问题**              |
| ---------------------- | ------- | ---------------------- |
| **原子性 (Rollback)**     | 保护事务完整性 | 防止程序出错或崩溃导致数据只改了一半     |
| **MVCC (Consistency)** | 提升并发性能  | 让“读-写”操作不再冲突，实现一致性非阻塞读 |
