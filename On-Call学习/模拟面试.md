# 对话Agent
## Q1：切分策略
  
> “在你的智能 OnCall Agent 项目中，内部文档和排障 SOP 格式比较复杂，请问你的知识库切分策略（Chunking）是怎么设计的？为什么这么选型？底层具体如何落地存储和映射？”

**核心回答提纲：**
**1. 选型动机与痛点权衡**
在文档切分上，传统的固定滑动窗口（如硬性每 500 字截断）在 OnCall 场景有两大致命伤：
- **结构截断**：极易把完整的排障命令、YAML 配置或代码块拦腰截断，导致模型理解出错。
- **检索与生成的天然矛盾**：切块过大（>800 字），向量表征被稀释，检索命中率暴跌；切块过小（<200 字），命中率虽高，但喂给模型时严重缺乏前后文依赖与环境背景。
为此，我们采用了“Markdown 标题层级切分结合父子文档索引（Parent-Child Indexing）”的串联方案。
**2. 核心架构与落地四步流水线**
- **第一步：按 Markdown 标题提取父块（Parent Chunk）**
    - 利用结构感知解析器，按照文档原生语义树（H1/H2/H3）拆分为相对完整的排障逻辑段落（通常 600~1000 tokens）。
    - 提取整条面包屑路径作为元数据（如 `{"path": "支付服务/HikariCP报错/排障步骤"}`），并赋予全局唯一 `parent_id`。
- **第二步：在父块内部递归细切子块（Child Chunk）**
    - 在每个父块内部，使用代码感知的递归字符切分器进一步拆分为高密度小块（约 150~250 tokens，带 20 tokens 重叠）。
    - 切分逻辑严格避开代码块（` ``` `）和配置语法内部，且每个子块元数据中强绑定 `parent_id` 并继承父级路径信息。
- **第三步：计算向量（仅子块）**
    - 仅批量调用 Embedding 模型对 **Child Chunk** 文本计算向量，**Parent Chunk 不做向量化**，保证语义聚焦度与向量空间的区分度。
- **第四步：双层存储分离落地**
    - **向量数据库（如 Milvus / Qdrant）**：仅存储 Child Chunk 的向量、子块文本与携带的 `parent_id`。
    - **文档 / KV 存储（如 Redis / DocStore）**：以 `parent_id` 为 Key，只存储 Parent Chunk 完整的 Markdown 大文本。
**3. 检索与反查工作流（闭环）**
- **高精召回**：用户提问（如“Hikari 连接池慢查询排查命令”）先在向量库中精准匹配到得分最高的 Child Chunk。
- **回溯反查**：应用拿到命中的子块后，提取其 `parent_id`，在内存中做 Set 去重（防止同篇文档多个子块命中导致重复拉取），随后以 $O(1)$ 复杂度直接从 KV 库读取完整的 Parent 文本。
- **组装 Prompt**：最终喂给大模型的是信息完备、代码完整的 Parent Chunk，既保证了“搜得准”，又解决了“答得全”的问题。
# 运维Agent
## Q1：AIOps 选 Plan-Execute 而不是 ReAct？
- **ReAct 的核心硬伤（单步推演的局限性）**：
    
    - **容易“失焦”或死循环（Goal Drift / Dead Loop）**：ReAct 采用“Thought $\to$ Action $\to$ Observation”的单步贪心策略。排障链路一旦超过 4~5 步（如查指标 $\to$ 查日志 $\to$ 查配置 $\to$ 查慢 SQL $\to$ 交叉比对），模型极易受到工具单次异常输出的干扰，忘记原本的排障主线，或者在两个工具间来回无效重试。
        
    - **Token 浪费与延迟极高**：每执行一步都要将前面所有步骤的观察结果全量塞回 Context 让模型重新思考，随着步骤加深，推理延迟成倍暴增。
        
- **Plan-Execute 的优势（全局规划 + 确定性执行）**：
    
    - **解耦规划与执行**：
        
        - **Planner（规划器）**：结合告警上下文和知识库检索出的 SOP，一次性生成一份全局执行计划（结构化的 Task DAG 或步骤列表，如 `[Step1: 查CPU指标, Step2: 抓取ERROR日志, Step3: 查活跃线程]`）。
            
        - **Executor（执行器）**：严格按照步骤调用工具执行，不让模型在每一步胡思乱想。
            
    - **动态重规划（Re-plan）兜底**：仅当某一步执行发生预期外的重大分支异常时，才将执行摘要交给 Re-planner 修正后续计划，既保证了全局目标的收敛，又大幅降低了延迟与 Token 成本。
        

**2. MCP 工具调用的安全防御与熔断机制**

在后端工程设计中，我们采用了“防御性边界设计”来确保高危工具调用的绝对安全：

- **数据与权限隔离（防误删 / 慢查询防护）**：
    
    - **账号层强隔离**：通过 MCP 接入的 MySQL 工具，底层配置专属只读数据库账号（强制 `READ ONLY` 权限），物理级阻断一切 `INSERT/UPDATE/DELETE/DROP` 操作。
        
    - **SQL AST 静态语法解析校验**：在后端执行器层，工具接收到模型生成的 SQL 后，先通过 SQL Parser 进行抽象语法树解析。强制要求必须带有 `LIMIT` 阈值（默认限制上限 100 条），且命中全局无索引查询或全表扫描风险时直接拒绝执行。
        
    - **连接保护与超时**：设置独立的数据库只读连接池，执行超时阈值压低到 3 秒以内，防止慢 SQL 拖垮业务数据库。
        
- **高危动作的人工介入（Human-in-the-Loop）**：
    
    - 将工具分级为“只读观测类”和“变更操作类”。
        
    - 对于服务重启、配置修改、Kill 线程等写操作或破坏性工具，Agent **只能生成操作建议工单**，必须触发告警群的人工审批确认回调（Webhook/审批按钮），人工确认后才由后端执行，杜绝模型自主误操作。
        
- **死循环熔断与异常兜底**：
    
    - **Max Iterations 强截断**：在 Eino 图编排的循环控制器上设置最大执行步数（比如最大 6 步），一旦超过阈值触发熔断，降级为“生成当前已知信息摘要 + 转交人工 OnCall”。
        
    - **Tool Execution Timeout**：每个外部 MCP 工具调用都挂载 Go 的 `context.WithTimeout`（如日志检索限时 5 秒），超时直接返回超时错误码给 Planner，由重规划逻辑选择跳过或降级处理，避免协程悬挂。

## Q2 高危指令防范
> “在你的 AIOps 智能运维系统中，Agent 需要调用诸如数据库操作、服务日志排查、甚至是杀死进程（Kill Process）这类工具。大模型存在幻觉、越狱（Jailbreak）和注入风险，请问你们在工程架构上是如何防止 Agent 误执行高危破坏性命令的？具体如何实现安全防御与人工介入（Human-in-the-Loop）？”
**核心回答提纲：**

**1. 核心认知与安全防线定位**
- **安全认知**：绝对不能依赖大模型的 System Prompt 来做安全约束。大模型本质上只负责规划并产出结构化的调用参数（JSON），**没有直接操作基础设施的权限**，系统调用权完全收敛在后端的 Executor 代码中。
- **防御原则**：采取“后端硬编码拦截 + 静态语法解析 + 物理权限隔离”的三层纵深防御体系（Defense-in-Depth），杜绝因模型失控或越狱对生产环境造成不可逆破坏。

**2. 三层硬隔离防御落地**
- **第一道防线：Executor 调度层的 AOP 硬拦截（状态机挂起）**
    - **元数据分级**：在工具注册中心将工具标记为“只读观测类（SAFE）”和“高危变更类（HIGH_RISK）”。
    - **代码级硬拦截**：Go 代码中的调度执行器内置拦截中间件。当检测到调用的工具属于高危类别（如 `kill_mysql_process`、配置变更）时，Go 代码的 `if-else` 分支直接打断执行，**物理阻断对底层 API 的调用**。
    - **状态挂起与建单**：代码将当前执行状态（Snapshot/Checkpoint）序列化存入 Redis，生成唯一的审批单 ID，将任务状态置为 `PENDING_APPROVAL`，并向前端返回等待状态。
- **第二道防线：参数语义层的 AST 静态解析校验**
    - 针对执行自由查询的工具（如 `run_mysql_query`），大模型可能在参数中注入恶意语句。
    - **语法树解析拦截**：后端在将 SQL 下发给数据库前，先通过 SQL Parser（如 `tidb/parser`）解析为抽象语法树（AST）。
    - **硬校验规则**：如果语法树根节点不是 `*ast.SelectStmt`（出现 `UPDATE`、`DELETE`、`DROP` 等 DDL/DML 操作），代码直接报错截断；同时强制在 AST 尾部追加 `LIMIT 100`，防止无限制全表扫描拖垮数据库。
- **第三道防线：基础设施与账号物理权限隔离**
    - **数据库只读账号**：Agent 主服务配置的 MySQL 连接账号在数据库层面被 DBA 赋予强隔离的全局 `READ ONLY` 权限。即使代码层全部失效，数据库引擎层也会直接以 `Access denied` 拒绝破坏性写入。
    - **特权凭证物理分离**：具备 Kill 进程或重启服务特权的凭证，**完全不配置在 Agent 服务中**，而是托管在独立的运维审批中心。只有当人工审批回调合法时，才由外部审批中心代为调用。
    
**3. 人工介入（Human-in-the-Loop）闭环流程**
- **群卡片推送**：任务挂起后，系统向飞书/企业微信值班群推送交互式 Webhook 卡片，明确呈现告警类型、大模型建议操作的命令、风险等级及影响评估，附带 `[ 确认执行 ]` 与 `[ 拒绝 / 转人工 ]` 按钮。
- **验签与鉴权**：值班工程师点击审批后，回调接口严格校验操作人权限并落库操作审计日志。
- **异步唤醒（Resume）**：验证通过后，审批中心以特权凭证调用底层动作，并将真实执行结果回填给原挂起的任务快照，唤醒 Eino 工作流继续向下复查指标并生成排障总结。
