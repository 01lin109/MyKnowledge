### 一、 为什么大厂一定要做 API 和 BIZ 的分离？

在规范的企业开发中，一个服务如果想被别人调用，绝对不允许直接依赖对方的整个项目源码。大厂之所以统一采用你提到的 `-api` 和 `-biz` 拆分，核心原因有三个：

- **保护核心源码与安全性：** 服务提供方（比如 `question-service-biz`）里包含了具体的 SQL 语句、核心业务算法、核心机密逻辑。对外公开的只有 `question-service-api`（只包含接口、DTO、Fallback），消费方只能看到接口定义，看不到具体实现。
    
- **极致的轻量化：** `-api` 模块通常极其干净，不引入任何数据库驱动（MyBatis/Hibernate）、缓存（Redis）、消息队列（MQ）等大依赖。消费方引入它时，绝对不会把一堆乱七八糟的间接依赖带进自己的项目里，保持了消费方自身依赖的纯净。
    
- **严谨的版本控制：** API 模块会作为一个独立的“二方库”，通过 CI/CD 工具自动打包并发布到公司内部的私服仓库（如 Nexus）。每次接口有变动，只升级 API 的版本号（如 `1.0.0-SNAPSHOT` -> `1.0.1-RELEASE`），消费方按需升级。
    

### 二、 大厂在“按需引入”时的研发标准

正如你刚才准确纠正的那样，大厂在 Maven 依赖管理上控制得极其严格。

1. **架构师的“依赖洁癖”：** 大厂的架构组通常会定期使用工具（如静态代码分析、Maven 依赖检查）去扫描各团队的 `pom.xml`。如果发现某个服务引入了根本没有使用的第三方 `-api` 包，或者有人试图搞“全量聚合包”，通常会在 Code Review 阶段被直接驳回，甚至触发架构报警。
    
2. **避免分布式单体：** 如果像我之前脑补的那样把所有 API 绑在一起，一旦某个边缘服务升级导致大包冲突，整个公司的发布流水线都会瘫痪。按需引入确保了“**微服务各自独立生命周期**”的底线。
    

### 三、 这种方案在大厂落地时的衍生演进

虽然这是标准方案，但大厂在庞大的业务体量下，针对这种方案也做了一些针对性的优化和变通：

#### 1. 专门的网关层（BFF）代替后端微服务做大聚合

在大厂里，如果前端（App/Web）需要一个页面，这个页面同时需要 A、B、C 三个微服务的数据，后端微服务之间通常不会互相引入对方的 API 去做复杂的拼装。 大厂更倾向于引入 **BFF（Backend For Frontend，服务于前端的后端）** 概念。通常会有一个专门的网关层或者聚合服务层（通常用 Go、Node.js 或轻量级 Java 实现），由它去**按需引入** A、B、C 的 API，并在这一层把数据聚合成一个大 JSON 丢给前端。这让底层的微服务可以专注于自己的领域，更加纯粹。

#### 2. 多语言生态下的变化（如 Go / Rust / Python）

你提到的基于 Maven 坐标和 Feign 注解的方案，是 **Java 生态（Spring Cloud）** 的绝对标准。 不过在很多大厂（比如字节跳动、腾讯、美团的部分团队），内部流行多语言开发（Java 和 Go 混用）。在这种场景下，大厂会逐渐把 Java 的 Feign 方案升级为 **gRPC / Thrift 等 RPC 框架**。

- 这时候，服务提供方不再提供 Maven 的 `-api.jar` 了。
    
- 而是提供一个 `.proto` 或 `.thrift` 的**接口定义文件**。
    
- 消费方（不管是 Java 还是 Go）拿到这个文件，用工具自动生成自己语言的客户端代码，同样保持了**按需引入**和**接口分离**的核心思想。
