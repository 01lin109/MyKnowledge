# 方案一：基于 Feign 接口的“多合一公用 SDK 抽象” (最常见)

很多互联网大厂为了不让各个微服务团队重复写 Feign 接口，会专门搞一个公共的 `api-dependency` 模块。

### 1. 架构师是怎么封装的？

1. **定义公共公共 API 模块**：服务 B、服务 C、服务 D 在各自开发时，都会把对外的接口抽离出来，写在一个公共的子模块里（比如 `service-b-api`）。
    
2. **大聚合（你看到的 Domain）**：架构师写了一个公共的全局 SDK（比如叫 `CompanyDomainContext` 或者一个大类），这个类里把服务 B、服务 C、服务 D 的 Feign 客户端**全部组合（Inject）或者通过继承连带了进去**。
    
3. **自动装配**：利用 Spring Boot 的自动装配原理，只要服务 A 的 `pom.xml` 引入了这个大 Domain 的 Starter，这个大 Domain 就会在服务 A 启动时，自动把所有其他服务的 Feign 代理对象全部初始化好。
    

### 2. 调用时的透明路由

对你而言，你以为你只是调用了一个本地的 `domain` 对象的方法。但实际上，当你点下那个方法的一瞬间，底层触发的是：

> **你的调用 -> 大 Domain 对象 -> 具体的 FeignClient 动态代理 -> 拦截器包装请求 -> Ribbon/LoadBalancer 负载均衡 -> Nacos 找到对应服务 IP -> 网络发出 HTTP/RPC 请求。**

整个底层的微服务网络通信，全被这个大 Domain 给“屏蔽”掉了，让你产生了“在写分布式系统，却像在写单体应用”的爽快感。

能够得到你的印证，说明你当时在实习期间确实非常细心，不仅完成了业务代码，还观察到了公司底层架构的流转模式！这种 **“API 接口打成 Jar 包对外暴露 + 消费端大聚合”** 的模式，是当前国内互联网大厂（包括阿里、美团等）最推崇、最标准的微服务协作规范。

既然你们公司采用的是这种高标准的**方案一（API 模块化剥离方案）**，那在木仓科技的面试中，这绝对是一个含金量极高的谈资。

为了让你在面试中能说得更专业、更滴水不漏，我帮你把这个方案的**内部协作细节**和**必考的面试衍生题**做个深度复盘。

## 一、 方案一的完整协作闭环（标准的微服务治理流程）

在实际开发中，你们的团队协作流程大概是这样的：

1. **服务提供方（比如题库微服务 `question-service`）**：
    
    - 团队负责人会把项目拆成两个 Maven 模块：`question-service-biz`（核心业务实现，包含 Controller、Service、Mapper，**不对外开放源码**）和 `question-service-api`（**对外公开的轻量级 Jar 包**）。
        
    - 这个 `-api` 模块里非常干净，只有三样东西：**Feign 接口定义**（带 `@FeignClient` 注解）、**DTO 传输对象**（用户入参和出参的实体类）、**错误降级兜底类（Fallback）**。
        
2. **大聚合 Domain（也就是你引入的那个核心组件）**：
    
    - 公司的公共架构组会维护一个全局的 SDK 或者是核心 `domain-starter`。这个公共组件的 `pom.xml` 里，会把全公司所有微服务的 `-api` 依赖全部 `dependency` 进来。
        
    - 利用 Spring Boot 的自动装配，它把这些 Feign 接口全部扫描并注册到 IOC 容器中，最终聚合成你看到的那个可以直接顺着点出来的 `domain` 对象。
        
3. **服务消费方（比如你的当前服务 A）**：
    
    - 你只需要在 `pom.xml` 里引入这个 `domain-starter`，你在写代码时，就能像调用本地方法一样，直接顺着点出其他服务的 API。

## 二、 面试官听完接下来的“夺命连环追问”预测

当你在面试中自信地聊出这个方案后，大厂的面试官为了试探你是不是真的懂，大概率会抛出以下两个**微服务核心技术问题**。你可以直接背下这些标准答案：

### 追问 1：既然所有微服务的 API 都打包在一个大 Domain 里，如果服务 B 的接口升级了（比如加了一个字段），服务 A 必须要重启或者重新打包吗？

- **满分回答**：
    
    > “这取决于接口变更的类型。因为我们使用的是基于 **HTTP/JSON 序列化（Feign）** 的通信机制，具有很强的兼容性。
    > 
    > - 如果服务 B 只是**新增了接口方法**，或者在 DTO 中**新增了字段**，服务 A 如果暂时不需要这个新功能，是**完全不需要重新打包或重启**的。因为基于 Jackson 的反序列化默认会忽略未知的属性，不会报错。
    >     
    > - 但如果服务 B 做了**破坏性变更（比如删除了某个旧接口，或者修改了原有字段的类型）**，那么整个大 Domain 的版本就需要升级，服务 A 也必须更新 Maven 依赖版本并重新发布，否则在线上运行时会抛出 `MethodNotFound` 或者反序列化异常。这也是为什么我们团队内部严格规定：**微服务接口只能向前兼容，严禁做破坏性修改**。”
    >     
    

### 追问 2：这种大聚合方案虽然爽，但如果遇到了“网络抖动”或者“下游服务挂了”，你们是怎么做服务熔断和降级的？

- **满分回答**：
    
    > “架构师在封装这个 `-api` 模块时，就已经考虑到了这一点。我们在定义 `@FeignClient` 注解时，都会配置 `fallback` 或者 `fallbackFactory` 属性。
    > 
    > 比如调用‘用户 VIP 状态服务’，如果对方服务响应超时或者直接挂了，底层的 **Sentinel / Resilience4j** 组件会立刻触发熔断，并自动调用我们在 `-api` 包里写好的 `UserRpcFallback` 兜底类。
    > 
    > 在兜底方法里，我们会返回一个安全的默认值（例如：默认认为该用户是普通用户，或者返回‘系统繁忙请稍后再试’），确保当前服务 A 的主流程不会因为下游的崩溃而一起瘫痪，从而实现了**服务的隔离与容错**。”

## 2.3Arthas使用
简单来说，**Arthas（阿尔萨斯）** 是阿里巴巴开源的一款 **Java 线上诊断工具**。

你可以把它想象成医院里的“便携式 B 超机”或“听诊器”。当线上的 Java 程序出现问题（比如卡死、变慢、报错）时，你不需要停掉服务，也不需要重新加日志、打包、部署，直接启动 Arthas 就能“无痛”地连进正在运行的程序里，看看里面到底发生了什么。

它最强大的地方在于：**诊断完全是动态的，不需要重启服务。**

### 哪些场景最适合用它？

开发和运维过程中，下面这几个让人头疼的场景，都是 Arthas 的拿手好戏：

- **“代码到底执行没有？”**：你刚发布了新版本，但不知道线上的包到底是不是最新的，可以用它直接反编译查看线上运行的字节码。
    
- **“怎么在线上排查报错？”**：某个接口报错了，但日志没打全。你可以用它来动态拦截这个方法，观察入参、出参和抛出的异常。
    
- **“为什么 CPU 飙到了 100%？”**：一键生成 CPU 火焰图，或者直接定位到是哪个线程、哪几行代码在疯狂消耗 CPU。
    
- **“是不是死锁了？”**：一键检测线程死锁，直接揪出互相等待的线程。
    
- **“这个方法怎么这么慢？”**：追踪一个请求的方法调用链路，精确计算出每一步耗时多少毫秒，直接抓出“性能杀手”。
    

### 核心常用命令

Arthas 采用的是命令行交互界面，虽然没有炫酷的 UI，但命令非常实用。这里列几个最常用的核心命令：

|**命令**|**它的作用（大白话解释）**|
|---|---|
|**`dashboard`**|**查看大盘**。展示当前系统的整体状态，包括线程、内存（JVM 各个区）、操作系统信息。|
|**`thread`**|**看线程**。比如 `thread -n 3` 可以直接打印出当前最忙的 3 个线程的堆栈信息，找 CPU 飙高立竿见影。|
|**`jad`**|**反编译**。直接把 JVM 里加载的类反编译成源码，用来核对线上代码版本是不是对的。|
|**`watch`**|**监视器**。动态观察某个方法的入参、出参、返回值、抛出的异常，甚至还能按条件过滤（比如只看耗时大于 500ms 的请求）。|
|**`trace`**|**链路追踪**。追踪一个方法内部所有子方法的调用耗时，排查性能瓶颈（比如看是哪句 SQL 执行慢了）。|
|**`sc` / `sm`**|**查类/查方法**。看看这个类到底是从哪个 jar 包里加载出来的，解决 `ClassNotFoundException` 或类冲突。|
