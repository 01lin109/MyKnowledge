# ⚔️ 第一战：学会给 AI 戴上“紧箍咒”（Harness 实战）

得物文章里说了，全栈 AI 开发最容易踩的坑，就是让 AI 从零开始、天马行空地写代码，这样写出来的叫“外星代码”。

### 🎯 核心心法

**永远不要说**：“帮我写一个结束语管理的 CRUD 接口。” **必须要学会说**：“帮我写一个结束语功能，**参考我们项目里现有的场景欢迎语功能**。数据结构、分层方式、命名风格必须保持一致。”

### 🛠️ 怎么在你的提示词（Prompt）里落地？

当你用 Cursor 或者 Claude 时，可以用这个**通用黄金提示词模板**：

> “我现在需要开发一个 `[新功能名称]`。
> 
> 1. 请你使用 **Harness（约束）思维**，死死参照我们项目中现有的 `[已有老功能名称]` 模块。
>     
> 2. 后端修改参考：`@[指向你的Controller或Service文件]`
>     
> 3. 前端修改参考：`@[指向你的前端组件或Table文件]`
>     
> 4. 无论是包结构、命名规范、还是数据分层，都要照猫画虎，不许自己发明创造。”
>

### 我的理解：
我觉得这个方案首先更适用于在现有项目工程基础上进行迭代开发或者快速开发有共通点的需求，并不适合于开辟一个全新的项目。与此同时我觉得，一家公司的开发规范如比如变量命名，或者之前我在实习中遇到的必须用javadocx注释等等这样的规范都是可以形成一篇文档的，就比如阿里巴巴的开发手册里面就有很多开发规范也有很多开发人员总结的经验，这些如果能形成一个skill是不是比直接在promot中显式说明更加高效而且方便呢，当然这些都是针对开发规范上来说的，如果是遵从或者复用其他业务的相似逻辑那肯定智能在promot中去实现了因为不可能每一个业务都写一个skill。
## 1. 概念校准与纠偏

### 📌 关于“只适用于既有项目迭代，不适合开辟全新项目”

- **指正**：**这并非绝对。** 实际上，当你用 AI 开辟一个**全新的项目**时，Harness 思维同样是最高效的解法。
    
- **原因**：即使是全新项目，你通常也会有可参考的“骨架”（脚手架）。比如公司内部通用的底层标准配置（Spring Boot + MyBatis-Plus + Nginx 模版），或者你之前自己写过的一个完美的开源脚手架。
    
- **全新项目的 Harness 玩法**：“请参照这个开源优秀的脚手架（提供代码结构），按照同样的架构、异常处理机制、统一返回对象（Result）去帮我构建一个全新的微服务。”
    
- **结论**：**Harness 约束的本质是寻找“参照物”，这个参照物可以跨项目存在。** ### 📌 关于“开发规范形成 Skill（或 System Prompt），比写在 Chat Prompt 里更高效”
    
- **指正**：**完全正确，你的直觉非常敏锐。** 阿里巴巴开发手册这类“放之四海而皆准”的规范，或者公司内部的 Javadoc 注释规范，如果每次都在聊天对话框（Chat Prompt）里手写，既低效又容易遗漏。
    
- **更高级的玩法**：在大模型开发或使用（如 Cursor / Claude Code）中，有专门的机制来承载这类规范：
    
    1. **`.cursorrules` / `.clauderc` 文件**：直接放在项目根目录，里面写满“必须使用 Javadoc、变量采用驼峰命名、禁止使用魔法值”等静态规范。AI 每次只要在这个项目里写代码，就会**自动、强制**遵循，不需要你在 Prompt 里反复提。
        
    2. **平台侧的 System Prompt / Custom Instructions**：把通用规范固化到 AI 的系统设定中。
        
- **结论**：**静态开发规范 -> 沉淀为 Skill/规则文件；动态业务逻辑 -> 在 Chat Prompt 中显式引用。** 这两者的结合才是大厂落地的最终形态。
    

## 2. OnCallAgent 项目中的落地实践

你的 **OnCallAgent** 核心价值是解决用户使用平台时的技术支持/运维响应（基于 RAG 的大模型应用）。这个项目自身在开发迭代时，可以通过以下几个具体场景狠狠实践 **Harness 思维**：

### 🛠️ 实践场景 A：RAG 工具类/接口的横向克隆

- **背景**：你的知识库中一定有不同的向量数据检索源或解析器（比如读取文档用 DocxParser，或者调用不同的 Embedding 模型）。
    
- **实战应用**：当你需要新增一个 `MarkdownParser`（Markdown解析器）时，千万不要让 AI 从零去写这个工具类。
    
- **Harness 做法**：
    
    > “请参照现有的 `DocxParser.java` 类的架构（包括它的自定义异常处理、日志记录规范以及重试机制），利用 Harness 思维帮我实现一个 `MarkdownParser.java`。不许自己发明新的返回结构，严格保持风格一致。”
    

### 🛠️ 实践场景 B：AI Agent 状态/多轮对话管理的“照猫画虎”

- **背景**：OnCallAgent 会涉及复杂的提示词控制和多轮对话状态维护，可能用了某些特定的框架或自定义的 Context 类。
    
- **实战应用**：假设你之前写好了 `ITSupportAgent`（IT支持智能体）的流式返回（Streaming）和上下文截断逻辑。现在需要新增一个 `HrSupportAgent`（针对平台内HR报销等指引）。
    
- **Harness 做法**：
    
    > “请帮我编写 `HrSupportAgent` 的业务核心层。不要放飞自我，去读取 `ITSupportAgent` 的代码，参考它是如何管理 `HistoryContext`、如何通过流式接口返回给前端、以及如何做用户权限拦截的，将其中的业务关键词替换，确保底层架构无缝克密。”
    

### 🛠️ 实践场景 C：将 OnCallAgent 本身作为“Harness 分发中心”

- **概念升级**：既然你的项目是 OnCallAgent（一个全天候在客群里解决用户问题的智能助手），你完全可以在它的底层 RAG 知识库里，**录入你们团队的代码开发规范规范说明文档**。
    
- **实战应用**：当团队里的其他同学向 OnCallAgent 提问“我想写一个数据库批量更新操作”时，OnCallAgent 不仅会从阿里手册里找答案，更会通过 RAG 召回项目里最优秀、最标准的那个 `BatchUpdateMapper.xml` 样例代码块，作为 **Harness（约束参照物）** 吐给同学，并告诉他：“按照这个标准去写。”

## 我的问题：
这是一个非常具有共鸣感且极度切中一线研发痛点的问题。作为新入职的员工或实习生，面对动辄几十万行、几百个类的企业级项目，“不知道该抄谁”是普遍面临的第一大难关。

你提到的两种思路——**“让 AI 盲目扫描全盘”**和**“幻想不给约束让 AI 全局盲搜”**，在实际工程中确实由于 Token 限制、上下文丢失、幻觉以及极高的成本而无法落地。

既然我们要在第一关做到极致，针对新入职、对项目不熟悉的场景，结合 AI 时代最前沿的研发工具（如 Cursor、Claude Code 等的最新能力），有一套大厂一线的“逆向推导找 Harness（约束）”通关秘籍。

## 🛠️ 第一招：从“物理入口”逆向抓藤蔓（最务实、最精准）

你可能不了解后端的 Service、Mapper 都在哪里，但**新需求永远有明确的“物理入口”**：

1. **前端入口**：产品经理让你在某个既有页面的 Tab 下面加个按钮。
    
2. **后端入口**：产品经理给你分配的需求，在路由上一定能推导出大致的 URL 规范（比如大厂通常按照 `/api/v1/业务域/功能` 命名）。
    

### 🧑‍💻 你的实操动作：

不要让 AI 去扫描整个项目。你只需要利用 Cursor 的全局搜索（`Ctrl+Shift+F`）或 Claude Code 的 `grep` 查找功能，先定位**离新需求最近的那一处前端组件代码或后端的 Controller 路由定义**。

定位到之后，把它（比如 `FeatureTable.tsx`）加入 AI 的上下文（通过 `@` 符号），然后用这个**逆向寻找 Prompt**：

> “我是一个新入职的开发，需要实现需求 `[简单描述新需求]`。
> 
> 1. 目前我只找到了离新需求最近的代码入口是 `@FeatureTable.tsx`。
>     
> 2. 请你利用静态分析和你的索引能力，帮我往上游和下游看：**在当前项目里，还有哪些组件或页面在调用它、或者它的周边有哪些功能非常相近的‘兄弟类’和‘相似方法’？**
>     
> 3. 请帮我找出 1-2 个最适合作为我本次开发 **Harness（模仿对象）** 的老接口和老代码路径。”
>     

**为什么有效？** AI 最擅长做的事情就是**局部依赖树分析（AST）**。你给了它一个锚点，它顺着这个藤蔓去摸周边的瓜，准确率会达到 90% 以上，根本不需要扫描整个全局。

## 🛠️ 第二招：利用最新 AI 编程工具的“Agent 探索（Explore）”能力

你之前尝试的“给出一个笼统概念再细分”，吃力且耗时的原因在于：**AI 输出的是没有针对性的通用概念**。

现在的尖端 AI 工具（如最新版的 Cursor Agent 模式，或 Claude Code 的命令行 Agent），具备主动的 **“探查（Explore / Research）”** 能力。你可以把“寻找模仿对象”的任务，以**极低的 Token 成本**委托给它：

### 🧑‍💻 你的实操动作：

在工具中切换到 Agent 模式（例如 Cursor Composer 的 Agent 模式，或者直接使用 Claude Code 命令行），敲入以下指令：

Bash

```
# 这是一条命令，让 AI 自主去探索，而不是让你去肉眼看代码
openspec-explore "我需要做一个结束语管理的 CRUD 接口。请你帮我调研整个 codebase 索引。看看项目里有没有任何已经实现的、带有很多配置属性的、极为相似的管理接口（比如某种欢迎语、通知管理等）。"
```

- **AI 会怎么做**：它不会傻傻地把所有代码读一遍。它在底层会先运行 `grep` 或语义索引搜索一些核心关键词（如 `Management`、`List`、`Crud`、`Save`），找到几个可疑的文件后，它会自动执行“读文件”命令去扫一眼类名。
    
- **结果**：它会像一个老员工一样，经过几轮自动的查阅后，最终给你汇报：“经过我的探查，我发现 `src/backend/service/GreetingService.java` 的逻辑和你的新需求高度契合，它实现了分页、批量排序和状态清理，建议将它作为 Harness。”


# ⚔️ 第二战：掌控“先计划、后动手”的节奏（SDD 文档编写）
## 2.1生成SDD文档提示词解析：
以下是经过实践验证的全栈 SDD 生成提示词模板：
每一个需求对应一套SDD文档；

```
这是一个前后端全栈开发工作区，需要你设计技术接口方案，同时开发前后端项目；
首先你需要 cd 到对应前后端应用目录中，创建 sdd 文件；
所以你需要生成两份 sdd 文档，之后我会启动两个 agent 分别实现；、
在生成之前，如果你需要确认某些细节，你应当先确认后生成 sdd 文档。

前端应用：service-frontend
/sdd-propose  feature/your-feature-name
前端修改入口参考：@FeatureTable/index.tsx:53-58 @columns/index.tsx

后端应用：service-backend
/sdd-propose  feature/your-feature-name
后端修改入口参考接口：/api/v1/feature/list

需求内容：（附上需求文档或描述，并提供前后端需求点清单）

```
**关键要素解读：**

|                     |                                |
| ------------------- | ------------------------------ |
| **要素**              | **作用**                         |
| "cd 到对应目录"          | 让 AI 在正确的项目目录下创建 SDD 文件，避免混放   |
| "生成两份 SDD 文档"       | 明确前后端各一份，防止 AI 写成一份            |
| "之后启动两个 agent 分别实现" | 暗示后续多 Agent 并行开发，让 AI 提前做好接口对齐 |
| "先确认后生成"            | 让 AI 遇到不确定的地方先问你，避免生成错误的 SDD   |
| "@文件路径"             | 利用 Cursor 的 @ 引用，让 AI 读取参考文件   |

**后端功能点（含接口清单）**

后端功能由 AI 根据前端需求描述自主设计数据表和接口。以下是 AI 在生成 SDD 前需要明确的关键设计问题（这些问题应在提示词中列出，让 AI 先回答再生成）。


**接口清单：**列表接口（支持分页，回显数据直接嵌入列表响应，无需单独回显接口）、新增接口、编辑接口（复用新增逻辑，根据 id 更新）、删除接口（逻辑删除，修改删除状态字段）、排序接口（批量更新，需考虑高效实现方案）。  

**字段设计：**结束语话术内容（数组类型）、结束语描述（文本）、优先级 / 序号（小整型）、更新人（字符串）、更新时间（时间戳）。

**需要 AI 在 SDD 中明确回答的设计问题：**

- 主键设计：如何设计主键字段？前端发起编辑、删除时需要传递该字段。
    
- 优先级自增逻辑：优先级应基于当前数据条数自增，无需前端传递，由后端自动处理。
    
- 排序如何高效更新：批量排序时如何设计接口，避免 N 次单条更新？
    
- 嵌套对象如何建表：参考已有的"场景欢迎语"接口，入参中存在嵌套子对象（如下方参考结构）。此类子对象应拆分到多张表，还是序列化为 JSON 字段存单张表？
    
- isNextDay 字段含义：次日逻辑的具体含义是什么？前端时段选择器中"次日"勾选状态如何映射到该字段？
    
- 列表回显设计：列表接口需要返回完整的回显数据（供编辑弹窗回填），无需单独提供详情接口。
    

**为什么要把这份清单放进提示词？**

这份清单做了两件重要的事：**前端侧**给 AI 完整的 UI 细节，让 AI 知道组件状态、字段约束、交互逻辑，避免它做"最简实现"。**后端侧**把模糊的设计问题提前暴露，让 AI 在写 SDD 之前先回答这些问题——这正是 Harness 思维的体现：让 AI 参照已有实现（如"欢迎语"）来解决"结束语"，而不是凭空设计。

**SDD 文档产出**

一次完整的全栈 SDD 生成，会产出以下文档：

**前端 SDD：**

- proposal.md — 需求提案，描述前端要做什么。
    
- spec.md — 技术规格，组件设计、接口调用、状态管理。
    
- tasks.md — 任务拆分，每个 task 对应一个可执行的代码变更。
    

**后端 SDD：**

- proposal.md — 需求提案，描述后端要做什么。
    
- spec.md — 技术规格，接口设计、数据库设计、分层架构。
    
- design.md — 详细设计，类图、字段映射、SQL。
    
- tasks.md — 任务拆分。

## 2.3**SDD 指令使用说明**

**典型工作流示例** 

**入门引导：**

1. openspec-onboard（首次，不熟悉才走，引导完整步骤）；
    
2. openspec-continue-change（提示你下一步要干嘛）；
    
3. openspec-ff-change（快进）。
    

**场景 A：初次开发**

1. openspec-explore（调研，脑暴）；
    
2. openspec-propose "..."（生成设计）；
    
3. openspec-apply-change（写代码）；
    
4. openspec-verify-change（自测，校验代码与 SDD 文档是否对应）；
    
5. openspec-archive-change（收尾，归档）。
    

**场景 B：二次开发，修改迭代已有功能**

1. openspec-explore（定位旧代码/旧 spec）；
    
2. openspec-propose "修改..."（生成变更 Spec）；
    
3. openspec-apply-change（应用修改）；
    
4. openspec-verify-change（验证回归）；
    
5. openspec-archive-change（归档）。
    

**场景 C：二次修改，需求变更**

1. openspec-explore（调研，脑暴）；
    
2. openspec-propose "..."（生成设计）；
    
3. openspec-apply-change（写代码）；
    
4. 发现有问题就用 openspec-explore 修改提案；
    
5. openspec-explore "需求变更：xxx"（二次脑暴）；
    
6. openspec-propose "根据探索结果修改提案"；
    
7. openspec-apply-change（执行提案中变更内容）；
    
8. 【可选】openspec-verify-change（验证是否有未完成任务）；
    
9. openspec-archive-change（归档）。
    

**场景 D：季度大清理**

1. openspec-bulk-archive-change --before 2023-12-31（批量归档）。
## 四大核心实战场景连招（如何玩转这套手柄）

看懂了基础键，我们把它们串联到你日常实习或写项目会遇到的真实场景中：

### 🎬 场景 A：从零初次开发一个新功能

这是最标准的黄金流水线：

1. **`openspec-explore`**：让 AI 去调研项目，看看要在哪个页面、哪个接口照猫画虎。
    
2. **`openspec-propose "..."`**：输出技术方案草案，人类在 md 文档里卡点 Review。
    
3. **`openspec-apply-change`**：人类说“OK没问题，动手吧”，AI 唰唰唰生成前端页面和后端业务。
    
4. **`openspec-verify-change`**：检查 AI 的任务清单是否 100% 执行完毕。
    
5. **`openspec-archive-change`**：完工，归档方案，提交代码。
    

### 🎬 场景 B：二次开发，去改别人的旧功能

实习中最痛苦的就是改前人留下来的代码。

1. **`openspec-explore`**：直接让 AI 顺着路由去把前人留下的旧代码以及旧的 spec 技术规格书找出来。
    
2. **`openspec-propose "修改..."`**：不要重写，让 AI 只输出一份“变更说明书”（只改动变化的字段）。
    
3. 后面同样是 **`apply`（改代码）** -> **`verify`（验证回归，防止把老功能改挂）** -> **`archive`（归档）**。
    

### 🎬 场景 C：做着做着，产品经理突然改需求了

这是研发常态。代码写到一半，PRD 变了，传统模式下 AI 的上下文就全乱了，但有这套指令就会非常丝滑：

1. 本来流程走到了第3步 `apply` 写代码。
    
2. 突然需求变了，立刻倒车，重新敲个 **`openspec-explore "需求变更：xxx"`** 开启二次脑暴。
    
3. 接着敲 **`openspec-propose "根据探索结果修改提案"`**，AI 会极其听话地只去修改那 7 份 md 文档里的接口定义。
    
4. 人类再次 Review 完变化的文档后，最后敲 **`openspec-apply-change`**，AI 会自动把之前写错的代码擦掉，重新按照新方案生成代码。这就极大地避免了代码越改越乱的灾难。
    

### 🎬 场景 D：季度大清理

- **`openspec-bulk-archive-change --before 2023-12-31`**：项目做久了，历史的 SDD 文档（md文件）积攒太多会污染工作区，这个就是“一键清理历史草稿箱”的批量归档工具。

<font color="#c0504d">总的来说，上述相对来说还是比较繁琐，保持最简使用：想（openspec-propose）、做（openspec-apply-change）、收（openspec-archive-change）即可。</font>


# ⚔️ 第三战：前后端并行不阻塞（分阶段验证法）

代码生成完或者正在生成时，最忌讳的就是把前后端环境绑在一起调试，网络调不通、环境起不来，时间全浪费了。得物团队推荐了**三阶段分离验证策略**：

- **阶段 1：前端 Mock 跑通交互**
    
    - **怎么做**：让前端 Agent 根据 `spec.md` 里的接口结构，直接写一套本地的 Mock 数据。
        
    - **目的**：在不依赖后端服务的情况下，先把页面的点击、弹窗、拖拽排序等 UI 逻辑和边界场景（比如列表为空、字符串超长）全部自测通过。
        
- **阶段 2：后端独立编译验证**
    
    - **怎么做**：后端代码写完，**不需要在本地启动整个庞大的微服务/服务网关**。直接在后端项目根目录下，敲入编译命令（如 Java 的 `mvn clean compile`）。
        
    - **目的**：只要编译能通过，说明你的依赖没问题、语法没问题、接口契约里的类型和返回值全都匹配上了。这能帮你过滤掉 90% 的低级错误。
        
- **阶段 3：真实联调与抓“内鬼”**
    
    - **怎么做**：后端部署到开发/测试环境，前端配置代理指向该环境进行端到端串联。
        
    - **抓内鬼（隐性功能陷阱）**：重点检查 AI 在“抄”既有功能时，有没有自作主张地塞进去一些你没要求的隐藏代码（例如自动清空某些状态、自增某些序号等）。


# SDD实战：

## 🛠️ 核心实战：SDD 提示词三部曲

请你在你的 AI 编程工具中，**直接复制并发送**以下三个阶段的提示词。

### 第一步：想（Propose）—— 逼 AI 吐出 7 份全栈设计文档

你在 IDE 的 Chat 框里，使用键盘 `@` 符号把你想让它参考的前端和后端文件挂载上，然后发送这段提示词：

Plaintext

```
这是一个前后端全栈开发工作区，我需要基于 Harness 思维和 SDD 范式开发一个新需求：【快捷回复模板管理功能】。

首先，请你【绝对不要直接写业务代码】，你需要先 cd 到对应的前后端应用目录中，创建 sdd-propose 文件夹，并在其中生成两份独立的 SDD 技术设计文档。之后我会启动两个 Agent 分别去执行。

【参考的 Harness 约束】：
前端修改入口与组件风格参考：@UserTagTable.tsx (请参考它的Tab切换、表格渲染与 columns 定义)
后端修改接口与分层风格参考：@UserTagController.java (请参考它的统一返回对象 Result、Service分层与PO定义)

【新需求点清单】：
1. 前端：新增一个快捷回复模板的 Table 页面，包含字段：模板名称、话术内容、优先级、更新人、更新时间。支持弹窗新增/编辑，支持点击保存按钮触发批量排序。
2. 后端：提供分页查询、新增、编辑（根据id更新）、逻辑删除（修改 is_deleted 状态字段）、批量排序接口。

【你必须在生成文档前，在 design.md 中明确回答我以下设计细节】：
- 优先级（sequence）自增逻辑是在后端自动处理，还是需要前端传递？
- 批量排序接口如何设计，才能避免在 Service 层循环进行 N 次单条数据库更新？
- 弹窗关闭时，前端触发哪些隐性的表单重置（reset）状态清理？

请严格按照规范，在前端和后端目录分别输出：
前端：proposal.md, spec.md, tasks.md
后端：proposal.md, spec.md, design.md, tasks.md
生成完毕后向我汇报，等待我 Review 契约字段。
```

### 第二步：卡（Review）—— 像架构师一样人机协同纠偏

AI 收到上面的提示词后，会在你的项目里乖乖长出 7 份 `.md` 文档。 这时候，**你千万不要看代码，直接点开 `service-backend/sdd-propose/spec.md` 和 `service-frontend/sdd-propose/spec.md`**。

用你的肉眼去对一下两边的字段：

- 看看前端发送的 `templateName`，后端接收的是不是写成了 `title`？
    
- 看看后端返回的 `Result<Page<Vo>>` 的 VO 结构，前端能不能直接解析？
    

如果发现了不一致，不要自己改文档，直接对 AI 说：

> “我看了你的 `spec.md`。后端的保存接口入参漏掉了主键 `id` 字段，导致前端无法复用该接口进行编辑更新；另外，前端拖拽排序必须是点击右下角‘保存’后再批量请求后端，请立刻修正两边的 SDD 文档。”

AI 会在一瞬间把文档更新完毕。此时，契约达成，技术方案在纸面上已经达到 100% 正确。

### 第三步：做（Apply）—— 启动双 Agent 无情执行

当文档完美后，你去看一眼两边 md 文档里的 `tasks.md`（任务清单），确认每一步要改的文件路径都没错。接下来就是享受 AI 全自动化威力的时刻。

你直接在 Cursor 或工具中发送终极执行指令：

Plaintext

```
很好，两边的 SDD 技术契约和设计细节已经全部 Review 通过。

现在请启动多 Agent 协作开发模式：
1. 请严格、逐字、100% 按照前端的 tasks.md 任务清单，批量修改和创建前端代码。
2. 请严格、逐字、100% 按照后端的 tasks.md 任务清单，批量生成后端的 Controller、Service、Mapper 以及建表 SQL。

开始执行，写完后告诉我。
```

- **这时候你会看到**：AI 会像被注入了灵魂一样，不带任何废话和犹豫，严格顺着清单把 `ShortcutController.java`、`ShortcutService.java`、`ShortcutTable.tsx` 全部极其精准地敲出来，甚至连包名、引用的公共异常类、团队统一的 Result 包装都和你老代码一模一样。
    

## 🧪 战后验证：别忘了得物的无阻塞大招

代码生成完后，按照得物的三阶段验证法，你只需要做两件事，就能以最省时间的方式收尾：

1. **前端自测**：让前端 Agent 参照 `spec.md` 给你在前端项目里写一段 `mockData`。你不用管后端，直接在本地把前端页面跑起来，点一点弹窗、试一试拖拽，确保 UI 逻辑完美。
    
2. **后端编译**：cd 到你的后端项目根目录，直接在终端敲入：
    
    Bash
    
    ```
    mvn clean compile
    ```
    
    只要控制台打印出 **`BUILD SUCCESS`**，就说明 AI 写的后端代码在语法、依赖、契约类型上全部没有任何低级错误，可以直接准备部署联调了！
