## 1.1 SpringBoot启动流程
![[Pasted image 20260611204117.png]]
SpringBoot主要通过SpringApplication.run()方法启动，主要可以分成创建SpringApplication实例和调用run（）方法两个阶段。
- 实例化阶段：`main` 方法执行 `SpringApplication.run()`。但在真正进入 `run()` 方法之前，系统会先 `new` 一个 `SpringApplication` 对象。在这个构造方法内部会判断当前应用的类型。然后会加载所有初始化器和事件监听器
- 执行run（）方法：执行run()方法会启动计时器并设置系统属性，初始化监听器并启动监听器，设置命令行参数，准备环境对象和应用上下文，刷新应用上下文并发布启动事件结束计时器，完成SpringBoot的启动。
## 1.2SpringBoot的理解：
• Spring Boot 提供了自动化配置，大大简化了项目的配置过程。通过约定优于配置的原则，很多常用的配置可以自动完成，开发者可以专注于业务逻辑的实现。
• Spring Boot 提供了快速的项目启动器，通过引入不同的 Starter，可以快速集成常用的框架和库（如数据库、消息队列、Web 开发等)，极大地提高了开发效率。
• Spring Boot 默认集成了多种内嵌服务器（如Tomcat、Jetty、Undertow)，无需额外配置，即可将应用打包成可执行的JAR 文件，方便部署和运行。
## 1.3Bean的生命周期
![[Pasted image 20260611210009.png]]
- 1.实例化：Spring会根据Bean的定义配置信息通过反射去创建一个Bean的实例
- 2.属性赋值：或者说叫依赖注入阶段，Spring会通过反射把`Autowired`、`Resource` 或 `Value` 注解标注的属性、各种引用的 Bean 注入进去。
- 3.初始化：
- 容器会检查**Aware相关的接口**看Bean是否实现了一些比如`BeanNameAware`、`BeanFactoryAware`、`ApplicationContextAware` 等接口，如果实现了，Spring 会把容器的对应的组件注入到 Bean 中。
	
- 然后会**执行前置处理**，就是如果Bean实现了BeanPostProcessor接口，Spring会调用它们的前置处理方法
	
- - **初始化后置处理（After）：** 触发后置处理器的“初始化后”方法。**这是整个生命周期最核心的扩展点，Spring AOP 的动态代理对象就是在这个阶段生成的。**
    
- **就绪驻留：** 此时 Bean 已经准备就绪，正式投入使用，并一直驻留在 Spring 容器中，直到应用准备销毁。
- 4.当容器准备关闭时，触发销毁流程。系统会先执行 **`@PreDestroy` 注解标注的方法**，接着触发销毁接口或自定义的 `destroy-method` 方法，完成资源的释放和收尾工作。
## 1.4 Spring IOC & AOP
• loC：即控制反转的意思，它是一种创建和获取对象的技术思想，依赖注入(DI)是实现这种技术的一种方式。传统开发过程中，我们需要通过new关键字来创建对象。使用loC思想开发方式的话，我们不通过new关键字创建对象，而是通过loC容器来帮我们实例化对象。通过loC的方式，可以大大降低对象之间的耦合度。
• AOP：是面向切面编程，能够将那些与业务无关，却为业务模块所共同调用的逻辑封装起来，以减少系统的重复代码，降低模块间的耦合度。Sprng AOP 基于动态代理：如果被代理对象实现了接口，Spring AOP 默认会使用JDK Proxy 创建代理对象；如果没有实现接口，则会使用CGLIB 生成被代理对象的子类作为代理。注意：自Spring Boot 2.0 起，默认配置
i spring.aop.proxy-target-class=true 
即无论是否实现接口都优先使用CGLIB，如需切回JDK动态代理需手动设为false。
 第一步：启动时——生成代理（做套子）

1. **扫描与匹配**：Spring 容器启动时，会扫描所有的 Bean 和你写的切面（`@Aspect`）。
    
2. **判断是否需要代理**：通过后置处理器（`BeanPostProcessor`），对照切入点（`Pointcut`）表达式，看这个 Bean 的方法是否需要被拦截。
    
3. **织入并创建代理**：如果需要，Spring 就会在内存中为这个目标对象（Target）创建一个“代理对象”（Proxy）。
    
    - 有接口？用 **JDK 动态代理**。
        
    - 没接口？用 **CGLIB 动态代理**。
        
4. **偷梁换柱**：最后放入 Spring 容器的，不是你原本写的那个类，而是这个**代理对象**。
    

 第二步：运行时——拦截执行（走流程）

当你在代码中调用这个 Bean 的方法时，实际上调用的是**代理对象**：

1. **客户端调用**：你发起方法调用。
    
2. **获取拦截器链**：代理对象把这个方法上所有需要执行的通知（Before、After、Around 等）打包排序，组成一个**拦截器链**。
    
3. **链式执行（责任链模式）**：
    
    - 先执行前置通知（`Before`）。
        
    - 真正执行你写的业务代码（`Target` 目标方法）。
        
    - 执行后置/返回/异常通知（`After`/`Returning`/`Throwing`）。
        
4. **返回结果**：把执行结果返回给你。
    

**一句话总结：** Spring AOP 的本质就是**在启动时用动态代理把你的目标类包装起来，在运行时通过拦截器链，在不改动你业务代码的前提下，把切面代码插在业务代码前后执行。**

### 一、 Spring 事务的底层原理

Spring 事务的本质是 **AOP（动态代理）** 与 **JDBC Connection** 的结合。

当你给一个方法加上 `@Transactional` 注解时：

1. **生成代理对象：** Spring 会在初始化阶段（AfterInitialization）为该类生成一个 AOP 代理对象。
    
2. **开启事务：** 当外界调用该方法时，代理对象会先拦截请求，通过 `TransactionManager` 获取数据库连接，把数据库连接绑定到当前ThreadLocal中，并执行 `connection.setAutoCommit(false)`（关闭自动提交，开启事务）。
    
3. **提交/回滚：** * 如果方法正常执行完毕，代理对象调用 `connection.commit()` 提交事务。
    
    - 如果方法抛出异常，代理对象调用 `connection.rollback()` 回滚事务。
        

### 二、 五大隔离级别（Isolation）

Spring 的隔离级别直接对应了数据库底层（如 MySQL）的隔离级别，通过 `@Transactional(isolation = Isolation.Xxx)` 来设置。Spring 引入了一个默认级别，共 5 种：

| **隔离级别枚举值**            | **含义**                          | **解决的问题**       | **潜在问题**                 |
| ---------------------- | ------------------------------- | --------------- | ------------------------ |
| **`DEFAULT`**          | **默认级别**。使用底层数据库当前配置的隔离级别。      | 视数据库而定          | 视数据库而定                   |
| **`READ_UNCOMMITTED`** | 读未提交。允许读取其他事务未提交的数据。            | 无               | 脏读、不可重复读、幻读              |
| **`READ_COMMITTED`**   | 读已提交（**Oracle默认**）。只能读取已提交的数据。  | 解决 **脏读**       | 不可重复读、幻读                 |
| **`REPEATABLE_READ`**  | 可重复读（**MySQL默认**）。同事务中多次读取数据一致。 | 解决 **脏读、不可重复读** | 幻读（MySQL通过Next-Key锁基本解决） |
| **`SERIALIZABLE`**     | 串行化。完全串行执行事务，效率极低。              | 解决 **所有并发问题**   | 性能暴跌，金融高并发场景极少使用         |

### 三、 七大传播行为（Propagation）—— _最爱考_

当一个带有事务的方法 `A()`，去调用另一个带有事务的方法 `B()` 时，底层连接应该如何处理？这就是事务传播行为（Propagation）。

为了方便记忆，我们可以把这 7 种行为分为 **三大类**：

#### 1. 必须要事务（没事务就建新的）

- **`REQUIRED`（默认行为）：** 如果当前有事务，B 就加入该事务；如果没有，B 就自己新建一个事务。**A和B只要有一个报错，全盘回滚。**
    
- **`REQUIRES_NEW`：** 不管当前有没有事务，B 都**必须新建一个属于自己的独立事务**。如果当前有事务，先挂起（暂停）A 事务。**B 报错只会回滚 B 自己，不会影响 A；但 A 报错回滚也无法影响已经提交的 B。**
    
- **`NESTED`（嵌套事务）：** 如果当前有事务，B 会在当前事务中嵌套一个“子事务”（创建一个 `Savepoint` 保存点）。**如果 B 报错，B 可以单独回滚到保存点，不影响 A 继续提交；但如果 A 报错，整个 A 和 B 全部回滚。**
    

#### 2. 顺其自然（有就有，没有就没有）

- **`SUPPORTS`：** 如果当前有事务，B 就加入；如果没有，B 就在**非事务**状态下运行。
    
- **`NOT_SUPPORTED`：** B 必须在**非事务**状态下运行。如果当前有事务，先把当前事务挂起，B 运行完了再恢复。
    

#### 3. 极度傲娇（不符合条件就抛异常）

- **`MANDATORY`（强制）：** B 必须在事务中运行。如果当前没有事务，直接**抛出异常**。
    
- **`NEVER`：** B 必须在非事务中运行。如果当前存在事务，直接**抛出异常**。
    

### 四、 核心重灾区：事务失效的常见场景

面试官最喜欢让你排查：_“为什么我加了 `@Transactional`，数据报错了却没回滚？”_ 以下是实际开发中最典型的失效原因：

#### 1. 自身调用（方法内部自调）—— _最高频_

- **场景：** 类 A 里面有两个方法，`methodA()` 没有注解，`methodB()` 加上了 `@Transactional`。在 `methodA()` 内部直接调用 `this.methodB()`。
    
- **原因：** Spring 事务基于 **AOP 代理**。你直接 `this.methodB()` 走的是原对象的内部调用，**根本没有经过代理对象**，事务拦截器无法介入，导致事务失效。
    
- **解决：** 引入当前类的代理对象再调用，或者将 `methodB` 拆到另一个 Service 类中。
    

#### 2. 注解加在非 `public` 方法上

- **场景：** 把 `@Transactional` 加在了 `private` 或 `protected` 方法上。
    
- **原因：** Spring 的 `TransactionInterceptor`（事务拦截器）在检查方法时，硬编码限制了**只会对 public 方法生效**。即使加了，也会被直接忽略。
    

#### 3. 异常被内部 `try-catch` 吞掉了

- **场景：** ```java
    
    @Transactional
    
    public void createUser() {
    
    try {
    
    userDao.save(user);
    
    int i = 1 / 0; // 发生异常
    
    } catch (Exception e) {
    
    log.error("报错了，但我把它 catch 住了");
    
    }
    
    }
    
- **原因：** AOP 代理对象之所以能回滚，是因为它**捕获到了方法抛出来的异常**。如果你自己在内部把异常 `catch` 住了且没有往外抛（`throw`），代理对象以为方法执行很成功，就会高高兴兴执行 `commit`，导致回滚失效。
    

#### 4. 抛出了非运行时异常（默认只回滚 RuntimeException）

- **场景：** 方法内抛出了 `IOException` 或 `SQLException` 等受检异常（Checked Exception）。
    
- **原因：** Spring 默认只会对 **`RuntimeException`（运行时异常）和 `Error`** 进行回滚。
    
- **解决：** 显式指定回滚所有异常：`@Transactional(rollbackFor = Exception.class)`。

# 二、设计模式
## 2.1单例模式：
[[并发安全#voliatle关键字有什么作用？]]
> “单例模式是为了确保一个类在整个 JVM 内部绝无仅有地只存在一个实例（比如共享的全局线程池、配置管理器）。 在多线程高并发环境下，我最推荐使用 **双重检查锁（Double-Checked Locking，简称 DCL）** 的懒加载实现。它既保证了线程安全，又通过缩小同步代码块的范围提升了高并发下的性能。同时，必须配合 `volatile` 关键字防止指令重排导致的半初始化对象问题。”

```java
public class Singleton {
    // 核心点 1：使用 volatile 防止指令重排，并保证线程可见性
    private static volatile Singleton instance;

    // 核心点 2：私有构造方法，防止外部直接 new
    private Singleton() {}

    public static Singleton getInstance() {
        // 第一次检查：为了提高效率。如果已经创建了，就不用再进锁竞争，直接返回
        if (instance == null) {
            synchronized (Singleton.class) {
                // 第二次检查：为了线程安全。防止两个线程同时通过了第一次检查，在排队进锁后重复创建
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

```java
instance  = new Singleton();
```

在我们看来，这是一行普通的 Java 代码；但在 JVM 底层，这行代码被编译成字节码后，实际上分成了 **3 步（3 条指令）** 执行：

1. **`memory = allocate();`** // 1. 分配对象的内存空间
    
2. **`ctorInstance(memory);`** // 2. 初始化对象（执行构造方法，填充字段）
    
3. **`instance = memory;`** // 3. 将 `instance` 引用指向刚刚分配的内存地址
    

⚠️ 什么是指令重排？
JVM 的 JIT 编译器和 CPU 为了提高执行效率，在不影响**单线程**执行结果的前提下，会对指令进行优化排序，这就是**指令重排**。
在多线程环境下，第 2 步和第 3 步并没有绝对的依赖关系。因此，JVM 可能会将执行顺序从 `1 -> 2 -> 3` 优化重排为 **`1 -> 3 -> 2`**。

💥 致命的并发 Bug 是如何发生的？
假设我们**没有**给 `instance` 变量加 `volatile` 关键字，此时发生了重排（顺序为 1 -> 3 -> 2），两个线程并发访问：

| **时间点** | **线程 A (Thread A)**                                                                           | **线程 B (Thread B)**                                                                                                          |
| ------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **T1**  | 进入同步块，执行 `new Singleton()`。                                                                   |                                                                                                                              |
| **T2**  | 先执行了步骤 1（分配内存）和**步骤 3（让引用指向内存）**。<br><br>  <br><br>此时，`instance != null`，但**步骤 2（构造方法）还没执行**。 |                                                                                                                              |
| **T3**  |                                                                                               | 调用 `getInstance()`，执行第一次判空：`if (instance == null)`。                                                                          |
| **T4**  |                                                                                               | 发现 `instance` 已经不为空了（因为线程 A 已经执行了步骤 3），于是**直接返回了这个 `instance`**。                                                             |
| **T5**  | 继续执行步骤 2，完成真正的初始化。                                                                            | 拿到 `instance` 愉快地去调用它的方法（例如 `instance.doSomething()`）。<br><br>  <br><br>❌ **由于对象还没初始化，直接爆出 `NullPointerException` (空指针异常)！** |

这就是经典的“半初始化对象”问题。线程 B 拿到的是一个虚有其表（有了内存地址）、但内部完全是空壳的“残疾”对象。

🛡️ `volatile` 是如何完美解决这个问题的？

当我们将变量声明为 `volatile` 后：

```java
private static volatile Singleton instance;
```

它会带来两个关键特性：

### 1. 禁止指令重排（依靠内存屏障 Memory Barrier）

JVM 会在生成的字节码指令序列中插入**内存屏障**。对于 `volatile` 变量的写操作，内存屏障会严格禁止 `1 -> 3 -> 2` 这种重排，强制执行顺序必须是 **`1 -> 2 -> 3`**。

这样就能保证：**只要 `instance` 指向了内存地址（不为 null），它背后的对象就一定已经完全初始化好了。** 线程 B 绝对不会读到中间状态。

### 2. 保证线程可见性

`volatile` 确保一个线程对该变量的修改，能够立即同步回主内存，并且让其他线程在 CPU 中的缓存失效，强制从主内存重新读取。这就保证了线程 A 刚 new 完对象，线程 B 立马就能看到最新的状态。
## 2.2策略模式+工厂模式 优化if-else
> “为了消除业务中臭长臭长的 `if-else`，我通常会采用 **策略模式 + 工厂模式**。 核心思路是：利用**策略模式**把不同的业务逻辑拆分到不同的实现类中；再利用 **Spring IOC 容器的自动注入特性**，在项目启动时把这些策略动态组装进工厂的 `Map` 里。后续业务调用只需一行代码，新增渠道也完全不需要修改原有代码，完美符合开闭原则。”

### 1. 策略接口与实现（利用 `@Component`）

```java
public interface PayStrategy {
    void pay(double amount);
    String getType(); // 核心：用于工厂的 Key
}

@Component
public class WeChatPay implements PayStrategy {
    public void pay(double amount) { /* 微信支付逻辑 */ }
    public String getType() { return "WECHAT"; }
}

@Component
public class AliPay implements PayStrategy {
    public void pay(double amount) { /* 支付宝逻辑 */ }
    public String getType() { return "ALIPAY"; }
}
```

### 2. 智慧工厂（高分亮点：消除传统工厂的 switch-case）
联想[[每日一面/清能互联实习#1. 静态元数据缓存（解决反射性能瓶颈）]]

```java
@Component
public class PayFactory {
    // 缓存所有策略
    private final Map<String, PayStrategy> strategyMap = new ConcurrentHashMap<>();

    // 核心：Spring 会自动把所有 PayStrategy 的 Bean 注入到这个 List 中
    @Autowired
    public PayFactory(List<PayStrategy> strategies) {
        strategies.forEach(s -> strategyMap.put(s.getType(), s));
    }

    public PayStrategy get(String type) {
        return strategyMap.get(type);
    }
}
```

### 3. 业务层调用（彻底消灭 if-else）

```java
@Service
public class OrderService {
    @Autowired private PayFactory payFactory;

    public void handleOrder(String channel, double amount) {
        // 以前需要 if-else 判断 channel，现在只需一行：
        payFactory.get(channel).pay(amount);
    }
}
```

## 3.1线程池
[[线程池]]
阿里巴巴Java开发手册》中有一条强制规定：**线程池不允许使用 `Executors` 去创建，而是通过 `ThreadPoolExecutor` 的构造方法。**

原因其实很简单：像 `Executors.newFixedThreadPool()` 和 `Executors.newSingleThreadExecutor()` 底层使用的是无界队列 `LinkedBlockingQueue`（默认容量是 $2^{31}-1$），如果并发量飙升，队列里会堆积几百万个请求，直接导致 **OOM（内存溢出）**；而 `Executors.newCachedThreadPool()` 允许创建的线程数量是 `Integer.MAX_VALUE`，高并发下会瞬间创建出无数个线程，把 CPU 和内存直接撑爆。
`ThreadPoolExecutor` 最全的那个构造方法：
```java
public ThreadPoolExecutor(
    int corePoolSize,               // 1. 核心线程数
    int maximumPoolSize,            // 2. 最大线程数
    long keepAliveTime,             // 3. 空闲线程存活时间
    TimeUnit unit,                  // 4. 时间单位
    BlockingQueue<Runnable> workQueue, // 5. 任务队列
    ThreadFactory threadFactory,    // 6. 线程工厂
    RejectedExecutionHandler handler // 7. 拒绝策略
)
```

## 3.4 CAS 
CAS和AQS有什么关系？CAS和AQS两者的区别：
• CAS 是一种乐观锁机制，它包含三个操作数：内存位置（V)、预期值（A）和新值（B)。CAS 操作的逻辑是，如果内存位置Ⅴ的值等于预期值A，则将其更新为新值B，否则不做任何操作。整个过程是原子性的，通常由硬件指令支持，如在现代处理器上，cmpxchg指令可以实现 CAS 操作。
• AQS 是一个用于构建锁和同步器的框架，许多同步器如ReentrantLock、Semaphore、CountDownLatch等都是基于AQS 构建的。AQS 使用—个volatile的整数变量　state来表示同步状态，通过内置的FIFo队列来管理等待线程。它提供了一些基本的操作，如　acquire(获取资源)
和release

## 5.1ArrayList.sort（）用的什么排序算法
### a. 对象数组（引用类型）

- 使用 **TimSort**（Java 7+）
- TimSort 是 **归并排序 + 插入排序的混合优化算法**
- 特点：
    - **稳定排序**（相等元素顺序保持不变）
    - 时间复杂度：平均 `O(n log n)`，最坏 `O(n log n)`，最好 `O(n)`（几乎有序）
- 使用场景：`Arrays.sort(Object[] a)`、`ArrayList.sort()`（因为它最终用对象数组调用 Arrays.sort）

### b. 原始类型数组（int, long, double...）

- Java 8+ 对 **`int[]`、`long[]`、`double[]`** 使用 **Dual-Pivot Quicksort**（双枢轴快速排序）
- 特点：
    - **不稳定排序**（相等元素顺序可能改变）
    - 平均复杂度：`O(n log n)`，最坏情况 `O(n^2)`（但优化了枢轴选择，几乎不会触发）
- 使用场景：`Arrays.sort(int[])`、`Arrays.sort(long[])` 等
## 5.2 1. hashmap & concurrentHashMap 如何多线程
### 1. 基础垫脚石：HashMap 的底层结构
[[Java/Java基础#1.HashMap]]
`HashMap` 的底层可以总结为八个字：**数组 + 链表 + 红黑树**。
### 核心运作机制：

1. **路由寻址**：当你 `put(key, value)` 时，把 key 的 `hashCode()` 经过扰动函数计算，然后通过 `(n - 1) & hash`（等价于取模）算出它应该落在数组的哪个索引（Bucket）上。
    
2. **哈希冲突（Hash Collision）**：如果两个不同的 key 算出了同一个索引，这就是冲突。Java 8 采用**尾插法**把它们串成一条单向链表。
    
3. **红黑树化（Treeify）**：如果运气太差，某条链表太长了，查询复杂度会从 $O(1)$ 退化成 $O(n)$。
    
    - **触发条件**：当**链表长度 $\ge 8$** 且 **数组总长度 $\ge 64$** 时，这条链表就会异步进化成一棵**红黑树**，把查询复杂度强行拉回 $O(\log n)$。
        

### 为什么 HashMap 线程不安全？

多线程同时去 `put` 的时候：

- **数据覆盖**：如果两个线程算出了同一个索引，同时准备插入，线程 A 刚判断完该位置为空还没写入，CPU 切换到线程 B 直接写进去了，接着线程 A 醒来直接覆盖，导致线程 B 的数据凭空消失。
    
- **扩容死循环（Java 7 致命伤，Java 8 已修复）**：Java 7 用头插法，多线程扩容会形成环形链表，导致 `get()` 时死循环把 CPU 飙到 100%。Java 8 换成了尾插法保持相对顺序，修复了死循环，但**依然存在数据覆盖和 size 计数不准**的问题。
    

### 2. 终极完全体：ConcurrentHashMap 怎么做到并发安全？

既然 `HashMap` 是个线程不安全的“脆皮”，传统的 `Hashtable` 或者 `Collections.synchronizedMap` 又太笨重（它们不管三七二十一锁住整个大数组，高并发下所有人都在排队，性能极差）。

Doug Lea 大神出手，在 `ConcurrentHashMap` 里实现了一种**极其精妙的局部锁（分段思想）**。

#### Java 8 舍弃了 Java 7 的 Segment 分段锁

- **Java 7 的做法**：把大数组分成 16 个小数组（Segment），每个 Segment 自带一把锁。最高支持 16 个线程并发。
    
- **Java 8+ 的做法**：直接舍弃 Segment！回归到一个大数组，直接**锁住数组的每个桶的“头节点”（Node）**。
    

3## Java 8+ 的三大核心并发武器：

##### ① CAS 无锁化写入（头节点为空时）

当线程去 `put` 某个 Key，计算出索引后，发现这个桶的**头节点是空的（还没有人占过）**。

- 此时**不需要加锁**！
    
- 线程直接通过 **CAS** 操作（`compareAndSwapObject`），尝试把自己的新节点塞进去。
    
- 如果成功，直接返回；如果失败（说明别的线程抢先塞了头节点），进入下一步。
    

##### ② `synchronized` 局部锁（头节点不为空时）

如果发现头节点已经存在了（发生哈希冲突了，需要往链表或红黑树里写）：

- 线程会以**这个桶的头节点（Node）作为锁对象**，直接 `synchronized(f)`。
    
- **爽在哪里**：只要你们两个线程算的索引不一样（比如你改索引 3，我改索引 5），我们两个完全可以**同时并行写入**，互不干扰！只有两个线程同时往索引 3 里写数据时，才会发生阻塞排队。
    
- 这把锁的粒度被压到了极致，只要数组足够大，几乎不会发生锁竞争。
    

##### ③ 配合 volatile 保证可见性

Node 节点的 `val` 和 `next` 指针全部用 `volatile` 修饰，保证一个线程改了，另一个线程读的时候立刻能看到，不需要加锁就能实现无锁安全读。

### 3. 面试必考：ConcurrentHashMap 那些令人拍案叫绝的细节

#### ① 扩容时的“多线程协作”（Help Transfer）

传统的 Map 扩容，是一个线程苦哈哈地把数据从旧数组挪到新数组。

`ConcurrentHashMap` 引入了**多线程协助扩容**。当一个线程发现 Map 正在扩容，它在写入时会化身为“搬砖工”，主动去帮领一部分数据迁移任务。大家一起搬，搬完再执行自己的写入。

#### ② 高并发下的“多名记账员”（LongAdder 思想）

如果 Map 里有 100 万个数据，怎么统计 `size()`？

如果搞一个全局变量 `count`，所有人 `put` 完都去用 CAS 改这个 `count`，那这个变量就会成为最严重的性能瓶颈（触发 CAS 疯狂自旋）。

Doug Lea 引入了类似 `LongAdder` 的 **CounterCell 数组**：

- 线程 `put` 成功后，不需要去改总计数器。
    
- 它会随机分配到一个 CounterCell（记账员），只把这个记账员手里的账本 $+1$。
    
- 当你调用 `size()` 时，Map 才会把所有记账员的数字加在一起汇报给你。**分而治之，极其高明！**
    
### 总结：两兄弟的终极对比

|**维度**|**HashMap**|**ConcurrentHashMap (Java 8+)**|
|---|---|---|
|**线程安全**|❌ 线程不安全|线程安全|
|**底层结构**|数组 + 链表 + 红黑树|数组 + 链表 + 红黑树|
|**并发控制手段**|没有任何控制|**CAS**（头节点为空） + **synchronized**（头节点不为空）|
|**锁的粒度**|无|**哈希桶的头节点**（Node 级别，极其细微）|
|**size() 统计**|内部一个普通的 `size` 变量|基于 LongAdder 思想的 `CounterCell` 数组分段统计|

## 6.3数据库死锁
### 1. 经典死锁场景还原（为什么会卡死？）

在 MySQL 里，最容易发生死锁的场景就是：**两个事务，以相反的顺序去更新相同的两行数据。**

假设我们有一张银行账户表，里面有 A、B 两个用户。现在同时发生两笔转账：

- **事务 1**：A 给 B 转账 100 元（需要先扣 A 的钱，再加 B 的钱）。
    
- **事务 2**：B 给 A 转账 200 元（需要先扣 B 的钱，再加 A 的钱）。
#### 戏剧性的碰撞过程：

1. **时刻 1**：事务 1 执行 `update account set money = money - 100 where name = 'A'`。MySQL 自动给 **A 这一行加上了行级排他锁（X锁）**。
    
2. **时刻 2**：事务 2 执行 `update account set money = money - 200 where name = 'B'`。MySQL 自动给 **B 这一行加上了行级排他锁（X锁）**。
    
3. **时刻 3**：事务 1 准备去加 B 的钱，执行 `where name = 'B'` 的更新。发现 B 被事务 2 锁住了，**事务 1 开始阻塞等待事务 2 释放 B**。
    
4. **时刻 4**：事务 2 准备去加 A 的钱，执行 `where name = 'A'` 的更新。发现 A 被事务 1 锁住了，**事务 2 开始阻塞等待事务 1 释放 A**。
    

> 💀 **死锁形成**：事务 1 在等事务 2 释放 B，事务 2 在等事务 1 释放 A。两个人像打结了一样，谁也无法继续，如果没有外力介入，他们会无限期地卡死在这里。

### 2. MySQL 自己是怎么处理死锁的？

面对这种死结，MySQL 的 InnoDB 引擎可不会坐以待毙，它有两套极其聪明的防御机制：

#### 机制一：死锁检测（Wait-for Graph 等待图）

- **原理**：InnoDB 内部维护了一个锁的等待图（类似于图论中的有向图）。每当一个事务发生锁阻塞，它就会在图中连一条线。
    
- **动作**：InnoDB 有一个后台线程，会定期去巡检这个图，一旦发现**图中出现了环路**（A 等 B，B 等 A），就说明爆发了死锁。
    
- **解决**：MySQL 会非常果断地选择一个**代价最小（持有的行锁最少、回滚成本最低）的事务进行主动强杀（Rollback）**，好让另一个事务顺利活下来。
    

#### 机制二：锁超时机制（innodb_lock_wait_timeout）

- 如果死锁检测因为某些原因没触发，MySQL 还有一个兜底参数（默认 50 秒）。一个事务如果被锁阻塞超过 50 秒，就会直接抛出 `Lock wait timeout exceeded` 异常，主动断开，释放自己手里的锁。
    

### 3. 线上突然爆发死锁，该怎么排查？

如果线上收到了死锁报警，作为一个资深开发，你应该掏出以下标准排查三板斧：

#### 第一步：去 MySQL 调出最后的死锁日志

直接在数据库执行这条神级 SQL：

```
SHOW ENGINE INNODB STATUS;
```

在打印出的大段文本中，找到 **`LATEST DETECTED DEADLOCK`（最近检测到的死锁）** 这一栏。

MySQL 会在日志里记录得清清楚楚：

- **TRANSACTION 1** 执行了什么 SQL，等的是哪张表的哪一行，手里握着什么锁。
    
- **TRANSACTION 2** 执行了什么 SQL，等的是哪张表的哪一行，手里握着什么锁。
    
- 最终 MySQL 决定回滚（WE ROLL BACK）了哪一个。
    

#### 第二步：分析原因（不仅有行锁，还有间隙锁）

很多时候，你发现两条 SQL 明明更新的是不同的 ID，为什么也会死锁？ 因为 InnoDB 在 `Repeatable Read（可重复读）` 隔离级别下，为了防止幻读，引入了 **Gap Lock（间隙锁）**。如果你更新一条不存在的记录，或者用范围查询，MySQL 会锁住一个“区间”。两个事务互相锁住交叉的区间，也会引发严重的死锁。

### 4. 彻底杜绝死锁的生产最佳实践（解法）

消灭死锁，核心思想就是**打破循环等待的条件**。

#### 解法一：严格约定一致的控制顺序（最常用）

回到刚才 A 转 B、B 转 A 的例子。我们可以在 Java 代码层进行优化：无论谁给谁转账，**永远先锁 ID 小的用户，再锁 ID 大的用户**。

- 事务 1（A给B）：A 的 ID 是 1，B 的 ID 是 2。先更新 A，再更新 B。
    
- 事务 2（B给A）：先更新 A，再更新 B。
    
- **结果**：事务 2 走到第一步时就会被阻塞，在门外排队，根本没有机会去锁住 B，死锁直接从源头被避免。
    

#### 解法二：大事务拆小，缩短持锁时间

死锁往往发生在一些复杂的、裹挟了大量业务逻辑的长事务中。事务执行时间越长，持有的锁被别人撞上的概率就越高。

- **优化**：尽量把不需要事务的逻辑（如调远程接口、发 MQ 消息）移到 `@Transactional` 外面。把大事务拆成几个独立的小事务，快进快出，闪电战解决。
    

#### 解法三：为表添加合理的索引

InnoDB 的行锁**必须建立在索引之上**。如果你的 `update` 语句里 `where` 条件后面跟的字段**没有加索引**，那么 MySQL 无法精准定位，会直接**把整张表的所有行全部锁死（行锁升级为表锁）**！这在高并发下百分之百会引发大规模的死锁和瘫痪。

### 总结

- **死锁的本质**：多事务、多资源、反向加锁、循环等待。
    
- **排查工具**：依靠 `SHOW ENGINE INNODB STATUS` 查看死锁日志。
    
- **预防药方**：排序加锁顺序、添加合理索引规避表锁、缩短大事务。
