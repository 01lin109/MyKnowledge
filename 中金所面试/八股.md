# 一、Spring相关
## 1.1 SpringBoot启动流程
![[Pasted image 20260611204117.png]]
SpringBoot主要通过SpringApplication.run()方法启动，主要可以分成创建SpringApplication实例和调用run（）方法两个阶段。
- 实例化阶段：`main` 方法执行 `SpringApplication.run()`。但在真正进入 `run()` 方法之前，系统会先 `new` 一个 `SpringApplication` 对象。在这个构造方法内部会判断当前应用的类型。然后会加载所有初始化器和事件监听器
- 执行run（）方法：执行run()方法会启动计时器并设置系统属性，初始化监听器并启动监听器，设置命令行参数，准备环境对象和应用上下文，刷新应用上下文并发布启动事件结束计时器，完成SpringBoot的启动。
## 1.2SpringBoot的理解：
• Spring Boot 提供了自动化配置，大大简化了项目的配置过程。通过约定优于配置的原则，很多常用的配置可以自动完成，开发者可以专注于业务逻辑的实现。
• Spring Boot 提供了快速的项目启动器，通过引入不同的 Starter，可以快速集成常用的框架和库（如数据库、消息队列、Web 开发等)，极大地提高了开发效率。
• Spring Boot 默认集成了多种内嵌服务器（如Tomcat、Jetty、Undertow)，无需额外配置，即可将应用打包成可执行的JAR 文件，方便部署和运行。
## 1.3Bean的生命周期
![[Pasted image 20260611210009.png]]
- 1.实例化：Spring会根据Bean的定义配置信息通过反射去创建一个Bean的实例
- 2.属性赋值：或者说叫依赖注入阶段，Spring会通过反射把`Autowired`、`Resource` 或 `Value` 注解标注的属性、各种引用的 Bean 注入进去。
- 3.初始化：
- 容器会检查**Aware相关的接口**看Bean是否实现了一些比如`BeanNameAware`、`BeanFactoryAware`、`ApplicationContextAware` 等接口，如果实现了，Spring 会把容器的对应的组件注入到 Bean 中。
	
- 然后会**执行前置处理**，就是如果Bean实现了BeanPostProcessor接口，Spring会调用它们的前置处理方法
	
- - **初始化后置处理（After）：** 触发后置处理器的“初始化后”方法。**这是整个生命周期最核心的扩展点，Spring AOP 的动态代理对象就是在这个阶段生成的。**
    
- **就绪驻留：** 此时 Bean 已经准备就绪，正式投入使用，并一直驻留在 Spring 容器中，直到应用准备销毁。
- 4.当容器准备关闭时，触发销毁流程。系统会先执行 **`@PreDestroy` 注解标注的方法**，接着触发销毁接口或自定义的 `destroy-method` 方法，完成资源的释放和收尾工作。
## 1.4 Spring IOC & AOP
• loC：即控制反转的意思，它是一种创建和获取对象的技术思想，依赖注入(DI)是实现这种技术的一种方式。传统开发过程中，我们需要通过new关键字来创建对象。使用loC思想开发方式的话，我们不通过new关键字创建对象，而是通过loC容器来帮我们实例化对象。通过loC的方式，可以大大降低对象之间的耦合度。
• AOP：是面向切面编程，能够将那些与业务无关，却为业务模块所共同调用的逻辑封装起来，以减少系统的重复代码，降低模块间的耦合度。Sprng AOP 基于动态代理：如果被代理对象实现了接口，Spring AOP 默认会使用JDK Proxy 创建代理对象；如果没有实现接口，则会使用CGLIB 生成被代理对象的子类作为代理。注意：自Spring Boot 2.0 起，默认配置
i spring.aop.proxy-target-class=true 
即无论是否实现接口都优先使用CGLIB，如需切回JDK动态代理需手动设为false。

### 一、 Spring 事务的底层原理

Spring 事务的本质是 **AOP（动态代理）** 与 **JDBC Connection** 的结合。

当你给一个方法加上 `@Transactional` 注解时：

1. **生成代理对象：** Spring 会在初始化阶段（AfterInitialization）为该类生成一个 AOP 代理对象。
    
2. **开启事务：** 当外界调用该方法时，代理对象会先拦截请求，通过 `TransactionManager` 获取数据库连接，把数据库连接绑定到当前ThreadLocal中，并执行 `connection.setAutoCommit(false)`（关闭自动提交，开启事务）。
    
3. **提交/回滚：** * 如果方法正常执行完毕，代理对象调用 `connection.commit()` 提交事务。
    
    - 如果方法抛出异常，代理对象调用 `connection.rollback()` 回滚事务。
        

### 二、 五大隔离级别（Isolation）

Spring 的隔离级别直接对应了数据库底层（如 MySQL）的隔离级别，通过 `@Transactional(isolation = Isolation.Xxx)` 来设置。Spring 引入了一个默认级别，共 5 种：

|**隔离级别枚举值**|**含义**|**解决的问题**|**潜在问题**|
|---|---|---|---|
|**`DEFAULT`**|**默认级别**。使用底层数据库当前配置的隔离级别。|视数据库而定|视数据库而定|
|**`READ_UNCOMMITTED`**|读未提交。允许读取其他事务未提交的数据。|无|脏读、不可重复读、幻读|
|**`READ_COMMITTED`**|读已提交（**Oracle默认**）。只能读取已提交的数据。|解决 **脏读**|不可重复读、幻读|
|**`REPEATABLE_READ`**|可重复读（**MySQL默认**）。同事务中多次读取数据一致。|解决 **脏读、不可重复读**|幻读（MySQL通过Next-Key锁基本解决）|
|**`SERIALIZABLE`**|串行化。完全串行执行事务，效率极低。|解决 **所有并发问题**|性能暴跌，金融高并发场景极少使用|

### 三、 七大传播行为（Propagation）—— _最爱考_

当一个带有事务的方法 `A()`，去调用另一个带有事务的方法 `B()` 时，底层连接应该如何处理？这就是事务传播行为（Propagation）。

为了方便记忆，我们可以把这 7 种行为分为 **三大类**：

#### 1. 必须要事务（没事务就建新的）

- **`REQUIRED`（默认行为）：** 如果当前有事务，B 就加入该事务；如果没有，B 就自己新建一个事务。**A和B只要有一个报错，全盘回滚。**
    
- **`REQUIRES_NEW`：** 不管当前有没有事务，B 都**必须新建一个属于自己的独立事务**。如果当前有事务，先挂起（暂停）A 事务。**B 报错只会回滚 B 自己，不会影响 A；但 A 报错回滚也无法影响已经提交的 B。**
    
- **`NESTED`（嵌套事务）：** 如果当前有事务，B 会在当前事务中嵌套一个“子事务”（创建一个 `Savepoint` 保存点）。**如果 B 报错，B 可以单独回滚到保存点，不影响 A 继续提交；但如果 A 报错，整个 A 和 B 全部回滚。**
    

#### 2. 顺其自然（有就有，没有就没有）

- **`SUPPORTS`：** 如果当前有事务，B 就加入；如果没有，B 就在**非事务**状态下运行。
    
- **`NOT_SUPPORTED`：** B 必须在**非事务**状态下运行。如果当前有事务，先把当前事务挂起，B 运行完了再恢复。
    

#### 3. 极度傲娇（不符合条件就抛异常）

- **`MANDATORY`（强制）：** B 必须在事务中运行。如果当前没有事务，直接**抛出异常**。
    
- **`NEVER`：** B 必须在非事务中运行。如果当前存在事务，直接**抛出异常**。
    

### 四、 核心重灾区：事务失效的常见场景

面试官最喜欢让你排查：_“为什么我加了 `@Transactional`，数据报错了却没回滚？”_ 以下是实际开发中最典型的失效原因：

#### 1. 自身调用（方法内部自调）—— _最高频_

- **场景：** 类 A 里面有两个方法，`methodA()` 没有注解，`methodB()` 加上了 `@Transactional`。在 `methodA()` 内部直接调用 `this.methodB()`。
    
- **原因：** Spring 事务基于 **AOP 代理**。你直接 `this.methodB()` 走的是原对象的内部调用，**根本没有经过代理对象**，事务拦截器无法介入，导致事务失效。
    
- **解决：** 引入当前类的代理对象再调用，或者将 `methodB` 拆到另一个 Service 类中。
    

#### 2. 注解加在非 `public` 方法上

- **场景：** 把 `@Transactional` 加在了 `private` 或 `protected` 方法上。
    
- **原因：** Spring 的 `TransactionInterceptor`（事务拦截器）在检查方法时，硬编码限制了**只会对 public 方法生效**。即使加了，也会被直接忽略。
    

#### 3. 异常被内部 `try-catch` 吞掉了

- **场景：** ```java
    
    @Transactional
    
    public void createUser() {
    
    try {
    
    userDao.save(user);
    
    int i = 1 / 0; // 发生异常
    
    } catch (Exception e) {
    
    log.error("报错了，但我把它 catch 住了");
    
    }
    
    }
    
- **原因：** AOP 代理对象之所以能回滚，是因为它**捕获到了方法抛出来的异常**。如果你自己在内部把异常 `catch` 住了且没有往外抛（`throw`），代理对象以为方法执行很成功，就会高高兴兴执行 `commit`，导致回滚失效。
    

#### 4. 抛出了非运行时异常（默认只回滚 RuntimeException）

- **场景：** 方法内抛出了 `IOException` 或 `SQLException` 等受检异常（Checked Exception）。
    
- **原因：** Spring 默认只会对 **`RuntimeException`（运行时异常）和 `Error`** 进行回滚。
    
- **解决：** 显式指定回滚所有异常：`@Transactional(rollbackFor = Exception.class)`。
