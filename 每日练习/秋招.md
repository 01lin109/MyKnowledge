# 华勤
## Q1你在华勤实习期间，主要参与了 **HMP 监控平台的监控探针 SDK 开发**。能不能介绍一下这个 SDK 的主要作用，以及你具体负责了哪些工作？
这个 SDK 主要用于采集各个业务系统的运行状态数据，包括 HTTP 请求异常、SQL 异常、数据库连接池以及 JVM 等指标，经过一定的聚合、去重和处理后，通过 ESB 异步上报到 HMP 监控平台，方便运维人员集中查看和处理异常。

我主要负责 **HTTP 请求异常和 SQL 异常两类数据的采集与处理**，其中通过 MyBatis 拦截 SQL 异常和慢 SQL，并对异常进行聚合去重后再进行上报。除此之外，我还参与解决了 SQL 脱敏正则导致的 StackOverflowError 问题。
## Q2 你在 HMP 监控平台中是怎么采集 HTTP 请求异常和 SQL 异常的？具体的处理流程是什么？
这个 SDK 主要通过 **MyBatis 插件机制采集 SQL 异常，通过 Spring 全局异常处理器采集 HTTP 请求异常**。

**SQL 异常方面**，我们通过 MyBatis 插件拦截 Executor 的 `query` 和 `update` 方法，在 SQL 实际执行过程中捕获异常。如果执行出现异常，就记录异常信息并重新抛出，不影响原有业务逻辑；如果没有异常但是执行时间超过配置的慢 SQL 阈值，则记录为慢 SQL。

采集到数据之后，我们会在**请求线程内同步完成 SQL 脱敏和 DTO 组装**，然后根据错误类型、调用方法等特征进入聚合去重窗口。窗口到期或者触发降级之后，再由异步线程将数据推送到 ESB，最终进入 HMP。

**HTTP 异常方面**，如果接口抛出的异常没有在 Service 等业务层被捕获，就会继续向上冒泡，最终进入我们的全局异常处理器。首先根据异常类型匹配对应的处理器，比如业务异常、参数校验异常等，这些属于预期异常，我们不会进行上报。

对于没有匹配到这些处理器的异常，会进入兜底逻辑。首先根据 Apollo 配置中心中动态配置的排除异常类型进行过滤；之后进一步对异常进行溯源，排除已经在 MyBatis 层采集过的 SQL 异常，避免同一个异常被重复上报。

经过过滤后，剩余的才是需要监控的 HTTP 异常。我们会提取异常信息并组装 DTO，然后通过异步线程进行后续处理和上报，同时请求线程正常返回错误响应，避免监控逻辑影响业务请求。

## Q3 SQL拦截为什么用Mybatis而不是JDBC层等

相比 JDBC 层，MyBatis 最大的优势是**业务定位信息更完整**。JDBC 层主要能拿到 SQL 和参数，而 MyBatis 的 Executor 层除了 SQL 和执行结果，还可以直接拿到 `MappedStatement`，知道具体是哪个 Mapper 方法执行的，比如 `UserMapper.selectById`，这样更方便定位具体业务。

JDBC 层理论上的优势是**覆盖范围更广**，像原生 JDBC、JdbcTemplate、JPA 都可以覆盖。但我们项目的数据访问统一使用 MyBatis，所以 MyBatis 层实际上已经是 SQL 执行的必经路径，JDBC 更广的覆盖范围在当前项目中没有实际价值，反而需要额外处理连接、参数以及不同数据访问方式带来的复杂度。

至于连接池层，比如 Druid 的监控机制，虽然也能采集 SQL，但会和具体连接池实现绑定，后续如果更换连接池，探针的兼容性会受到影响。

另外，MyBatis 插件本身就是官方提供的扩展机制，对业务代码基本没有侵入。

所以最终我们选择的是 **MyBatis 插件层**：相比 JDBC，它虽然覆盖范围没那么广，但在我们当前技术栈下，**业务定位信息更完整、覆盖已经足够，而且实现成本和侵入性更低**。

## Q4 ConcurrentHashMap+延迟调度 实现N——1
  
**背景一句话**：监控模块错误日志要推 ESB，线上 bug 爆发时同秒成百上千条相同异常，逐条推送打爆下游、刷爆大盘。设计**时间窗口聚合（N→1）**：同类错误 N 秒窗口内合并成一条上报。

**核心设计（两个组件）**：

1. `ConcurrentHashMap<String, ErrorWindow>` —— value 是"攒数据的桶"：持有首次错误完整 DTO（堆栈/URL 只留第一份）、`volatile int occurCount`、`lastOccurTime`、`flushed` 防重标记。去重键 = `errorClass|errorMethod`（同一位置同种异常=同一问题）。

2. 单线程 `ScheduledExecutorService` —— 负责"定时倒桶"。


**流程**：命中窗口 → `recordRepeat()` 计数+刷新时间，**不推送直接返回**；未命中 → `putIfAbsent` 建新窗口，**只有创建成功的线程**挂一个 `schedule(N秒后flushWindow)` 一次性延迟任务。窗口存续期再来的错误只改桶内字段不产生新任务（1000条=队列里1个任务）。到期刷出：复用首条完整信息，覆盖 `occurCount/firstOccurTime/lastOccurTime`，推1条，map remove。**本质：用最多N秒的延迟换 N→1 的推送量压缩，次数和时间跨度不丢。**


**兜底防御（按三条原则讲）**：

- **永远降级、永不阻断**：dedupeKey 构建失败→退回实时推送不丢数据；pushErrorLog 整体 try/catch，监控是旁路组件，自己炸了业务必须无感。

- **宁可多报、不可丢报、不可 OOM**：map 超 `maxPending` 上限→降级实时推送（背压阀，防几千种异常撑爆内存）；`@PreDestroy` 强制刷出所有未到期窗口（发布重启不丢数据）。

- **不信任并发和输入**：`putIfAbsent` 兜 check-then-act 竞态——get 和 put 非原子，两线程同时未命中各自 new 窗口，输的一方 `recordRepeat()` 累加进赢家窗口（不丢数据、不产生影子窗口）；`flushed` 标记+synchronized 双检防定时刷出与 @PreDestroy 强刷撞车重报；配置值 `Math.max(windowSeconds, 1)` 钳边界（Apollo 配 0/负数会退化聚合）；调度任务强制 try/catch（ScheduledExecutorService 任务抛未捕获异常会**静默死掉**，桶永久泄漏在 map）。


**追问防御**：

- 调度器为何单线程？→ 刷出只是拼 DTO+推送，无并发需求，守护线程足够。

## Q5：介绍你的 bizflow-tracing skill——四轮迭代是怎么演进的？

  

**背景一句话**：系统大量业务逻辑走 Activiti 流程引擎，AI 看到的是 Java 类，人描述问题用业务语言（"竞聘审批卡在部门评审节点"），两者对不上，AI 只能盲目 Grep。

  

**第1轮：BPMN 业务-代码速查表**。skill 只定义表结构（节点ID/业务含义/对应处理类），调用时 AI 扫描 BPMN 定义自动填充，**人工审核后入库**——表是后续所有检索的地基，地基错全错，一次审核换长期可信。

  

**第2轮：网关路由表**。光知道节点对应哪个类不够，跨流程 bug 的关键是"为什么走了这个分支"。补一张表：网关ID → 路由变量名 → 取值 → 分支节点 → 业务含义。

  

**第3轮：引入 codegraph + 速查表瘦身**。表从"存代码"变"存指针"——只留 BPMN节点→类的映射，代码本体让 AI 现场用 codegraph 拿。解决两个问题：token 膨胀、**代码一改表就过期**（陈旧映射比没有更糟）。职责分离：表管语义映射（AI 最缺的），codegraph 管代码本体（永远是新鲜的）。

  

**第4轮：工具编排 + 维护闭环**。发现 AI 不会自发用表，在 skill 里固化检索顺序：**速查表（确定性语义映射）→ codegraph（结构追溯）→ Grep（兜底）**，越往后成本越高噪音越大。初始化时主动向用户提问确认业务含义。另设计 hook：代码变更影响分析涉及表内内容时，主动询问是否更新表——把维护嵌入日常工作流而非靠人记。

  

## Q6：这个 skill 的效果怎么验证的？

  

**单变量对照实验**（人这个变量控制不了，控制其余所有变量）：同一个工具（opencode）、同一个模型、同一个提示词、同一个跨流程 bug，唯一区别：一组明确指示"先查速查表"，另一组直接行动。

  

采集三维度：①过程数据（各工具调用耗时，prompt 要求模型上报）；②成本数据（总耗时、token 消耗）；③质量数据（提示词里预设统一回答结构，使两次输出可对比）。

  

**三个追问的防御**：

- 样本少？→ 诚实承认是探索性实验；AI 同模型同提示词方差小；结论机制上自洽（查表 O(1) vs 全文搜索）；改进方向是 N 个 bug × 多轮取均值。

- "明确告知用表"≠AI 自发用？→ **这正是第4轮做工具编排的动因**——实验证明表有价值，但 AI 不自发用，所以把顺序固化进 skill。实验和迭代在此闭环。

- token 对比？→ 速查表组读表会多耗 token，tradeoff 表述：用可控 token 开销换定位时间和准确率。

  

**佐证**：上传公司内部平台后有较多下载使用（反响数据未回收，可顺势讲"该加轻量反馈钩子"体现产品意识）。

  

## Q7：CLI 类 AI 工具和 Trae 类 IDE 工具在检索处理上的差异？各有何优劣？

  

**两种范式**：

- **Trae = 预检索（RAG）**：后台维护 embedding 语义索引（代码切块→向量化），用户提示词先查索引，top-K 相似代码块**先于模型注入**上下文，模型带着检索结果开始干活。

- **CLI = 自主检索（Agentic）**：提示词直接给模型，模型自己在对话循环中决定何时 Grep/读文件，无预建索引、无预注入。

  

**优劣对比**：预检索首轮快、换说法也能命中（语义模糊查询强），但死穴是**替模型做了一次不可撤销的猜**——top-K 错了模型在错误前提上工作且不自知，且检索管道先于模型抢跑、skill 编排被压制；自主检索全程透明可控、策略可干预、深层调用追溯强，但冷启动盲目（第一跳靠猜关键词）。

  

**业务语言场景**：中文业务词（"竞聘审批"）和英文代码标识符在向量空间几乎正交，预检索在断层处最弱——注入的 top-K 大概率全错还占上下文。**我的 skill 本质是给自主检索消灭冷启动**（第一跳由确定性资产给出），所以它在 CLI 里如鱼得水、在预检索宿主里反而吃亏。

  

**结论（面试金句）**：两种范式各有死穴，最优是分层混合——第一跳确定性资产（速查表）→ 第二跳结构检索（codegraph/LSP）→ 第三跳语义/文本兜底（向量/Grep）。可迁移性设计不能只考虑 skill 内容，还要考虑与宿主检索层的共存策略。

  

**诚实边界**：Trae 内部实现（索引方式、注入条数）是从行为推断的通用架构，未看过源码——被追问时答"行为归因，实现未深究"反而严谨。
