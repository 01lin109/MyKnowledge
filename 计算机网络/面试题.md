# 1.SSE和WebSocket
## 一、 什么是 SSE（Server-Sent Events）？

简单来说，**SSE 是一种允许服务器端向客户端单向推送实时数据的技术。**

在传统的 HTTP 请求中，客户端给服务器发一个 Request，服务器回一个 Response，连接就断开了（一问一答）。

但在大模型生成文本时（比如 DeepSeek 吐字），它是**逐字、逐句**吐出来的。如果等它憋了 30 秒把 1000 个字全生成完再打包回给你，用户体验会极差。

### 1. SSE 的工作原理

SSE 的精髓在于：客户端发送一个普通的 HTTP 请求后，服务器在响应头（Response Header）里玩了个花样，带上了这几行：

HTTP

```
Content-Type: text/event-stream
Cache-Control: no-cache
Connection: keep-alive
```

这告诉浏览器：“**这个连接别断开，我接下来要像挤牙膏一样，一点点给你喂数据了。**”

随后，服务器就可以使用一种非常简单的固定文本格式，源源不断地往这个管道里塞数据：

Plaintext

```
data: {"content": "你"}

data: {"content": "好"}

data: {"content": "，我是"}

data: {"content": "AI"}
```

浏览器侧通过 HTML5 原生支持的 `EventSource` API 监听到这些 `data:` 碎块后，就能立马把它实时渲染到前端网页上，实现“逐字吐字”的效果。

## 二、 SSE 与 WebSocket 的全方位对比

很多人会问：“既然要实时推数据，为什么不用老牌的 WebSocket，而要用 SSE？”

我们把它们俩放在拳击台上面对面对比一下：

|**维度**|**SSE (Server-Sent Events)**|**WebSocket**|
|---|---|---|
|**数据流向**|**单向**（只能服务器 $\rightarrow$ 客户端）|**双向全双工**（双方可以同时互相发）|
|**底层协议**|纯粹的 **HTTP 协议**（基于标准的 HTTP/2 或 HTTP/1.1）|独立的 **WebSocket 协议**（需要从 HTTP 握手升级为 `ws://` 协议）|
|**数据格式**|纯文本格式（通常里面包 JSON 字符串）|支持二进制流、支持纯文本|
|**断线重连**|**原生自带**。如果网络断了，浏览器会自动重连，并带上上次的 ID。|**需要手写**。必须在前端写心跳检测、手动触发 `reconnect` 逻辑。|
|**轻量程度**|**极度轻量**。服务器端只需要维持普通的 HTTP 长连接，开发极简。|**较重**。需要专门的 WebSocket 服务器/网关配合，维护成本高。|
|**防火墙友好**|**极好**。因为就是普通的 HTTP(S) 流量，不容易被公司或学校的防火墙拦截。|**一般**。某些严格的局域网网关会直接掐断非标准 HTTP 端口的 `ws://` 链接。|

## 三、 为什么在大模型（Agent）时代，业内全都偏爱 SSE？

回到你的 `ChatStream` 接口，你用了 GoFrame 的连接托管，底层吐字其实就是 SSE。大模型场景下，SSE 展现出了压倒性的三大优势：

### 1. “单向推送”完美契合大模型的业务场景

多轮对话的特征是：

- 客户端发一句话（**这笔请求是一瞬间就发完了的，不需要流式发**）。
    
- 大模型思考，然后开始源源不断地回话（**需要流式收**）。
    
    WebSocket 的“双向同时收发”能力在大模型对话中属于“火力过剩”，我们根本不需要在模型说话的同时，客户端还在同一个通道里源源不断地发数据。
    

### 2. 完美的断线重连机制（Last-Event-ID）

运维场景经常会遇到网络抖动。SSE 原生支持一个骚操作：服务器发送数据时，可以带上一个 `id: 123`。

如果吐字吐到一半网络断了，浏览器会自动发起重连，并在 HTTP 请求头里自动带上 `Last-Event-ID: 123`。你的 Go 后端拿到这个 ID，就知道这个用户刚才听到了哪一步，“断点续传”瞬间就能接上。

### 3. HTTP/2 多路复用（Multiplexing）加持

在传统的 HTTP/1.1 时代，浏览器对同一个域名的 SSE 连接数有限制（通常最多 6 个），这导致如果一个用户开了好几个运维窗口对话，系统就会卡死。

但现在业内普遍升级到了 **HTTP/2**，在 HTTP/2 下，SSE 可以在同一个 TCP 连接上跑无数个流。这使得 SSE 既拥有了 WebSocket 的高并发能力，又保留了 HTTP 的简单轻量。

## 四、 回看你的 `ChatStream` 代码

现在你理解了 SSE，我们再回头看你刚才发的 `ChatStream` 里的核心循环：

```go
for {
   chunk, err := sr.Recv() // 1. 从 Eino 拿到大模型吐出的一个 Chunk
   if errors.Is(err, io.EOF) { ... }
   
   fullResponse.WriteString(chunk.Content)
   
   // 2. 这里的 SendToClient，在底层就是往 HTTP 响应体里写一行 "data: chunk.Content \n\n"
   client.SendToClient("message", chunk.Content) 
}
```

这就是标准的 SSE 在 Go 后端的体现！Eino 负责把大模型流式的 gRPC/SSE 流量接进来（`sr.Recv()`），而你的 GoFrame 控制器负责把这个流量转化为标准的 HTTP SSE 规范，转发给前端浏览器。

## 三次握手：
### 1. 趣味生活化比喻（听力测试）

想象一下，你（客户端）和面试官（服务端）戴着耳机进行一场远程语音面试，为了确认通话设备没问题，你们开始对话：

- **第一次对话**：
    
    - **你**：“喂，面试官听得到吗？（**SYN**）”
        
    - _你的心理_：我不知道我能不能说，也不知道你能不能听。
        
    - _面试官的心理_：**哦，这小伙子声音挺清楚，他能发，我能收。**
        
- **第二次对话**：
    
    - **面试官**：“听到了！你能听到我说话吗？（**SYN + ACK**）”
        
    - _面试官的心理_：我不知道我能不能说，也不知道你能不能听。
        
    - _你的心理_：**太好了。我刚才发过去他听到了（对方能收），我现在也听到他说话了（对方能发、我能收）。但我还没告诉他我能听见，他现在还不敢说正事。**
        
- **第三次对话**：
    
    - **你**：“听到了听到了，咱们开始面试吧！（**ACK**）”
        
    - _面试官的心理_：**完美，他也听到我说话了（我能发、他能收）。现在双向通道完全畅通！**
        

### 握手全过程拆解：

- **第一步（Client ➡️ Server）**：
    
    - 客户端向服务端发送一个 **SYN**（Synchronize）报文，表示想要建立连接。
        
    - 此时客户端随机生成一个初始序列号 `seq = x`。
        
    - **状态变化**：客户端进入 `SYN_SENT`（同步已发送）状态。服务端此时处于 `LISTEN`（监听）状态。
        
- **第二步（Server ➡️ Client）**：
    
    - 服务端收到 SYN 报文，同意建立连接。它需要做两件事：
        
        1. 确认收到客户端的包：回复一个 **ACK** 报文，确认号 `ack = x + 1`。
            
        2. 自己也想建立连接：同时发送一个 **SYN** 报文，也随机生成一个自己的初始序列号 `seq = y`。
            
    - **状态变化**：服务端进入 `SYN_RCVD`（同步已收到）状态。
        
- **第三步（Client ➡️ Server）**：
    
    - 客户端收到服务端的 SYN + ACK 报文。
        
    - 客户端回复一个 **ACK** 报文，确认号 `ack = y + 1`，自己的序列号 `seq = x + 1`。
        
    - **状态变化**：客户端发送完后，直接进入 `ESTABLISHED`（连接已建立）状态。服务端收到这个 ACK 包后，也进入 `ESTABLISHED` 状态。此时，双方可以开始愉快地传输业务数据（Data）了。
        

### 2. 灵魂拷问：为什么不能是“两次握手”？

这是面试官百分之百会追问的连环坑。
![[PixPin_2026-06-12_18-24-21.png]]

#### 答案一：为了防止“历史失效的连接请求”突然复活，造成服务端资源浪费（最标准答案）

- **场景**：客户端发了第一个建立连接的请求 A，但是在网络里迷路了（被网络节点堵住了）。
    
- 客户端等急了，以为 A 丢了，于是重新发了一个请求 B。这次网络很顺畅，三次握手成功，事情办完，连接关闭。
    
- **突然**，那个迷路的老请求 A 终于慢悠悠地飘到了服务端。
    
- **如果只有两次握手**：服务端只要收到 A，就认为连接建立了，立刻开辟内存资源等客户端发数据。但对客户端来说，A 早就是历史报废垃圾了，它根本不会理会服务端。结果就是，**服务端单相思，白白浪费了服务器资源。**
    
- **如果有三次握手**：服务端收到 A，回一个确认给客户端。客户端一看：“这啥啊？这不是我刚才丢的那个老古董吗？不予理会。” 服务端迟迟收不到第三次 ACK，就知道这个连接不作数，直接释放资源。
    

#### 答案二：为了让双方初始化并交换各自的“序列号（ISN）”

TCP 是可靠传输，靠的就是序列号来保证数据不丢、不乱序。三次握手才能确保双方都明确接收到了对方的初始序列号。

### 3. 生产安全痛点：SYN 洪泛攻击（SYN Flood）

聊到三次握手，如果你能主动和面试官提一下这个安全漏洞，职级评定直接往上涨。

- **攻击原理**：黑客利用伪造的随机 IP 地址，疯狂向服务器发送第一次握手的 **SYN 包**。
    
- 服务器收到后，极其认真地回复第二次握手的 **SYN+ACK 包**，并且进入 `SYN_RCVD` 状态，开辟好资源等待第三次握手。
    
- 但由于黑客的 IP 是伪造的，服务器永远也等不到第三次 **ACK**。
    
- 服务器会傻傻地在那里等待直到超时（通常有几十秒）。黑客一秒钟发几十万个这样的包，服务器的半连接队列（Syn Queue）瞬间被挤爆，导致正常的合法用户根本无法建立连接。
    

#### 怎么防范？

1. **降低 SYN 维持时间（Timeout）**：别傻等那么久，早点释放占座的资源。
    
2. **SYN Cookies 技术（大厂常用）**：服务器在收到 SYN 包时，**不立刻开辟内存资源分配座位**。而是用这个包的源IP、端口等信息算出一个加密的 `cookie`，作为序列号回发过去。只有对方能把第三次的 ACK 带着正确的 cookie 回传过来时，服务器才真正给它分配资源。
    

### 💡 面试作答黄金总结

回答 TCP 三次握手，请严格死守这个逻辑链：

1. **一句话定性**：三次握手是双向确认“能发能收”能力的过程，是无状态网络到可靠连接的基石。
    
2. **报文流转**：说出 SYN ➡️ SYN+ACK ➡️ ACK 三个动作，以及 `SYN_SENT`、`SYN_RCVD`、`ESTABLISHED` 三个状态。
    
3. **破除两手**：解释防止历史失效连接复活导致服务器死锁浪费的现象。
    
4. **高阶外延**：提一嘴 `SYN Flood` 攻击和 `SYN Cookies` 的防范策略。


## 四次挥手
![[Pasted image 20260612181530.png]]
 ### 1. 为什么断开连接需要“四次挥手”？

TCP 是**全双工**的通信协议。这意味着，客户端和服务端之间有两条并行的、互不干扰的单向通道：

- **通道 A**：客户端 ➡️ 服务端（客户端说话，服务端听）
    
- **通道 B**：服务端 ➡️ 客户端（服务端说话，客户端听）
    

当客户端想要分手时，它只能决定“我不向你发送数据了”**，但它无法替服务端决定**“你也不准向我发数据了”。

这就导致了服务端的 `ACK`（我知道你想分手了）和 `FIN`（我也想分手了）**无法像握手那样合并在一起发送**。

### 挥手全过程拆解：

1. **第一步（Client ➡️ Server）**：
    
    - 客户端发送一个 **FIN**（Finish）报文，用来关闭客户端到服务端的数据传送。
        
    - **状态**：客户端进入 `FIN_WAIT_1` 状态。
        
2. **第二步（Server ➡️ Client）**：
    
    - 服务端收到 FIN 包，回复一个 **ACK** 包。
        
    - **状态**：服务端进入 `CLOSE_WAIT`（等待关闭）状态。客户端收到这个 ACK 后，进入 `FIN_WAIT_2` 状态。
        
    - _此时，客户端到服务端的通道关闭，但服务端如果还有数据要发，客户端依然要接收。_
        
3. **第三步（Server ➡️ Client）**：
    
    - 服务端把最后的存量数据发完了，向客户端发送一个 **FIN** 报文，表示“我也要关闭通道了”。
        
    - **状态**：服务端进入 `LAST_ACK`（最后确认）状态。
        
4. **第四步（Client ➡️ Server）**：
    
    - 客户端收到服务端的 FIN 包，回复最后一个 **ACK** 包。
        
    - **状态**：服务端收到 ACK 后直接进入 `CLOSED`（彻底关闭）。**而客户端却必须在原地死等 2MSL 的时间后，确认没事，才进入 `CLOSED` 状态。**
        

### 4. 灵魂拷问：为什么客户端在第四次挥手后，必须傻等 2MSL 才能关闭？

> 💡 **名词解释**：`MSL`（Maximum Segment Lifetime）叫**最大报文生存时间**。2MSL 就是一个报文在网络里一去一回的最长生命周期。
![[PixPin_2026-06-12_18-29-34.png]]
这是四次挥手里最经典的面试题，原因有两个：

#### 原因一：为了保证第四次挥手的 ACK 报文能够安全到达服务端

网络是不可靠的。客户端发出的最后一个 ACK 包，完全有可能在路上丢了。

- **如果没有 2MSL 的等待**：客户端发完 ACK 直接拍拍屁股走了。万一这个 ACK 丢了，服务端在 `LAST_ACK` 状态下迟迟收不到确认，就会以为是自己的第三次挥手（FIN）丢了。于是服务端会**超时重传** FIN 包。但此时客户端早就关闭了，根本没人理它，服务端就会一直死锁在等待状态。
    
- **如果有 2MSL 的等待**：客户端发完 ACK 在原地留守。如果 ACK 真的丢了，服务端重传的 FIN 包就会在 2MSL 时间内再次飘到客户端。客户端一看：“哎呀，刚才的拜拜包对方没收到。” 于是重新补发一个 ACK，并重新倒计时 2MSL。这保证了服务端能体面地关闭。
    

#### 原因二：为了让本次连接中产生的所有“网络残留报文”全部死在路上

如果不等 2MSL 客户端直接关闭，然后操作系统极其巧合地马上又用**相同的源 IP 和端口**建立了一个新连接。这时候，上一次连接因为网络拥堵而迷路的那些老报文，突然“复活”飘了过来。新连接收到这些老古董报文，会导致数据错乱。 等了 2MSL，就能确保上一次通信的所有残余报文在网络中全部因超时而自然消失。

### 5. 生产灾难：大量 `CLOSE_WAIT` 或 `TIME_WAIT` 怎么破？

如果你在线上遇到网络问题，用 `netstat` 命令一查，发现服务器上堆积了成千上万个某种状态，这通常对应了严重的业务 Bug：

- **服务器出现大量 `CLOSE_WAIT`**：
    
    - **原因**：对方已经发了 FIN（第一次挥手），我方也回了 ACK（第二次挥手）。但我方（服务端）的代码里**迟迟没有调用 `close()` 方法**去触发第三次挥手。
        
    - **根源**：通常是**代码里有 Bug**。比如数据库连接或 HttpClient 用完没在 `finally` 里释放，导致连接泄露。
        
- **服务器出现大量 `TIME_WAIT`**：
    
    - **原因**：**谁主动发起断开连接，谁就会进入 TIME_WAIT**。这说明服务器正在疯狂地主动跟客户端断开连接。
        
    - **根源**：高并发下采用了**短连接**（比如没有开启 Keep-Alive 的 HTTP 服务）。每处理一个请求就主动关掉连接，导致几万个端口全被 `TIME_WAIT` 占着死等 2MSL，新连接根本进不来。
        
    - **解法**：开启 HTTP 长连接（Keep-Alive），或者修改 Linux 内核参数（如 `tw_reuse`）允许端口快速复用。
        

### 总结：进出门全景口诀

- **进门 3 步（握手）**：客户端想进 ➡️ 服务端同意并也想进 ➡️ 客户端确认。双向通道开通。
    
- **出门 4 步（挥手）**：客户端要走 ➡️ 服务端说你等等 ➡️ 服务端说我也好了 ➡️ 客户端说收到并留守 2MSL 站最后一班岗。双向通道关闭。
